# Spec index

Specs are the source of truth (CLAUDE.md). Module specs inherit the Shared Standards in the foundation spec (§6) and do not redefine them. The foundation changes only through a version bump approved by the owner, with a changelog and "Changed by" markers, like any module spec (R34); appending an error code that a module spec defines (foundation §6.2) needs no bump.

> ⚠️ Changed by 01d v1.0 (R-5): was "The foundation is frozen at v1.7 (D64): later issues are fixed in module specs or covered by unit tests." See R34.

**File naming:** `NN_<Module>_Spec_v<major>.<minor>.md`. `NN` is the build order below (`03a`/`03b` keep the shared number). On a version bump the file is renamed and this index is updated in the same commit. The foundation is versioned like a module spec since R34 (`00_Foundation_Spec_v1.8.md`; earlier versions kept as history) and is listed as row **F**; module `00` is Hub Platform & Access (R2).

## Spec size budget

- A module spec covers about **10–25 commands/endpoints**.
- **Split** a spec that grows above ~30 commands/endpoints or ~60 build tasks.
- **Merge** a spec that has fewer than 5 commands/endpoints into its neighbour.
- Each split or merge is recorded below as a README decision and in the module map.
- For 00, the ~30 applies to the cloud access part (00 §6.33). *(Changed by 01d v1.0, R-9, with 00 v1.6 H-11.)*

## Module spec approval checklist

Every module spec is checked against this list before its status moves to Approved. A reviewer ticks every line in the review file in `docs/reviews/`. One unticked line blocks approval.

**Section order (Module mode, exactly these 12 sections, in this order):**

- [ ] §1 Header: module name, version, depends on (spec + version), stories covered, in scope, out of scope, "inherits Shared Standards from Foundation v1.8" (the current foundation version).
- [ ] §2 Existing architecture that must not change (from the foundation and earlier modules).
- [ ] §3 Domain rules specific to this module (state machines, eligibility, conflicts, module decisions).
- [ ] §4 Contracts: what it consumes and what it exposes. Later modules rely only on what is listed here.
- [ ] §5 Data model and migrations (tables, columns, constraints, indexes with the query each one serves).
- [ ] §6 Endpoints, commands and events in the Phase 3 format, in batches of about 8.
- [ ] §7 Cross-cutting items for this module only, each YAGNI-justified.
- [ ] §8 Client contract (if the module has clients).
- [ ] §9 Error catalogue additions.
- [ ] §10 Tests: per-endpoint integration cases, concurrency and race cases, acceptance table (story AC → test).
- [ ] §11 Build order: an ordered checklist with target files, each item citing spec sections.
- [ ] §12 Definition of Done, final endpoint checklist, Open Questions, Deferred until needed.

**Inherits foundation §6 (does not redefine it):**

- [ ] §6.1 envelope: every response is `{ data }` or `{ error }`; no 204; idempotent replay returns the stored response with `Idempotent-Replay: true`.
- [ ] §6.2 errors: every new code is `<SUBJECT>_<CONDITION>`, has a status from the status map, a typed `details` shape and the condition that returns it; no existing code is renamed or reused.
- [ ] §6.3 hub HTTP: commands go through `POST /commands/:name` via the registry; each per-command script is a subset of the fixed processing order; queries make no writes and use a fixed number of SQL statements.
- [ ] §6.4 cloud HTTP: `/v1` prefix; `Idempotency-Key` on creating `POST`s (or a recorded reason why not); tenant guard on every route.
- [ ] §6.5 WS: new message types are added to the `WsServerMessage` / `WsClientMessage` unions; catch-up part defined per role.
- [ ] §6.6 naming: one fact per event (`<Subject><PastTenseVerb>`), commands `<Verb><Subject>`, snake_case on the wire, `_at` / `_ms` / `_minor` suffixes.
- [ ] §6.7 tests: per hub command, happy path + one test per error code + retransmit test (D32) + COMMIT-failure test where the engine is touched (D45); numbered spec tests cited in test names.
- [ ] §6.8 migrations: forward-only `NNNN_<name>.sql`; no edits to merged files; money as `_minor` integers; times as Unix ms.
- [ ] §6.9 folders: new files only inside the listed folders.

**Consistency:**

- [ ] Every foundation section the spec overrides is named in a decision with its reason, or changed through a foundation version bump listed in its "Changes to other specs" table (R34; was the D64 freeze rule, changed by 01d v1.0).
- [ ] Every change to an earlier approved spec is listed in this spec's own "Changes to other specs" table, and the target spec is bumped with a changelog entry and an inline "Changed by" marker at each edited section (R26).
- [ ] Status codes match between §6 endpoints and §9 error catalogue; permissions used exist in the permission catalogue.
- [ ] No forward reference to an unwritten module except through an "Exposes" contract.
- [ ] Size is inside the spec size budget.
- [ ] Hostile self-review done: races, idempotency gaps, missing indexes, N+1, privacy leaks, over-engineering.

## Carried conventions

Rules every module spec written after 01b follows (and cites by number), folded from `docs/reviews/01b-auto-decisions.md` on 2026-10-28 and corrected by the as-built review (`docs/reviews/01b_v1.1_asbuilt_review.md`). Each convention states what **new** modules do; where 01a or 01b differs, the row names the divergence and both are kept as built. Where 01a and 01b disagree, a module follows the one it extends (01c extends 01a, so 01a's behaviour is its default) (R27). A module that needs to depart from one names it in a decision with its reason, as for a foundation override.

| # | Convention | Source |
|---|------------|--------|
| C1 | **Lists are sets; unknown ids are `not_found`.** New modules: a repeated id in a list of ids is dropped, not refused; the stored and returned list holds it once. Error `field` paths name the list and the index **as sent**: `<list>.N.<key>`, `<list>.N.<sublist>.M` for a nested list. A referenced id that does not exist answers `422 CONFIG_REFERENCE_INVALID { field, reason: 'not_found' }`, as 01a does (`restaurant/service.ts`, `assertReference`). **Divergences, both kept as built:** 01b answers `reason: 'not_at_branch'` for an unknown person in `responsibilities.N.staff_ids.M` and `reports_to.N.lead_staff_id` (one check covers unknown and not working there), and `404 BRANCH_NOT_FOUND` for an unknown id in `branch_ids`. | AD-11; R27 |
| C2 | **A foreign branch is a 404.** A `branch_id` in a query string or path that is outside the owner's allowed branches (the JWT's `allowed_branch_ids`: another tenant's, unknown, or not allowed to this owner) → `404 BRANCH_NOT_FOUND { branch_id }`.
