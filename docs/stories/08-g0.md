## 0. Naming (read first)

| Term | Meaning |
|---|---|
| **hub** | The local per-branch server (SQLite, event-sourced, offline-first). NOT a kitchen. |
| **CK (commissary)** | Central kitchen that makes coded packets (TP-1, QM-1, PY-1) and bases. Location type `commissary`. (Replaces "hub_kitchen" from source notes.) |
| **raw item** | Purchased ingredient (beef, paye, ghee, onion). |
| **packet item** | Coded CK output sent to branches (TP-1…). Stock unit = **g**. |
| **produced item** | Output of a `per_batch` recipe at a branch or CK (PAYE-COOKED piece, QEEMA-COOKED g). |
| **AP / EP** | As Purchased / Edible Portion. |
| **business_date** | Trading day with a cutoff (default 04:00) — every inventory event carries it. |

## 1. Decisions log (conflicts resolved)

| # | Topic | Decision | Why |
|---|---|---|---|
| D1 | Void food outcome | System derives `prep_state_at_void` (not_fired / fired_not_started / in_progress / done / unknown) from KOT + station taps. If state ≥ station `consumption_point`, the voider (or manager) must pick `food_outcome_at_void`: `made_wasted` \| `made_reused`. If below, outcome = `not_made` automatically. Choosing `not_made` against a KDS state of in_progress/done needs manager override + reason. | Brown: taps are reliable data & father enforces taps. Dopson: costing needs the *outcome* (reused vs wasted), and rush can make taps late. Merge keeps both; cashier cannot falsely claim "nahi bana tha". |
| D2 | Station consumption point | `station.consumption_point`: tawa/karahi/tandoor = `on_start`; degh-serve (paye, qeema, chanay) = `on_done`. `unknown` → tenant `unknown_void_policy`, default `consumed` (+ flag). | Brown. |
| D3 | Price vs cost source | `PriceObserved` = **price history only** (kinds: manual, quote, market_rate, grn). **Moving weighted average (MWA) is driven only by stock-receipt events** (`GoodsReceived`) that carry qty + price. Each costed receipt line also emits `PriceObserved{grn}` for trend. | Brown's single-source rule. Dopson's goal (real MWA for A-items in pilot) is still met because the pilot quick-receive writes `GoodsReceived` with qty + price. |
| D4 | Receiving event | **One event: `GoodsReceived`**, with `mode: quick_receive | supplier_delivery | cash_purchase | night_drop`. Pilot uses only `quick_receive` (minimal fields). No separate `StockReceived`. | Avoids a pilot-only event that must be migrated later. |
| D5 | Count event | One `CountRecorded` shape supporting both pilot daily sheet (business_date, raw + cooked) and POST sessions (session_id, entries[]). | Merge of both shapes. |
| D6 | Kg items | `recipe.basis = per_kg` + `kg_basis: raw_input | served` + `base_qty_kg`. Sale line: `sold_qty_kg`, `weight_source: nominal | weighed`. | Dopson ("1 kg karahi" = raw gosht). |
| D7 | qty_basis | No default. Derived: `per_batch` → AP, `per_unit`/`per_kg` → EP. Warn on EP line inside per_batch. | Dopson (avoids double yield). |
| D8 | Yield storage | Fraction, `CHECK (yield > 0 AND yield <= 5)`. >1 allowed (chanay, rice, dough). | Dopson. |
| D9 | Missing data | Missing price or missing yield ⇒ `cost_status = partial`. Never assume price 0 or yield 1.0. | Dopson. |
| D10 | Secret BOM | Packet recipes (`visibility_scope = ck_only`) — both `RecipeVersionPublished` and `ProductionBatchRecorded` for them — live in a **CK-only stream**, never replicated to branch hubs. Branches only receive `StockTransferDispatched {lot_code, item: TP-1, qty, unit_cost}`. | Brown (batch) + extended to recipes; otherwise the BOM sits raw in branch SQLite. |
| D11 | Default variant | Every menu item has ≥1 variant; default variant "Regular" auto-created, hidden while alone, **renamed** (not replaced) when a 2nd variant is added; never deleted if it has recipes/sales (archive only). | Both chats. |
| D12 | Comps & voids in usage | Comp lines (staff/owner/guest/remake) go into **theoretical usage**. Voids with `made_wasted` emit `WasteRecorded{reason: void_after_prep, source: system}`. `made_reused` = no extra usage. | Otherwise comps show as theft. |
| D13 | Pilot count | Not a full count module. **A-item daily sheet** (§3.9) for 5 items. | Dopson's challenge accepted; needed so the pilot detects loss, not just prices. |

### 3.1 Units & conversions — PILOT
```jsonc
UnitConversionDefined {
  conversion_id,
  scope,              // "global" | "item"
  item_id,            // required iff scope = item
  from_uom, to_uom,   // e.g. piece → g, peti → kg, darjan → piece, pao → g
  factor,             // NUMERIC(14,4)
  effective_at
}
```
- Seed globals: kg↔g, pao = 250 g, maund = 40 kg, darjan = 12, tray = 30 (eggs).
- Item-specific (versioned): paye `1 piece ≈ X g` — updated from weigh tests; on-hand stock is never recomputed when it changes.
- Convertibility validated at **recipe save**, never at sale time.

Price change audit: every price write is an event (user + note); jump > X% → owner alert (alert = POST).

### 3.5 Cost resolution — PILOT
Projection `item_cost[item, branch]`:
1. MWA from `GoodsReceived` lines for (item, branch), if any (pilot: A-items via quick receive).
2. Else latest effective `PriceObserved` with kind ∈ {manual, market_rate}: branch-specific first, then tenant-wide; tie → latest valid_from, then recorded_at.
3. `quote` never becomes cost.
4. Packet items at a branch: cost = branch MWA of transfer-in cost (pilot: manual price on the packet item).

MWA:
```
new_avg = (on_hand × avg + recv_qty × landed_unit_cost) ÷ (on_hand + recv_qty)
if on_hand ≤ 0: new_avg = landed_unit_cost        // offline sale synced before receipt
```

### 3.6 Yield profile — PILOT
```jsonc
YieldProfileSet {            // append-only
  yield_profile_id, item_id, supplier_id?,
  yield,                     // fraction, 0 < y ≤ 5
  source,                    // manual_test | batch_avg (POST)
  test_ap_qty?, test_ep_qty?,
  effective_at
}
```
- Pilot: one active profile per item. Resolution (POST): item+supplier → item default.
- Explosion of past sales uses the yield effective at sale time.

### 3.7 Recipes — PILOT
**recipe_version** (immutable once published):
| Field | Notes |
|---|---|
| recipe_id, version | one `published` per (owner_type, owner_id) |
| owner_type | variant / addon_option / produced_item |
| owner_id | |
| basis | per_unit / per_kg / per_batch |
| kg_basis, base_qty_kg | required iff per_kg (default 1.0) |
| batch_yield_qty, batch_yield_uom | required iff per_batch; owner MUST be produced_item |
| portion_qty | informational for per_unit (cost_per_portion = total) |
| scale_with_parent | add-ons only (true = scales with kg parent) |
| misc_allowance_pct | default 5%; applies to **cost only**, never to usage |
| visibility_scope | all / ck_only |
| prep_instructions, finishing_holding, serving_utensil, plating_photo, accompaniments[] | optional |
| effective_at | backdating only via restatement (POST) |

**recipe_line:**
| Field | Notes |
|---|---|
| item_id | raw / packet / produced |
| qty, uom | negative allowed only in addon_option recipes |
| qty_basis | AP / EP, derived per D7 |
| is_garnish | optional |

Cost fields (`total_cost`, `cost_per_portion`, `cost_status`, `cost_computed_at`) are a **projection**, not part of the published event.

Events: `RecipeDraftSaved`, `RecipeVersionPublished`, `RecipeArchived`.

Validation (at save):
- Unit convertibility for every line.
- Removal add-on valid only if the item exists in the parent's recipe version.
- Sub-recipes: cycle detection, max depth 3.
- `kg_basis = raw_input` → main protein is an AP line with qty ≈ base_qty_kg; `served` → main line is a produced item.
- EP line inside per_batch → warning.

Example structure:
- `PAYE-COOKED` (produced, piece) ← per_batch recipe: 40 paye (AP), ghee, onion, adrak-lehsan, 2 × PY-1; batch_yield = actual servable pieces.
- Variant "Paye Half" ← per_unit: 1 PAYE-COOKED + shorba.
- Variant "Tawa piece" ← per_unit: beef EP 250 g, TP-1 15 g, oil, onion, tomato, makhan.
- Variant "Chicken karahi" ← per_kg, kg_basis raw_input, base 1.0 kg.

### 3.8 Cost formulas — PILOT
```
cost_per_stock_unit = item_cost[item, branch]            // §3.5, normalized
line_cost = convert(qty, line.uom → stock_uom) × cost_per_stock_unit ÷ (qty_basis = EP ? yield : 1)
recipe_cost = Σ line_cost × (1 + misc_allowance_pct)
produced_item unit cost = batch recipe_cost ÷ batch_yield_qty
per_kg line cost at sale = cost per base_qty_kg × (sold_qty_kg ÷ base_qty_kg)
deal cost = Σ chosen component costs + chosen add-ons   // menu shows min/max range
suggested_price (ex-tax) = cost_per_portion ÷ target_food_cost_pct
target_food_cost_pct (MFC) = 1 − (non_food_cost_pct + profit_pct)   // tenant/branch setting
cost_status = costed | partial (missing price/yield) | no_recipe
```
Precision: NUMERIC(14,4); round at display only.

### 3.9 Sale snapshot — PILOT
```jsonc
SaleCompleted.lines[] += {
  parent_line_id,          // add-on / deal component
  line_kind,               // item | addon | deal | deal_component
  variant_id, addon_option_id,
  sold_qty_kg?, weight_source?,   // per_kg items
  recipe_version_id,       // null = no recipe
  cost_basis,              // per_unit | per_kg
  unit_cost_snapshot, line_cost_snapshot,
  cost_status,
  revenue_allocated: null  // POST
}
// + sale.config_watermark (last applied config-stream seq on the hub)
```
Rules:
- Deal line has no own cost; = Σ children.
- Ingredient lines are not snapshotted; theoretical usage is exploded later from `recipe_version_id` + yields effective at sale time.
- Snapshot computed on the hub using only versions/prices that are **synced locally and effective ≤ completed_at**.
- Never mutated. Late sync / backdating → `SaleCostRestated` (POST).

### 3.12 A-item daily sheet — PILOT
Items (initial): paye, beef, ghee, anday, coded packets. Business date cutoff 04:00 (configurable).

```jsonc
GoodsReceived {                       // mode = quick_receive in pilot
  grn_id, branch_id, receiving_location_id, mode: "quick_receive",
  supplier_id?, supplier_name_freetext?, received_by,
  lines: [{ item_id, qty, uom, qty_stock_unit,
            piece_count?,             // paye: kg AND pieces
            price_total?,             // present ⇒ MWA update + PriceObserved{grn}
            receipt_photo? }]
}

StockTransferDispatched { transfer_id, from_location_id, to_location_id, lot_code?,
                          lines: [{ item_id, qty_stock_unit, unit_cost_snapshot }] }
StockTransferReceived   { transfer_id, received_by,
                          lines: [{ item_id, qty_stock_unit }] }   // ≠ dispatched ⇒ discrepancy

WasteRecorded { waste_id, location_id, item_id, stock_qty, uom, unit_cost_snapshot,
                reason,   // spoiled | expired | dropped | burnt | quality_reject | void_after_prep | ...
                stage,    // raw | cooked
                source,   // user | system
                sale_line_id?, photo?, recorded_by }

CountRecorded {
  location_id, item_id,
  kind,                     // opening_seed | closing | spot (POST)
  session_id?,              // POST sessions
  raw_entries: [{ full_units, partial_fraction?, weight_kg? }],
  cooked_qty?, cooked_uom?, // WIP / leftover: pieces, g
  qty_stock_unit_equiv,     // SYS: raw + cooked converted (pieces ÷ pieces_per_trotter etc.)
  is_estimated, counted_by
}

DailySheetClosed {          // immutable snapshot; correction = new one with supersedes
  branch_id, business_date, closed_by, recipe_coverage_pct, supersedes?,
  items: [{ item_id, opening, received, transfer_in, transfer_out, waste, closing,
            actual_usage, theoretical_usage,
            variance_qty, variance_pct, variance_value, unit_cost_used,
            flag }]             // ok | over | under | unreliable
}
```
Formulas:
```
opening  = previous closing (or opening_seed)
actual   = opening + received + transfer_in − transfer_out − waste − closing
theoretical = Σ (sold + comp lines) × recipe explosion through produced items (pieces → trotters)
flag over/under iff |variance_pct| > 3% AND |variance_value| > Rs 500   (both configurable)
flag unreliable iff recipe coverage by revenue < 95% OR chain broken (missing closing → 2-day period, shown)
```
