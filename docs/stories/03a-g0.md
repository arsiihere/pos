## 1. What 03a is (in one paragraph)

03a is the kitchen's timing brain. It has no screens. It computes ETAs before an order is punched, fires each item at its latest start so an order lands together, fills batch loads, uses pre-cooked stock time while stock lasts, re-plans when capacity changes, warns the table's order taker when an order slips, and rebuilds all of that from the event log after a power cut without firing anything twice. 02 and 03b display what it computes.

## 4. Decisions (G1, developer with the owner's answers of 2026-11-02)

**Scope**

| ID | Decision |
|---|---|
| D1 | **Nothing is deferred.** Owner (2026-11-02): "this is to be implemented from day 1". Cascade (D42), overrun (D33), hold at pass, boost (D3), live capacity, slip warning, settings screen — all pilot. Taps are mandatory by restaurant rule, so `two_tap` is the default (§3 #10). |
| D2 | 03a = engine package + hub host only. Ready to serve / Handover → 03b; `TableLockReleased` and estimated Served → 02 (§2). |

**Dispatch algorithm (per station)**

| ID | Decision |
|---|---|
| D3 | **Policy per station, knobs per item.** A station picks one of three variants: **Waada Guard** (default), **EDF**, **FIFO**. One engine, three switches: **FIFO = no hold**: fire as soon as a slot is free, in submit order (today's kitchen; ETAs still computed, naan may be ready early); **EDF** = hold-and-fire, Waada Guard with weights 1, keep 0, padding 0. Item knobs: `weight`, `max_early_ms` (slot stations: how early it may be fired to fill idle capacity; batch stations: caps the station's `freshness_window_ms` for this item — the join rule D14/D17 is unchanged, no second concept), `max_carry_ms` (how far it may travel), `max_late_ms` (overload: the share of lateness this item may carry; past it the engine stops shifting it and raises `station_overload`, D20 — it is a reporting cap, never a refusal). Order-type weight multipliers: dine-in, takeaway, delivery, parking, **`follow_up`** (default 3). **Delivery:** the target is the rider pickup time 02 sets on the order (sync to it like a karahi), not "as soon as possible". All config (R18); pilot values are constants until the owner asks. |
| D4 | **Waada Guard, normal load:** the promise given to the customer never breaks. Within an item's slack, priority = `weight × waiting time`. Items may be fired early up to `max_early_ms` to fill idle capacity (D16). **The one allowed promise-breaker is boost (D3 story):** a boosted order takes the earliest fit, displaced orders get slip warnings (foundation §4.7 "Boost"); nothing else may push an item past its target. |
| D5 | **Overload** (promises cannot all be kept): lateness is shared evenly — EDF on the engine target, weighted (a weight-2 item carries half the lateness). Owner answer A (2026-11-02). Proven optimal only for one slot; heuristic for capacity > 1; the simulator decides (§6). |
| D6 | **Breathing room (Hole 2 fix):** `promise_padding_ms` (branch or station; default 180 000) is added **only to the promise shown to people**, never to the engine target — slack is measured from the target, so padding is never consumed by other orders. `min_slack_keep_ms` (station; default 60 000): the last part of every item's slack is never given to another order. |
| D7 | **`follow_up` flag (Hole 1 fix):** 02 flags an order whose table already has a served order; the engine only sees its weight. |

**Routing across stations**

| ID | Decision |
|---|---|
| D8 | **An item goes where it reaches its point earliest:** `arrival = ready time + carry time(station → point)`. Config: carry time per station → point (01a v2.1, measured with a stopwatch first, learned from K11 events later), `min_gain_ms` (route elsewhere only if it saves this much), allowed stations per order type, `reserve` slots per station for its home type (default 0). |
| D9 | Ties (gain < `min_gain_ms`) go to the order type's **home station**. At Lake City all stations and both tandoors are adjacent (carry 0), so this reduces to "wherever it is ready first"; the same code serves a kitchen with a tandoor per floor. |
| D10 | **Re-routing (Hole 4 fix):** only items still hidden from the chef (D16 "later") may move stations. An item in Now / Next belongs to that station; on station Off the assembler reassigns those by hand (K8). |

**Sync, split sends, "goes with"**

| ID | Decision |
|---|---|
| D11 | **Sync stays sync; a human splits it.** When a sync order's estimated land time passes **`target + slip_threshold_ms`** (measured from the engine target, so the order taker hears before the padded promise is blown; the card shows minutes against the *promise*), the slip warning reaches the table's order taker as a **01d `named` request** (`needs_pin: 'never'`, answers `send` / `wait`, receiver = the table's current owner via `table_team depth: 'owner'`), not as an info card with bolted-on buttons — the request model, `apply` handler and receipts already exist. `apply` on `send` returns `ItemsReleased { order_id, alert_id, released[], expedite[] }` (read-only contract, 01d §3.5). The order taker may also open the same card from the table view at any time (02 raises the request itself). No automatic split. The waiter is alerted digitally (Ready-to-serve kind, 03b) and the assembler view shows the released items as "go". Permission: the table's `mark-served` holder (same person who marks Served; no new permission). |
| D12 | **"Goes with" links** (01a v2.1): category default + item override, soft (a suggestion, never a rule). The Send card pre-ticks remaining items linked to what is being sent (roti with karahi, raita with pulao; nothing with biryani); the order taker can change any tick. Ticked items are `expedite`: they become immediate with the `follow_up` weight; untick items stay sync with each other. No links configured → nothing pre-ticked, still works. Owner answer C (2026-11-02). |
| D13 | **Re-plan on every submit (D23 bump):** a new order may move the *internal* fire times of older unfired items within their slack (D6 keep applies); the promise never moves. Owner answer A. Re-plan still runs on void, boost, stock update, capacity change, `ItemsReleased`. Frozen items (D16) are fixed input to the re-plan. **No events for it (D44 kept):** the submit re-plan is a pure function of `(state, OrderPlaced, recorded_at)` inside `applyEvent`, so replay reproduces it exactly and no `ReservationsShifted` is written — R6's ≈ 45k/day stands. `ReservationsShifted` stays tick-only (overrun / late start depend on `branchNow`). The freeze window (D16) is evaluated against the event's `recorded_at`, never a wall clock, for the same reason. **Cost bound (spec §7):** a re-plan touches only the unfired items of the stations the new order uses (≤ ~100 at design size); the spec states a measured per-submit and per-replay bound against the 90 s boot budget, with the day-close checkpoint (README "To 03a" row 1) keeping replay to one day. |

**Chef screen contract (03b builds it; the engine must support it)**

| ID | Decision |
|---|---|
| D14 | Tandoor is a **slot** station (each naan starts and finishes alone; capacity = wall slots, ~30). Batch = everything starts and ends together (fryer basket, paye degh). |
| D15 | **Freeze window** `freeze_ms` per station (default 120 000; tandoor 1–2 min, karahi 3–4 min, degh 0): items whose fire time is within it are fixed and shown; nothing before them may be inserted. |
| D16 | Chef screen = **Now** (fired; never moves, D44) + **Next `freeze_ms`** (frozen) + **"Later: N"** (count only). | D17 | **Screen rule:** new tickets append at the bottom; Done removes that line (usually the top); the engine never reorders what is visible. Only human-triggered items (expedite D11, boost, Give me more) jump to the top, with a red marker and the reason ("T12 is eating"). |
| D18 | Start and Done are tapped per **line** ("T5 Roti ×4" is one tap), not per piece. |

## 6. Simulator drill (2026-11-02, `03a-sim/tandoor_sim.py`)

One tandoor, 10 naan at once (200 / h), 2 h rush, dispatch only (no reservation timeline, so EDF / Waada Guard numbers are pessimistic). "late" = done after the promise; "cold" = minutes a dine-in naan waits for its karahi.

| Load | Policy | Dine-in | Takeaway | Follow-up |
|---|---|---|---|---|
| Normal 90 % | FIFO (today) | late 0 %, **cold 14 min** | late 82 % | late 92 % |
| Normal 90 % | EDF, no keep / pad | late 65 %, cold 0.3 | late 67 % | late 67 % |
| Normal 90 % | Waada Guard + keep 60 s + pad 3 min | late 22 %, cold 0.3 | late **2 %** | late **0 %** |
| Peak 100 % | Waada Guard + keep + pad | late 75 %, max 7.6 min | late 28 %, max 3.1 | late 6 %, max 0.5 |
| Overload 125 % | any | 20–30 min late for everyone |

Yardstick note: with padding on, "late" is measured against the padded promise (what the customer was told), so part of the drop is the later time itself; wait times are unchanged across the two Waada Guard rows (takeaway 4.5 min both), which is the honest comparison.

Findings: FIFO is exactly today's problem (cold naan, takeaway waits); just-in-time firing without a cushion breaks promises even at light load (Hole 2); D6's two knobs are the single biggest win; weights work (follow-up max late 6.9 → 0.5 min at peak); at 125 % no policy helps — only capacity or fewer punches, hence D19–D21. Dine-in at peak carries the lateness because takeaway and follow-up are weighted higher; flip the weights if the owner prefers (field Q9).
