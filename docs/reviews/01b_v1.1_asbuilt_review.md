**S-2 · 01b:333, 01b:783 (AD-19) against `apps/cloud/src/modules/staff-roles/service.ts:625-626`: a duplicate station in a no-op PUT answers 200, not 422.**
`putResponsibilities` builds the merged set with `toResponsibilitySet`, which merges rows by station (`versions.ts:71-84`). It returns the no-op **before** `checkResponsibilities`, where the duplicate check lives (`service.ts:697-699`). Example: the stored set is S = {A} and the body is `[{S,[A]},{S,[A]}]`. That answers `200`, not the marked `422 { field: 'responsibilities.1.station_id' }`. In the same way, an entry for an unknown or archived station with empty lists answers 200 when the rest is unchanged. v1.0 already said "≤ one entry per station". No test covers the duplicate case at all (nothing in `responsibilities.int.test.ts`).
*Fix:* run the duplicate-station check (it is structural) before the no-op compare, and add a test. Alternatively, amend AD-19 and C6 to say "unless the PUT is a no-op (C4)". I recommend the code change, because a structurally invalid body should not depend on the stored state.

**S-3 · README:128 (C4) "no-op decided … before any rule": the 01b role PATCH does the opposite.**
`updateRole` runs `checkGrants` (duplicate permission, approvers iff `requires_approval`, approver states, scope) **before** the no-op compare (`service.ts:380-393`). Staff PATCH (`service.ts:226`) and responsibilities PUT (`service.ts:625`) compare first. So one module already has two orders: a role PATCH whose grants duplicate a stored permission answers 422, while the same shape on responsibilities answers 200.
*Fix:* name the role PATCH as a known divergence in C4 (the way C9 does) or align the code. Either way, decide before 01c copies one of the two.

**S-4 · README:128 (C4) and 01b:1228 (D-16): C4 carries the rule that D-16 leaves open, and D-16's example cannot happen.**
C4 makes "unsent fields are trusted" a convention for every later module. 01b §12.3 still lists that same rule as an open contradiction, and D-16 ends "until decided, the code's rule stands". That wording conflicts with CLAUDE.md ("If code and spec disagree, STOP and ask").
D-16's example ("a stored lead who has since left is not re-checked by a rename") cannot happen. When a lead leaves, B15 moves their reports at every branch (`service.ts:258-263`, `movedAt = leaving ? before.branch_ids : removed`), so no stored lead row points at a leaver. The same holds for a lead removed from a branch. A stored archived role also cannot exist, because a role archive deletes its `staff_roles` rows (`repository.ts:193`). That leaves only one observable difference: a floor archived after it was assigned. v1.0 §3.2 rule 6 (01b:276) already says "A floor archived later keeps its rows".
*Fix:* close D-16 now with this analysis, amending §6.4 to the built rule (it is consistent with v1.0). Correct the example and delete "the code's rule stands". Until then, mark C4 as provisional.
