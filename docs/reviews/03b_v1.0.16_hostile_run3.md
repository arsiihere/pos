## BLOCKER

### R3-B-1 — The boost rule strands an early pickup or makes it ready too soon

**Where** — §3.4 ll. 242, 249, §6.15 l. 564, §10 tests 110 and 116 (ll. 778, 784).

**Evidence** — §3.4 l. 242 keeps `pickup_at_ms` after Boost. The tap, catch-up and tests still say “null after a boost”. Obeying the catch-up/test makes the client lose pickup readiness. Obeying the owner with the current tap predicate still holds a station-less Cola until the original pickup time after Boost. 03a §12.3 Q-PK-9 l. 2181 requires retaining the timestamp and using `EngineOrder.boosted` to clear the hold. 02b §3.7 l. 328 carries that rule, while its §4.2 l. 421 still says the timestamp becomes null and uses the original time for station-less readiness.

**Fix** — Carry the stable pickup timestamp and boost state in `point_view`, live order metadata and the 02b readiness source consumed by the tap and board. Update the live state on `OrderBoosted` and preserve it on reconnect. Use the timestamp to select whole-order readiness and the boost state to release only the time hold. Amend tests 74, 110 and 116 to assert the same early-pickup case live and after reconnect: an unmade held drink still blocks after Boost, then a completed bag with a station-less Cola can be handed over before the original time.

### R3-B-2 — One manager approval unlocks sibling Pass cards

**Where** — Owner review OR-7, §3.4 l. 249, §4.3 l. 385, §10 test 113 l. 781.

**Evidence** — `docs/plans/02b-tk-rulings.md:43` and 03b say the unlock applies to that order only. The card sends its own ID, but 02b §3.7a ll. 320–321 dedupes by bill key, captures the existing unpaid siblings and sets the flag on each. 02b §10 test 92 l. 1025 expressly unlocks both root A and addition B from the request for B. Every affected Pass card then meets 03b’s flag check.

**Fix** — Align the pilot drafts with OR-7. Key the request and dedupe by the requested order ID, use the bill key only to read the amount, and stamp only the approved order. For the counter’s group action, re-evaluate authorization for each order it would serve. Update 01d’s carried request row and 02b test 92. Extend 03b test 113 with two simultaneously unpaid cards on one bill key: approve B, A remains grey.

### R3-B-3 — Undo at one point leaves the other point ringing “ready”

**Where** — §3.5 steps 2–5 and Closing, ll. 262–271, 274, 286, §6.21 ll. 580–588, §10 tests 102–103 ll. 770–771.

**Evidence** — B marks its drinks Ready first, then A completes the bag and owns the only alert with `counter_screen`. Undo B within its window. Undo closes B’s alert and leaves A’s lines unsettled but still in A’s Ready. A’s alert retains its fixed gate and keeps ringing at 1×/2× for an incomplete bag. Test 102 undoes A only. The merged Undo reads the current point’s Ready and closes its alert (`apps/hub/src/kds/commands/ready.ts:318–347`). A new return line on another point can break the same invariant without touching A’s Ready.

**Fix** — Define a single counter-alert owner per order. On a commit that loses bag completeness, close or replace the counter-enabled alert while preserving the underlying per-point Ready memberships. On regained completeness, close its predecessor and start one fresh clock, including completion triggered at a different point. Specify the transactional read and close budget. Extend tests 102–103 with Undo at B and a new return at B, and assert silence at both deadlines until the bag becomes complete again.

## MAJOR

### R3-M-1 — Archiving a routed point strands its existing work (OWNER)

**Where** — PT-3/PT-4 ll. 121–122, §3.1 l. 190, §3.5 step 1 l. 261 and Handover step 1 l. 277.

**Evidence** — 01a PT-6(c) l. 158 permits archiving a routed-only point and preserves the old lines’ point. The cloud archive guard checks active stations naming it as default (`apps/cloud/src/modules/restaurant/service.ts:1051–1055`). Both commands require a live point, and the hub returns `404 POINT_NOT_FOUND { point_id }` for an archived one (`apps/hub/src/kds/commands/ready.ts:32–36`). A line routed to TA can therefore lose its normal Ready/Handover path, and a return can inherit the same inaccessible point after archive.

**Fix / owner question** — How should staff finish outstanding and returned lines at an archived routed point? Default: let the existing Pass assignment display and drain those lines at their stored point, including a return, with the existing station actions, Ready, Undo and Handover. Keep archived points out of new routing and keep archived-point alert restrictions. Specify who can drain if the screen is removed. Add an archive-and-return fixture.

### R3-M-9 — The amber clock starts for a partial bag

**Where** — §3.4 l. 248, §3.5 ll. 267–270, §4.2 l. 368, §4.3 l. 383 and §10 test 107 l. 775.

**Evidence** — On a two-point order, B’s local Ready can turn B’s card amber while A is still cooking because the Pass uses local `ready.at`. The kiosk uses the maximum historical per-point Ready time plus current ready n = m (02b §6.16 l. 753). If A later finishes cooking without pressing Ready, the kiosk can immediately turn amber from B’s old time even though the counter never rang. Neither clock is tied to the complete-bag counter alert required by R8.

**Fix** — Expose a distinct order-level complete-bag time for R8 from the same transition that starts the counter alert, with one batched read or a projected value. Clear or restart it when completeness changes and preserve the agreed carry-over behavior. Keep the historical per-line/point ready times for the board and other existing readers. Test B first, A done without Ready, then A Ready and amber at exactly 1× from the complete-bag transition on both surfaces.

### R3-M-10 — Tap and retry responses have incompatible handling

**Where** — §3.4 l. 249, §4.3 l. 387, §10 tests 120 and 122 ll. 788, 790.

**Evidence** — “When the tap’s read fails” means disabled/offline, but the same paragraph demands a scope toast for `403 PERMISSION_DENIED { reason: 'outside_scope', order_ids }` from `apps/hub/src/orders/queries/order-view.ts:45–52`. Also, a live `409 ITEM_WRONG_STAGE` can be `{ order_item_id, stage: 'added' }` after Undo as well as `removed`/ `voided` (`apps/hub/src/orders/commands/mark-served.ts:158–163`). A resend that merely omits dead IDs can deliver an unmade line after its fire or create an empty list, which the payload forbids (ll. 103–107).

**Fix** — Apply offline handling only to disconnection/transport failure, show scope errors explicitly, and clear a cancelled/vanished card on the definitive read. Restrict automatic recovery to the `removed`/ `voided` details. Reread, reapply readiness and Due checks, and retry once with a fresh command ID only for the remaining eligible originally selected IDs. If none remain, finish without a send. Test a scope refusal, an Undo to added/cooking, an empty remainder and a successful removal retry.
