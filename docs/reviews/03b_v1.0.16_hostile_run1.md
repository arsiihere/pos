## BLOCKER

### B-1 — Kiosks get a lock-only alert with no token, and the placer on a kiosk loses his card
**Where:** §3.5 step 4 (l. 171: "a kiosk where the placer is signed in shows one card"), §6.21 note (l. 492: "The kiosk shows the same card and lock labels"), changelog (l. 17 (2)), §4.5 D-7 (l. 329: "as a device recipient"), tests 21, 99 (l. 568, 638).
**Problem:** D-7 makes every kiosk a **device recipient**. 01d's one card rule (§6 batch 3, AD-162 / AD-163, ruled) gives a device target `lock` only, "whatever its session kind — … a signed-in kiosk's cashier socket" (01d l. 1705). AD-75 adds: "a kiosk cashier socket that is also the person's own staff socket gets lock only" (l. 1706). AD-R-d-3 decides "device target" per step, and from v1.0.16 the kiosk is a target from **step 0**. The code does exactly this: `planStep` claims the device-target sockets first and skips them for person rows (`ws-frames.ts:476–535`, `if (deviceTarget.has(socket)) continue`), and `cardRule` returns false for a device target (`ws-frames.ts:444`). Three things follow:
1. **No token on the kiosk.** The lock text is `alert.ready_to_serve.lock` = "Ready to serve · {table} · {point}" (`apps/client/src/i18n/en.ts:2645`). For takeaway `display.table_code` is `null` (`ready.ts:112`, `:193`), so the kiosk shows "Ready to serve · · Pass" and nobody at the counter can tell which bag. The token ("#12") lives only in `details.identifier`, which is card-only (01d D-1).
2. **Regression for the placer.** A takeaway is placed at the kiosk, so the placer is normally signed in on it. Today (v1.0.15) the placer is a person recipient and gets the **card** there: token plus the `details.lines` list (v1.0.10). From v1.0.16 that same socket is a device-target socket and gets **lock**. The placer's inbox and catch-up go lock as well, since they "decide it over all steps".
3. The spec's statement "shows one card" is false, and test 99 would not catch it: it checks `AttemptSent.recipients`, not the frame.
**Fix:** pick one of these and write it into D-7 and §6.21. (a) The kiosk alert carries a **lock-safe identifier**: the takeaway token is not contact (R3 allows tokens on the TV board), so add `display.table_code = "#12"` for takeaway (or a new lock-safe param `identifier_code` with a `.lock` label variant). Parking's car number is a privacy call for the owner, so keep "PARKING" until he rules. (b) D-7 resolves `cashier_kiosks` to the **signed-in staff of each kiosk as person rows** plus the device row only for a signed-out kiosk. This keeps the card, but every cashier gets inbox rows (check against BF-3). (c) An 01d card-rule exception per kind (`device_card: true`, details are not secret for `ready_to_serve`), which is a ruled-rule change and needs the owner. In every option, keep the placer's own card when he is on a kiosk. Add tests: placer signed in on kiosk K → K's socket gets the card (or the agreed form) with the token; another kiosk shows the token in its lock text.

## MAJOR

### M-1 — `open-orders` drops every paid takeaway, so `readyAtOf` cannot drive the kiosk tile or "Pack next"
**Where:** §4.2 `readyAtOf` (l. 264, "read by 02b v1.0.25 `open-orders`"), §4.3 To 02b (l. 278, "one call per page"), §3.4 (l. 159, Pass joins `open-orders`), test 104 (l. 643, "an order missing from `open-orders` sorts by `placed_at`").
**Problem:** `open-orders` lists `orders_open` = `billed_at IS NULL AND cancelled_at IS NULL AND day_closed_at IS NULL` (`open-orders.ts:51–58`). `billed_at` is set by `OrdersBilled`, which 05 writes when the bill **closes**, i.e. when it is paid (05 B2; B16 "takeaway / parking close any time after the first Send"). A walk-in "send & pay" takeaway (plan C3-1, the common case) is therefore gone from `open-orders` while it cooks and while it waits to be collected. Calling `readyAtOf(db, <the page's order ids>)` never asks about it, so R8's "ready tile turns amber at 1×" fails for every prepaid bag. The hand-off names this as **G-1** ("paid pay-first orders vanish while cooking"), but the draft neither depends on G-1 nor states it. Test 104 turns the gap into expected behaviour: every paid order sorts by `placed_at`.
**Fix:** state the hard dependency in "Depends on" and §4.3. 02b v1.0.25 `open-orders` must keep a takeaway / parking order until it is handed over (G-1), not until it is billed. Or `readyAtOf` must be called from the kiosk catch-up / token query that does list paid orders. Say which. Change test 104 to use a paid order that is still listed. Until 02b v1.0.25 is drafted, list this as an open dependency that blocks approval.

### M-2 — "Kiosk" is chosen by hardware; 05a says screens decide
**Where:** §6.17 (l. 443, `SocketCtx.deviceType === 'cashier_kiosk'`), §4.5 D-7 (l. 329, "every unrevoked `cashier_kiosk` device"), tests 97, 99 (l. 636, 638).
**Problem:** 05a v1.0.6 §2 (l. 54) makes `device_type` "hardware only". C-1 (l. 279) says "what is shown comes from the profile …, never from `device_type`". l. 177 lists the **three** things hardware still decides: contact, drawer, bill audiences. The draft adds a fourth without a 05a row. In practice: (1) a takeaway counter run on a **tablet** with the `takeaway` screen (the hand-off's `HomeTablet`, `QueueTablet` frames; 05a l. 169 offers `cashier` on a tablet) gets neither the Pass frames nor the alert, so R8's "reach the kiosks" misses that counter; (2) a `cashier_kiosk` whose profile is `dine_in` + `cashier` only (a dine-in cashier desk) rings for every bag.
**Fix:** target "devices whose profile `screens` include `takeaway` (or `parking`, per OQ-7)". `deviceProfile(id).screens` is the in-memory map (`apps/hub/src/auth/device-profile.ts:13, :56`), so the cost stays 0 statements in the audience and in D-7 (filter read (5) by the map). Or add the rule to 05a's hardware list through an 05a row and get the owner's yes. Test both cases.

### M-3 — A Pass `Handover` to the cashier ends "not collected" while the bag is still on the counter
**Where:** §3.5 Handover step 7 (closes the Ready `done`), §4.2 `readyAtOf` (l. 264, "a Ready closed `done` … no longer counts"), §3.4 amber rule (l. 159), test 102 (l. 641).
**Problem:** R8 is about the **customer** not collecting. For takeaway the Pass can `Handover` the bag to a staff receiver (scope `placed_by = receiver`, step 2), usually the cashier. Step 7 then closes the Ready `done`, so the 1× / 2× steps stop, `readyAtOf` returns nothing, and the kiosk tile and Pass card lose amber. The bag is now sitting at the counter, and the only thing left is a one-step `served_card` with no escalation (`kinds.ts:58–73`). "Not collected" is only tracked if the packer never uses Handover.
**Fix:** define "collected" for takeaway / parking as the **customer** hand-over (`ItemServed`, 02b `MarkServed` from the kiosk), not the Pass→staff `Handover`. Either (a) for `to_counter` orders keep the Ready open until its lines are settled (Handover step 7 does not close it), or (b) have `readyAtOf` also return `handed_at` for hand-overs with `open_lines > 0`. Owner question if (a) changes the Pass flow. Add a test.

### M-4 — R2 is misapplied to the Pass's staff-to-staff Handover
**Where:** §3.4 (l. 159: "a 'Due' chip and the greyed Hand over on a Due order (R2 …)"), test 104.
**Problem:** R2 greys the hand-over **to the customer** on an unpaid order (kiosk token view, plan C2-2; G-7 is about "the call that would serve the last live lines"). The Pass's `Handover` always names a **staff** receiver (§3.5 step 2). Greying it on Due stops the packer from passing an unpaid bag to the cashier, who is the person who collects the money. That inverts the flow.
**Fix:** on the Pass, show the Due chip as information only and keep Hand over enabled; the greying belongs to the kiosk's customer hand-over (02b §8). Or ask the owner explicitly.

### M-5 — D-7 is under-specified, and OQ-6 changes the kind's shape, so it must be decided before approval
**Where:** §4.5 D-7 (l. 329), §6.21 (l. 456–467), §11 task 0h (l. 700), OQ-6 (l. 755).
**Problem:** (1) "`when_value` names a **boolean** key … (startup error otherwise, like `from_value`)". But `from_value`'s check requires a **required** string (`alerts/kinds.ts:148–153`), while `to_counter` is `z.boolean().optional()` (l. 467). The rule for an optional boolean has to be written, or the startup check rejects 03b's own kind. (2) `AlertStepTargetSchema` is a `z.union` of fixed shapes (`packages/events/src/alerts.ts:44–49`). The new member `{ kind: 'cashier_kiosks', when_value }` and the `stepTargets` branch for it (`targets.ts:333–345`: an object without `from_value` passes straight to `resolveTarget`, whose `switch` has no case and returns `undefined`) belong in D-7's text. (3) Nothing covers what a kiosk device row means for `alerts_open` (alert-mode reconnect, 01d l. 785), the `alerts` catch-up part, receipts with `staff_id = ''`, or "Moved to" (`projections/alerts.ts:290` takes the first **person** of the new step). (4) No 01d draft exists (the latest file is v1.3.6), and OQ-6 (b) would replace the whole mechanism with a second kind with its own labels and link. The 03b text cannot be approved while its routing rule is still a choice.
**Fix:** get the owner's answer on OQ-6 first. Then write D-7 as full 01d text (schema member, `stepTargets` / `resolveTarget` branch, optional-boolean validation, catch-up and `alerts_open` rows for kiosks), together with B-1's card decision. Review the 01d bump together with this one.

### M-6 — Orders with two points: two alerts per order on every kiosk, and tile and re-alert disagree
**Where:** §4.2 `readyAtOf` (l. 264, "the **largest** `ready_at` over its points"), §3.5 step 4 (l. 171), test 102 (l. 641).
**Problem:** A takeaway with food at point A and drinks at point B gets one Ready, so one `ready_to_serve` alert, per point (dedupe key `order:point:-`). Every kiosk rings twice, and each alert re-alerts at **its own** 1×. `readyAtOf` returns only the later `ready_at`, so the kiosk rings "again" for A at t_A + window while the tile is still white (amber waits for t_B + window). R8 ties the two together ("1× → alert the counter again … amber at 1×"). If B is not ready yet, `readyAtOf` returns t_A and the tile goes amber for a bag that is not complete.
**Fix:** decide per **order** for `to_counter`. Either (a) the counter alert is raised only when every point of the order has an open Ready (or the last one), or (b) amber and the counter re-alert both run from the same per-order time and the same rule (first or last). Write the rule and test it with two points.

### M-7 — Tests miss the cases that would show B-1, and two existing assertions are wrong
**Where:** §10 tests 97–104 (l. 636–643), test 99 statement assertion (l. 638), test 100 (l. 639).
**Problem:** Missing: (1) the placer signed in on a kiosk: which frame each socket gets, card or lock, and its text (B-1); (2) a kiosk revoked, or a new kiosk paired, between step 0 and step 1 (read (5) is re-read per tick); (3) Undo after an extending press re-raises the rest (`ready.ts:347`), so its step 1 and `readyAtOf` move to the Undo; (4) a kiosk that is **bound to the point**: `pointResolver` returns every non-kds device of the point (`kds/device-roles.ts:84`), so at 2× such a kiosk **is** a recipient and test 100's "no kiosk entry" fails for that setup; (5) kiosk reconnect: `alerts_open` / catch-up carry the open kiosk rows; (6) Handover step 5's `ReadyToServe { alert_id: null }` reaching kiosks and the tile ignoring it. Wrong: test 99 asserts "statements unchanged (§6.6, 4 …)" for a **takeaway**, but the takeaway path is 3 (`ready.ts:245–247`: no `currentTableOf`). §6.6 says a flat 4, while Handover's row already splits 5 / 4.
**Fix:** add (1)–(6). Test 99: "3 for takeaway / parking + 01d's fixed reads". Fix §6.6 to "4 dine-in, 3 otherwise". Test 100: kiosks not bound to the point, plus one case with a point-bound kiosk.
