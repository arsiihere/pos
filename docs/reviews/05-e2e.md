## Setup

- **Client:** `pnpm --filter @pos/client build`. The hub serves `/staff/`.
- **Hub:** a throwaway boot script outside the repo (`/dev/shm`, not committed). It uses the same helpers as `apps/client/e2e/global-setup.ts` and the 05 hub tests:
  - `createTestHub`: SQLite under `TMPDIR=/dev/shm`, the hub's real writer, folds and commands, and `buildHubServer` with the `none` fiscal adapter registered at boot (HEAD fix).
  - `billingDirectory()` (Owner / Manager / Cashier / Order taker over the cloud `DEFAULT_ROLES`, fixture PINs).
  - `voidsMenu()` with Chicken Karahi and Naan on `tc-food`.
  - The billing doc from `close-split.int.test.ts`: PK built-in, Rs 1 nearest rounding, 16 % cash / 5 % digital. Cash, Card and Voucher modes; no buyer-ID threshold; adapter `none`.
  - `openDay`, then a cashier kiosk and a manager tablet paired.
  - `startPrintWorker` and `startTickLoop`.
  - The clock was fixed; I advanced it 1 s per second.
- **Printer stub:** the hub's `fakeLanPrinter()` (a real TCP socket on loopback), saved as `PrinterSaved` with `BillRouteSet` per device. This is the same approach as `03b-fixture.ts`. Every document job was acked.
- **Postgres:** not used. These flows are hub-only. 5433 was not touched.
- **Browser:** Python Playwright (webapp-testing skill) on `/usr/bin/google-chrome`, headless. Devices were paired through the `pos-device` IndexedDB store, as in `smoke.spec.ts`. Viewports: kiosk 1920×1080, tablet 1280×800.
- **Actions with no UI** were sent as hub commands with `fetch` from the signed-in page, using the same device token and session: `SetSplits`, the `ReopenBill` raise, `RemovePayment`. Each one is marked **[API]** below.
- **Day-close clock:** `CloseBusinessDay` answers `opened_recently` until the day has been open for `day_min_gap_hours` (4). Before flow 4, I advanced the hub clock 4.5 h through the Node inspector. This is an environment limit, not a bug.
- All servers are stopped, and the temporary hub directories were removed.

### New findings (not fixed)

**R-1 — Medium, client: after a reopen, the re-close tells the cashier to hand out change that was already given.**
- The close screen shows `CloseSplit`'s `change_minor` as "Give change" / "Change due" (`BillScreen.tsx:497–498`). §6.12 step 4 defines it as Σ the split's cash payments' `change_minor` ("each already on its own shift"). This includes payments whose change was given at the first close, before the reopen.
- Repro (this run): T4 split 2 was paid Cash 320 given 500 (change 180, given at the first close). Reopen. Add a Naan. Pay Cash 34 given 50 (change 16). Close split 2. The screen says **"Change due Rs 196.00"**, but only Rs 16.00 is owed now. Split 1 (no new change) says **"Give change Rs 38.00"**.
- Risk: the cashier gives Rs 180 too much. The shift, the Z and the invoice are right (change given 234 = 38 + 180 + 16).
- Spec: §6.12 Result, §8 Bill screen ("tendered amount entry with change due", M-6; the change for a payment comes from `AddPayment`'s `change_due_minor`, §6.9). The spec does not say what the close screen shows, so the owner should rule which change to show (for example, only change not yet shown at Add payment, or none at the close).

**R-2 — Low, client: a reprinted or moved receipt row stays "Printing on …" after the printer has acked it.**
- After Reprint receipt, `onPrinted` reloads the bill once (`BillScreen.tsx:992`), while the job is still unacked. Nothing reloads it again. The row stays "Printing on Counter…" (checked for 12 s; the job was acked within 1 s). It shows "Printed" only after a reload. The same thing happens after Print to → "Moved to Counter".
- Spec §8 Print status ("each bill document shows waiting / printed / failed").

**R-3 — Low, client / config: the day-close screen says "the Z prints by itself" even when nothing prints.**
- With no `report` or `default` route, the Z fold skips the print (§3.16: `report` route → `default`). That is correct per the spec. But the screen still says "the Z prints by itself" (`billing.dayclose.done_sub`) and shows no print status. The manager is not told that no Z was printed.
- Spec §8 Day close ("Z shown and printed"), §3.16. Production setup should give each branch a `default` or `report` route, or the screen should show the print state.

**R-4 — Low, client layout (E-6 leftover): Add payment starts under the Close bar.**
- At the 1920×1080 kiosk, with the cash pad open on a split that has payment rows, Add payment first sits at y≈1,008–1,080, under `.b5-close` (y≈938–1,080). Scroll-into-view (keyboard focus) also stops there, because the pane has no bottom scroll padding. A touch user must scroll the pane to its end to reach the button.
- The fix for E-6 works, since the button can be reached. The pane still needs scroll padding equal to the bar's height.
