### Default grant of `reverse-inventory-entry` (asked check)

- The repo has **no store-keeper default role**. `DEFAULT_KEYS = ['owner', 'manager', 'cashier', 'order_taker', 'waiter', 'cook']` (`permissions.ts`), and `DEFAULT_ROLES` (`default-roles.ts`) gives Owner every permission, Manager everything except `MANAGER_EXCLUDED`, and Cashier / Order taker / Waiter / Cook fixed lists that contain no 08d key.
- So the spec's "defaults Owner + Manager (seed already grants them; backfill for running tenants)" is **correct against the code**. Adding the five keys to `PERMISSIONS` puts them on Owner and Manager automatically, and the 0020 backfill (once n-5 is fixed) reaches the pilot tenant.
- Consequence for the owner's rule ("jo banda entry kare wo khud theek kar sake"): out of the box only Owner and Manager can record anything (`receive-stock`, `record-waste` are on no other default role), and both already hold `close-daily-sheet`. The own-entry branch of S19 is therefore **dead by default**. It works only once the owner builds the custom "Store keeper" role of OQ-4 **and ticks `reverse-inventory-entry` there by hand**. A role given `receive-stock` but not that key silently loses the owner's rule: the Undo button is hidden and the command answers `403`. → n-1.

## Part 2 — New findings

### MAJOR

#### N-1 — The replacement lands after the count in the fold and in the moves-after-count rule, so test 14 cannot pass
**Where:** S19, S7, §5.2 fold state, §6.5, S14 "moves after count", tests 14, 2b.
**Problem:** The owner's case: 18 500 kg typed at 07:00 on day D, counted 18.5 kg at 22:00 (seq `c`), the typo noticed on D+1 and reversed with `replacement` 18.5 kg. The replacement event gets `business_day_id` = D but a **new `seq` r > c**. Three things follow:
1. **Fold:** `on_hand` adds "anchor-day moves with `seq > anchor.seq`", so the replacement's 18 500 g is added **on top of** the count that already holds it. `on_hand` is too high by 18 500 g until the next count.
2. **MWA:** if the replacement is priced, it weighs against that inflated, later `on_hand`, not the `on_hand` at 07:00. The `avg` differs from "a history without the typo". Test 14 and test 2b both claim it is equal.
3. **Close:** S14 lists any move of D "after its count (by `seq`)". The fixed typo therefore forces a recount, or `confirm_moves_after_count` with reason `moves_after_count`, on day D. This is the same "one typo, two flags" that M-2 was meant to remove.

**Fix:** Give every move an **ordering position** `order_seq`: the event's own `seq`, or for a replacement the `order_seq` of the event it replaces (carried as `replaces_event_id`, already in §5.3). Store it in `inventory_moves`. The fold, the recompute reads (`ORDER BY order_seq, seq`) and the moves-after-count test all use `order_seq`. A replacement is always applied by recompute (`foldItemCost`), never as a tail `stepItemCost`. "Affected items" = items of the reversed lines **∪** items of the replacement lines. Tests 14 / 2b: priced replacement on D after D's count → `avg`, `on_hand`, `max_seen` equal the history without the typo, and day D's close shows no "after count" row.

#### N-2 — The frozen day set is computed in a projection from the live snapshot, so a rebuild gives another set
**Where:** S2 ("frozen at the day's first `CountRecorded`"), §5.2 `inventory_day_sets`, §6.4 apply ("day set frozen on the day's first count, 1 `INSERT OR IGNORE`"), §5.3 `CountRecorded` (no set field), test 22.
**Problem:** The set (A-items + ticked cooked items whose explosion uses an A-item) comes from the snapshot. `CountRecorded` does not carry it, so the projection must read `branchConfig()` during apply. On a group rebuild (test 22: "reproduces the six tables exactly, including … day sets"), every past day gets **today's** set. An open day then gets a different required set after a rebuild, and `INVENTORY_COUNT_MISSING` changes. Projections must be a function of events.
**Fix:** The command computes the set when the day has none yet (it already reads inside the single writer) and writes it into the **first** `CountRecorded` of the day: `required_set?: { a_item_ids, cooked_item_ids }`, present only on that one. The projection stores it with `INSERT OR IGNORE`. The fixture and test 33 cover the field; test 22 rebuilds after a tick change and asserts the old set.

#### N-3 — Whole-key `InventorySnapshotSchema.safeParse` contradicts 08b v0.3's element-wise parse; one bad row takes the screen down
**Where:** S2, §3.3 row 1, §9 `INVENTORY_NOT_CONFIGURED`, test 9; against 08b v0.3 N-4 / B15 (c) / §4.3 row "08d".
**Problem:** 08b v0.3 decided that a builder output failing the schema is **sent as built** (logged `inventory_key_invalid`), and that `buildCostInputs` parses element by element: "one bad row never voids every cost". 08d v0.3 parses the **whole key** and answers `409 INVENTORY_NOT_CONFIGURED` on any failure. One malformed price or yield row (a builder bug that 08b chose to ship anyway) then blocks every receipt, count and close at the branch, while 08c keeps costing the same snapshot.
**Fix:** "Not configured" = the key is absent, or `buildCostInputs` cannot read its top level (not an object / no `items` array). Otherwise 08d uses `CostInputs` as built: an item dropped by the element parse is `404 STOCK_ITEM_NOT_FOUND` for that line only, and the day view shows `dropped > 0` as "Some inventory settings could not be read". R-b (2) then asks only for `buildCostInputs` and `CostInputs.dropped`. Test 9: one malformed price row → other items still receive.

#### N-4 — 08b v0.3's text does not carry 08d's v0.3 contract (asked cross-check)

R-b says 08d cannot be approved until 08b's approved text carries the row, so the gate is not met. The meaning is close (08b's row also says "08d decides which prepared items it counts"), but the text is not the same.
- **`theoreticalUsage` contract: ✗.** 08b v0.3 §4.3 "08c" defines it as "Σ `explodeUsage` over the business day's sale and comp lines … voided lines, coverage by revenue and day attribution are 08c's rules". It has **no `count_seq_by_item` input**, **no `sold_after_count` output**, no per-item `status`, and no `revenue_minor`. Row "08c / 08d" returns coverage only. Both parts are requirements on 08c, and today they describe two different call shapes. Both headers also say "cross-slice contract (same text in 08d)".

**Fix:** In 08b (its next text, v0.3.1, or at the fold into the module file), make the "08c" row point to 08d R-c for the signature: "`theoreticalUsage(db, { business_day_id, count_seq_by_item }) → { items: Map<id, { sold, comp, void_waste, staff_meal, sold_after_count, status }>, coverage_bp, revenue_minor }` as 08d §4.1 R-c". Also copy 08d's R-b (3) sentence word for word, or change 08d's R-b (3) to 08b's wording. Either way, one text in both files. 08d gets no spec edit here: this is a finding for the author and for 08b.
