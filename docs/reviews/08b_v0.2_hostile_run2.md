### M-2 dominance vs 08a I7 (`prices.ts:32`)

The candidates are I7's (current unit, `created_at ≤ now < valid_until_at`). Within one scope, a row is dominated when a newer row's validity ≥ its own (null = ∞). The newer row is then in effect whenever the older one is, and the newer one wins, so dropping the older one never changes I7's answer. Because dominance works inside a scope, the "branch set if non-empty" choice is kept.

| Case | Rows | I7 at hub time t | Dominance keeps | Same? |
|---|---|---|---|---|
| Manual only | M1 < M2 | M2 | M2 | ✓ |
| Market rate after manual | M (∞) < R (t₁) | R before t₁, M after | both | ✓ |
| Manual after market rate | R (t₁) < M | M (newer wins; kind does not rank) | M | ✓ |
| Two market rates, the newer expiring first | R1 (t₁) < R2 (t₂ < t₁) | R2 before t₂, R1 to t₁, then manual | M, R1, R2 | ✓ |
| Daily market rates | R(d) < R(d+1), each to its midnight | the latest unexpired | the latest only (bounded body ✓) | ✓ |
| Branch market rate over a tenant manual | B (t₁, branch scope) vs M (null scope) | B until t₁, then M (I7 falls back by itself) | B and M (different scopes) | ✓ |
| Expired, never-dominated branch rate | B expired at t₁, nothing newer | nothing in the branch set → every-branch set | B is kept (harmless; the hub skips it) | ✓ |
| `stock_unit` changed | old-unit rows | ignored | filtered before dominance | ✓ |
| Hub clock behind the cloud | newest row created after hub `now` | the cloud would use it | the hub must too | ✓ only with n-1's mechanism |

**Yes:** the answer is the same in every case, provided the builder really uses the time-free query (N-3) and the hub ignores `created_at` (n-1).
