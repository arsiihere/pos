### M-2 — "Handed over" is any `served_at`, so the estimate tick and a Pass `Handover` take a paid takeaway off the queue before the customer collects it
**Where:** §3.3 Open (lists) (l. 181: "served = `served_at` set (tap, estimate or zone)"); §3.7 Estimated Served (l. 224); §6.16 SQL second branch (l. 576–580: `l.served_at IS NULL`), `handed` (l. 592), `ready_at` (l. 591); §8 Hand-over undo (l. 722); tests 66, 68 (l. 831, 833). Code: `orders/served-estimate-tick.ts:1-11, 46-60`. 03b v1.0.16 §6.8 (`Handover` accepted for takeaway, "4 statements otherwise"), test 25, §4.2 `readyAtOf` (Ready closed `done` by a full `Handover` → absent).
**Problem:** R3 and R8 need "in the queue until the **customer** has it" and "not collected → amber, re-alert". 02b treats any `served_at` as handed: (a) the `served_estimate` tick (built, `served-estimate-tick.ts`) appends `ItemServed { source: 'estimated' }` for every line of a 03b `Handover` older than `served_estimate_ms` (a nullable branch setting the restaurant can turn on). (b) 03b lets the Pass `Handover` a takeaway to a receiver (03b test 25 covers every scope × takeaway / parking). At a counter where the Pass hands bags to the cashier, the Ready alert closes `done`, so `readyAtOf` returns absent and `ready_at` becomes `null` (no amber, no R8 re-alert). After `served_estimate_ms` the lines become served, the paid takeaway drops out of `open-orders` and the catch-up, and the kiosk's queue search no longer finds it, while the bag is still on the counter. Neither the estimate tick nor the Pass hand-off is a hand-over to the customer.
**Fix:** define "handed over" for a takeaway / parking line as `served_source = 'tap'` (or zone), never `'estimated'`, in §3.3, the second-branch `EXISTS`, `handed.n` and day close. Alternatively, state that the `served_estimate` tick skips takeaway / parking orders (in `handoversDue` or the tick's filter, with an 03b row). State what a 03b `Handover` of a takeaway means: either refuse it (takeaway goes Ready → counter `MarkServed`), or accept it and keep the order listed, with `ready_at` read from the latest Ready **including** closed `done` ones for takeaway (needs a 03b change to `readyAtOf`). Add tests: an estimate-served takeaway stays listed; a Pass `Handover` of a paid takeaway keeps it listed with a non-null `ready_at`.

### M-3 — "End of the business day" is a stale-prompt proxy: a stale day refuses every pickup, and earliest > latest is not handled
**Where:** §3.2 step 2b latest (l. 154); §9 row (l. 747); §8 Phone and pickup (l. 723: "latest = end of day"); test 60 (l. 825); TK-Q2 (l. 933). 01a v2.1 S33 (`day_stale_after_hours` 1…72, default 16, "Safety net for a forgotten close"); 01a v2.11 defines no day end.
**Problem:** R4 binds "latest pickup = end of the business day". 01a has no such concept, and 01a v2.11 (the 02b-TK bump that could have added one) does not add it. So 02b substitutes `opened_at + day_stale_after_hours`, which is the hour after which the hub *nags* that the day was **forgotten**, not when the restaurant closes. Consequences: (1) on a stale day (forgot to close last night, still open and still taking orders at 11:00, which is exactly what S33's stale prompt exists for), latest is in the past, so **every** pickup is `422 after_day_end` while plain orders are accepted. The client's picker gets a range with `earliest_ms > latest_ms` and nothing to choose. The spec neither handles nor tests this. (2) A kitchen that opens the day at 08:00 for stock counts and serves until 01:30 with the default 16 h refuses a 00:30 pickup phoned in at 22:00. (3) An owner who raises `day_stale_after_hours` to 72 to stop the prompt silently allows pickups three days ahead. The setting now carries two meanings, and the owner cannot tune one without changing the other.
**Fix:** take TK-Q2 to the owner as a blocker for the pickup part. The clean answer is a real 01a setting (for example `business_day_end_local_ms`, the local clock time the day ends, with the next occurrence after `opened_at` as latest), added to the 01a v2.11 draft with a §4.5 row. With any proxy, specify `latest < earliest` (stale day): either refuse with `reason: 'day_stale'` and have the client prompt "Close the day first", or fall back to `earliest + N h`. Add a stale-day test and a "day opened 08:00, pickup 00:30" test.

### M-4 — Changing `openOrderRows` breaks unlisted tests and changes the catch-up contract without a client rule
**Where:** §3.3 Open (lists) (l. 181); §6.16 (l. 568–583); §6.18 Catch-up part `orders` (l. 615); tests 66–68 (l. 831–833); §12.2 rows 16, 19. ### M-5 — R3's client search hands every kiosk user the contact that `customer-orders` and held drafts gate per person
**Where:** §6.18 catch-up contact rule (l. 615, "only for cashier kiosks and the placer's sockets"); §6.18b Permission / Scope (l. 624–625); §7 Privacy (l. 693); §8 Queue search (l. 716), Held drafts (l. 718); test 72 (l. 837). ### m-1 — `orders_open_takeaway_paid` is not selective; the statement count is fixed but the work grows with the day

### m-2 — `phone_key` edge cases that real cashiers will type
**Where:** §3.1 Phone key (l. 125–142); §6.18b Query (l. 623); TK-Q5 (l. 936); test 64 (l. 829).
**Problem:** (a) `0092 300 1234567` (the international `00` prefix) has 14 digits and is **refused** by the 10–13-digit rule at `SubmitOrder` and at `customer-orders`. (b) `+92 0300 1234567` (a very common mixed form) gives 13 digits `9203001234567` and falls to rule 4, so it never matches. (c) `300 1234567` (TK-Q5) does not match. (d) In a query string an unencoded `+` decodes to a space. That is harmless after stripping, but the spec should say the client sends `encodeURIComponent`. (e) Any later change to `phoneKey` (TK-Q5's answer) needs another refold, and the spec should say so.
**Fix:** extend the rules: strip a leading `00`; `920` + 10 → `92` + 10; optionally `3` + 9 → `92` + d (TK-Q5). Allow up to 14 digits when the input starts with `00`, or say explicitly that it is refused. Add these rows to test 64. Note that a `phoneKey` change is a migration with a checkpoint delete.

### m-3 — `customer-orders`: no audit trail, root chosen among matches only, `on_menu` misses option offers
**Where:** §6.18b Log (l. 633), Statement 1 (l. 628), `RepeatLine` (l. 631).
**Problem:** (1) A phone → name + order history oracle is logged as `info { staff_id }` only. After a privacy complaint nobody can tell which number was looked up or how often. `order-contact` at least logs `order_id`. (2) "Root `order_id` = the visit's earliest order" is computed over the **matching** orders only. When the root has no contact and an addition has one, the addition becomes the "root". (3) `on_menu` checks that items, deals, parts and options exist in `branchConfig()`. An option that exists but is no longer offered at this branch (`is_offered: false`) or no longer attached to the item's groups passes, and Repeat then fails at Send with `OPTION_CHOICE_INVALID`.
**Fix:** (1) log `{ staff_id, matched: orders_count > 0 }` and, if the owner wants auditability, a per-lookup audit row with a keyed HMAC of `phone_key` (no plain digits). Put it to the owner as TK-Q10. (2) Take the root as the visit's earliest order over all orders of the `bill_key` (statement 2 already reads them). (3) `on_menu: false` also when an option is not offered at the branch or not in the item's current groups.

### m-5 — `handed { n, m }` counts children and deal parts, and Hand over must send every one of them
**Where:** §6.16 `handed` (l. 592); §8 Unpaid hand-over (l. 715), Hand-over undo (l. 722); §3.7 (l. 222).
**Problem:** m counts every live non-deal line: option children with or without a station, and each deal part. A karahi with two linked sides and a deal of three parts reads "0 / 6" on a two-item order. More importantly, the order leaves the queue only when **every** such line is served. If the client's Hand over sends only the root line ids, as the summary rows suggest, a no-station option child stays unserved and the paid takeaway stays listed until day close.
**Fix:** state that Hand over sends every live unserved non-deal line id of the order (children and parts included) in one `MarkServed`, and test it. Consider computing `handed` over root lines (as `lines_summary` does) for display.

### m-8 — Addition pre-fill and preview drift at the 10-minute bound
**Where:** §3.1 Pickup time (l. 144: "the client pre-fills the root's pickup while it is still in the future"); §8 Phone and pickup (l. 723); test 62 (l. 827).
