## BLOCKER

### R2-B-1 — `when_none` skips the target presence filter, but the route presence check still drops the absent Owner's devices
**Where:** §3.5 note l. 674; §3.4.1 l. 611; §3.4.3 route 2 (b); To 05c "Presence" l. 1334; test 121 l. 2100. Code: `routes.ts` `bindingIsRoute` (`const present = isPresent(reads, binding.staff_id); if (permanent) return { route: connected && present, … }`).
**Problem:** OR-4 is there for the case where every manager is ticked absent. In that case the Owner usually is too, or is off site. `when_none` makes him a recipient "without the presence filter", but §3.4.3 route 2 (b) still refuses a binding route for a person marked absent. That covers his permanent-bound listed phone and his tablet. Route 1 (screen) exists only while he is signed in, and then he already counts as present, so `when_none` changes nothing. The result for an absent Owner is an `alert_inbox` row with "no route", which he sees at his next sign-in. That is the "money unseen until later" outcome the owner rejected. Test 121 ("→ the Owner … even when the Owner is ticked absent") checks recipients only, so it passes while nothing rings.
**Fix:** in §3.4.3 route 2, add "(b) does not apply to a person added by a `when_none` entry, for that alert" (memory, 0 statements; the recipient is already tagged by entry while the step is planned). Mark it "Changed by v1.3.7 owner review (OR-4)". Test 121 adds: the Owner is ticked absent, his listed phone is connected with a permanent binding → the phone gets the `alert` frame, and the receipt shows it delivered.

### R2-B-2 — `hand_over_unpaid` declares `skip_requester: true`, which is a startup error on a request kind
**Where:** To 02b l. 1327 ("`skip_requester: true` … Every part exists in 01d today; nothing in 01d changes"); changes row OR-7 l. 66; test 122 l. 2101 ("registers at boot with no startup error"); §3.5 startup errors ("`skip_requester: true` on a request kind (02a v1.0, D-3)") and the kind comment ("not allowed on request kinds"). Code: `kinds.ts:160` `fail('skip_requester: true on a request kind …')`. Source: 02b v1.0.25 §6.12a l. 637.
**Problem:** `defineAlertKind` throws at module load, so the hub does not boot. This is the same class of break as run 1 B-1.
**Fix:** drop `skip_requester` from the kind, both in 01d To 02b and in 02b §6.12a. `answerers` already excludes the requester (§3.3 rule 5). The test 122 text is then right.

## MAJOR

### R2-M-1 — `hand_over_unpaid` never expires and has no closer
**Where:** To 02b l. 1327 (`closes_on: 'owner'`, `expires_at_day_close: true`); test 122 ("`BusinessDayClosed` expires it"); §3.3 "No expiry for requests" l. 579; §3.5 day close l. 797 ("Requests stay open"). Code: `projections/alerts.ts:345-351` (`request_json IS NULL`); `billing/kinds/index.ts:47` ("no effect on a request kind"). 02b v1.0.25 test 88 ("day close → the open request expires").
**Problem:** day close expires only non-request alerts. 02b never closes the request: not on payment (due → 0), not on hand-over, cancel or day close. 05's day-close appender closes only 05's requests and 02b's `comp` (l. 581). So a pending `hand_over_unpaid` stays in `requests-to-answer` indefinitely, and a manager can still approve it days later. Tests 122 and 02b 88 assert something the code cannot do.
**Fix:** To 02b must name the closer. Recommended: 02b closes it `obsolete` through `alerts.close` in the transaction that pays the order in full, hands it over or cancels it, and at day close through a 02b day-close appender or 05's (with a 05 row). Reword test 122 as "day close → closed `obsolete` note `day_closed` by 02b", and fix 02b test 88 to match. "Nothing in 01d changes" stays true.

### R2-M-2 — By default the Owner is already a "manager", so OR-4 does not describe the real behaviour and test 121 is wrong
**Where:** OR-4 row l. 65 ("also goes to the Owner role"); To 05c l. 1330, 1334; test 121. Code: `default-roles.ts:38` (Owner = `PERMISSIONS.map(allowed)`), `targets.ts:461` (`managers` = branch-scope `force-release-table-lock`).
**Problem:** the Owner holds `force-release-table-lock` at branch scope, so `managers` includes him whenever he is present. In practice `when_none` fires only when every holder, the Owner included, is ticked absent, and then it reaches the Owner anyway. Test 121's first case ("two managers, one ticked absent → the present manager only, not the Owner") fails on default roles, because the unticked Owner is present and is a manager. The second case passes for the wrong reason unless the Owner is also ticked absent.
**Fix:** state the actual effect in OR-4 and To 05c: "when every branch-scope holder of `force-release-table-lock` (the Owner included by default) is absent, the holders of `manage-payment-providers` get it regardless of presence". Give test 121 explicit fixtures: one case with the Owner ticked absent, one with a custom role without `force-release-table-lock`.

### R2-M-3 — `manage-payment-providers` does not exist in 01b yet, and as written Managers would hold it
**Where:** OR-4 row l. 65 ("held by the Owner role only by default, 05c R-1 / 01b"); §1 Version row l. 205 and header l. 1/5 (co-approval list). 01b v1.12 l. 23 ("05c v0.2 R-1 … Not applied: carried when 05c is approved"). Code: `default-roles.ts:31` `MANAGER_EXCLUDED = ['manage-roles', 'skip-blind-count', 'manage-fiscal-settings']`.
**Problem:** (1) The step target's `permission` is typed by `@pos/domain` `Permission`, so 05c's kind does not compile until 01b carries R-1. (2) If R-1 adds the key to `PERMISSIONS` but not to `MANAGER_EXCLUDED`, every Manager holds it. The `when_none` entry then sends the alert to **absent** Managers with no presence filter, which is the reverse of "Owner only". (3) The co-approval list leaves out 02b v1.0.25 (OR-7), 01b v1.12 (B-5 `hand-over-unpaid`) and the 01b bump that carries R-1.
**Fix:** add 02b v1.0.25, 01b v1.12 and "the 01b bump carrying 05c R-1, with `manage-payment-providers` in `MANAGER_EXCLUDED`" to "approvable only together with" (l. 5, l. 205). Cite that row in OR-4.

### R2-M-4 — OWNER: "present" means "not ticked absent", so a branch that never ticks the list never triggers `when_none`
**Where:** §3.4.1 safety rule l. 611 ("if no one has been ticked today, everyone counts as present"); §3.5 l. 674 ("no person (after the §3.4.1 presence filter)"); To 05c l. 1334.
**Problem:** on a day with no ticks, every manager counts as present, including off-duty ones nobody can reach. They get inbox rows, and `when_none` stays silent. A manager who is ticked present but not signed in, with no route, also blocks it. The owner's words were "no manager present … never unseen until the next day". The spec reads "present" as the presence list, not as "reachable now". That reading is defensible (the rule is stable and has no route timing), but the owner should confirm it.
**Fix:** record it as a Q-37f sub-answer. Recommended default: keep the presence-list meaning as written, add a sentence saying so, and add test 121 cases "nobody ticked → managers only, no Owner" and "managers present but with no route → no Owner". The alternative, "no person **with a route**", would need the routes before the step is planned, so it is not 0 statements and not minimal.

## MINOR

### R2-m-1 — The `when_none` entry's target and its ordering against the lead fallback are not constrained
**Where:** §3.5 l. 674 (any target; "the same permission read … 0 extra statements").
**Problem:** a `when_none` entry with a resolver target (`table_team`, `point`, `zone_order_taker`) needs a second resolver call after the batch. That breaks the "0 statements" claim and the one-call-per-kind rule (§3.4). A device target (`always_on`, `device`, `screen_devices`) adds no people, so the condition is meaningless for it. On a `lead_fallback: true` kind, nothing says whether "no person" is measured before or after the §3.4.3 lead fallback.
**Fix:** add startup errors for a `when_none` entry whose target is not `permission` (or `person`), and for `when_none` on a kind with `lead_fallback: true`. Say that "no person" is counted on the other entries' resolved people before §3.4.3 routing.

### R2-m-2 — One startup error can never fire
**Where:** l. 674 ("on an entry whose `set` is not `recipient`"); test 121 ("on an `answerer` set").
**Problem:** a non-request kind already cannot use `answerer` / `informed` (existing error), and `when_none` on a request kind is refused anyway. So the rule never triggers on its own, and test 121's case cannot be built in isolation. This is over-specification.
**Fix:** drop the rule and the test case, or note it as implied.

### R2-m-3 — The warn log line is per route, not per recipient
**Where:** To 05c l. 1334 ("only when nobody holds it either does the raise reach nobody (the warn log line)"); OR-4 row. Code: `ws-frames.ts:166` (`if (payload.routes.length === 0) … 'no_receiver'`).
**Problem:** the line is also written when the Owner is a recipient with no route, which is exactly the R2-B-1 case.
**Fix:** reword it to "a step with no route writes the warn line, as today", or keep it as is once R2-B-1 is fixed.

### R2-m-4 — The day-open re-raise can dedupe onto the alert that is just expiring
**Where:** To 05c l. 1330 ("05c raises it again after each `BusinessDayOpened` … as 05 raises `fiscal_outbox_stuck`"); §3.5 day close l. 797 (`expire_due` set, the tick closes it later). Code: `raise.ts:234` (dedupe `WHERE state = 'open'`).
**Problem:** if a day opens before the tick has written `AlertClosed { expired }` (≤ 500 ms, longer if a tick pass fails), the re-raise returns the dying alert, the tick then expires it, and 05c does not re-raise again that day. `fiscal_outbox_stuck` re-raises continuously, so the analogy does not hold for 05c's once-per-day re-raise.
**Fix:** make the dedupe read skip `expire_due = 1` rows (same statement, mark it changed), or state the ordering 05c relies on and test close-then-open inside one tick interval.
