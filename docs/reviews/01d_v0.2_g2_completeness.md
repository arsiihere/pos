## 0. Known item — the tick takes the write lock every 500 ms

**Proposed fix: CONFIRMED, with three conditions (fix as finding 1).**

What the code does today:
- Every `writer.run` is `BEGIN IMMEDIATE` (`apps/hub/src/engine-host/writer.ts:85`). Even an empty run still swaps the state (`:86`) and calls **every** registered `afterCommit` hook with `[]` (`:90–91`). At 500 ms, that is 2 empty transactions and 2 rounds of every hook per second, all day.
- The empty commit itself costs little: no WAL frames, so no fsync. The cost is the hook calls, the state swap, and noise in every future "count transactions" test.
- The spec contradicts itself here. §3.5 (race rule) says "an empty tick still takes the write lock briefly … it is the price of the rule". The §3.5 pseudo-code says "return without writing (the transaction ends empty)". §7 says "skip the transaction when nothing is due". Test 22 says "Tick with nothing due writes nothing (**no transaction**)". Test 22 cannot pass against the §3.5 rule.

Why the fix keeps the race rule:
- The hub has **one** synchronous better-sqlite3 connection, and `writer.run` has no `await` inside it. A command and the tick can never interleave inside a transaction. The only gap is between a read done outside the lock and the `writer.run` that follows it.
- With the fix, the outside read is only a hint. The authoritative select still runs inside `writer.run`, after `BEGIN IMMEDIATE`, so any alert answered or closed in between is seen as closed and gets no step. A hint that is wrong the other way, saying "nothing due" just before something becomes due, only delays the step to the next tick (≤ 500 ms). That is within the G1-16 budget.

Conditions:
1. **One read-only statement for the pre-check**, served by the indexes that already exist: `SELECT EXISTS (SELECT 1 FROM alerts WHERE state = 'open' AND next_due_at <= ?) OR EXISTS (SELECT 1 FROM alert_flags WHERE dirty = 1)` (`alerts_due` partial index; `alert_flags` has one row). Day-close expiry already sets `next_due_at = recorded_at`, so the pre-check sees it. A backlog left by `LIMIT 200` keeps the pre-check true.
2. **Registered ticks need their own cheap "has work" check.** As written, `registerTick({ name, intents(tx, state, now) })` (§4.2) can only be asked inside a transaction. Once 03a registers, every tick takes the lock again. Change the contract now to `registerTick({ name, due(db, state, now): boolean, intents(tx, state, now) })`. 03a's `getTickIntents` is pure over the in-memory state, so `due` can be pure as well. See also finding 4: each registered tick gets its own transaction.
3. **Rewrite test 34.** "Two connections, the tick's `writer.run` entered while the answer holds the lock" cannot happen in this hub (one connection, synchronous). Test what can happen instead: the pre-check returns true for alert A → `AnswerRequest` for A commits → the tick body runs → no `AttemptSent` / `EscalationStepped` for A. Then the same in the other order. Rewrite test 22 as: nothing due → `writer.run` is not called (a spy on the writer), and no `afterCommit` hook runs.

Then reword the §3.5 race-rule bullet ("selection inside `writer.run` is authoritative; a read-only pre-check outside it decides only whether to open the transaction") and drop "it is the price of the rule".

## 1. Findings

### MAJOR

**1. MAJOR — §3.5, §7, §10 test 22 / 34 — the tick contradicts itself and takes the lock when idle.**
*Problem:* see §0. *Fix:* §0 conditions 1–3.

**2. MAJOR — §4.5 C-F (missing rows) — the foundation's WebSocket contract changes silently.**
*Problem:* Alert mode (a socket with a device token and no session) and the new frames change text that the **foundation** owns and that 00 M12 did not override:

- foundation §5.4 diagram (the session on connect; "event push" is the only hub → device traffic).
- foundation §6.5 (hub → device lists `catch_up`, `event` and `error`; device → hub lists only `ack`; "Only committed events are pushed, in strictly ascending `seq`").

The foundation is frozen until R34. CLAUDE.md says "never silently diverge". C-00 H-2 cites "§6.5 (`@pos/events/src/ws.ts`)", but **00 §6.5 is `POST /v1/hubs/register`**. The WS message format is in foundation §6.5 and 00 §6.21.

*Fix:* Add F-5: foundation §6.3 `/ws` row → "device token + session, or device token only (alert mode, 00 M12)"; §5.4 note; §6.5 adds `alerts_open`, `alert`, `alert_closed` (outside the `seq` stream, no gap logic) and the device → hub `receipt`. Correct H-2's section to "00 §6.21 and `packages/events/src/ws.ts`".

**3. MAJOR — §4.5 C-00, §6 batch 3 (catch-up part `alerts`) — the 00 catch-up and socket-context contracts change silently.**
*Problem:* 00 §4.2 exposes `registerCatchUp { part, appliesTo(socketCtx), build(db, state) }`, as built in `apps/hub/src/ws/catch-up.ts:15–19` and `:40` (`part.build(db, state)`). `build` gets no socket. The `alerts` part needs "open alerts for this person and device", so it cannot be built on today's interface. The 00 §4.2 socket context `{ deviceId, deviceType, sessionId, kind, staffId, stationId, asOfSeq }` (`catch-up.ts:5–13`: `sessionId: string`, `kind: 'staff' | 'station'`) has no shape for a socket without a session. `deliver()` sends to every open socket that an audience allows (`server.ts:87–94`). Neither change is in C-00.

*Fix:* Add H-7: `build(db, state, socketCtx)` (additive third argument; existing parts ignore it). Alert-mode sockets are kept in a **separate list**, outside `deliver()`, audiences and catch-up, so the 00 socket context stays as it is. State that in H-1.

**4. MAJOR — §3.5 tick, §4.2 `registerTick`, §4.3 "To 03a" — one transaction ties 01d failures to the kitchen.**
*Problem:* The tick appends "registered ticks' intents (03a) — same transaction, D44". If anything in 01d's part throws (a resolver bug, a kind's step function, a constraint), 03a's `FireDispatched` / `TableLockReleased` intents roll back with it, and the kitchen stops firing every 500 ms. D44 requires all **fire-scheduler** intents of one tick in one transaction. It does not require 01d's alert steps in the same one. G1-16a asks for one clock (same loop, same `branchNow`), not one transaction.

*Fix:* Keep one loop and one `branchNow` value per tick. Give each registered tick (01d alerts, 03a fire scheduler) **its own** `writer.run`, opened only when its `due()` is true (§0 condition 2). Catch and log errors per registered tick so one failing part does not stop the others.

**5. MAJOR — §3.7, §5.2 `device_bindings` — the binding projection cannot tell which device a session ended on.**
*Problem:* "Derived from session events, no new event", but `SessionEnded` carries no `device_id` (`packages/events/src/events/staff/SessionEnded.v1.ts:4–21`; 00 §4.2). On `logout` the projection has to know which device's binding to end. `device_bindings (device_id, staff_id, since)` has no session column. A lookup in `staff_sessions` works live, but not when the projection is rebuilt after a cloud-only restore (00 M40 step 4b, where `staff_sessions` is empty and sessions end `hub_restored`).

*Fix:* Add `session_id` to `device_bindings`. `SessionStarted` (kind `staff`, `device_id` in its payload) writes `(device_id, staff_id, session_id)`. `SessionEnded` with an ending reason deletes `WHERE session_id = ?`. `taken_over` / `replaced` overwrite on the next `SessionStarted`. Add a rebuild case to test 27.

**6. MAJOR — §3.4.3, §3.8 `registerRoute.routesFor` — the route lookup is per person (N+1 contract for 01e).**
*Problem:* Target resolvers are batch-shaped "one SQL statement per call" (§3.4), but `routesFor(staffId)` is called per person, per alert, inside the tick transaction. 01e's pager route reads hub assignment state (G1-17a), so 200 due alerts × ~3 people turns into hundreds of statements. The §3.5 bound "≤ 2 + 4 + R" and test 35 do not count route reads. This interface is exposed to 01e, so fixing it later costs a 01d bump.

*Fix:* `routesFor(tx, staffIds: string[]) → Map<staff_id, Array<{ route_ref }>>`, one statement per registered route per tick. Add "+ T (registered routes)" to the bound, and a pager-like fake route to test 35.

**7. MAJOR — §5.1 retention — `alert_recipients` is never purged, and the purge breaks a foreign key.**
*Problem:* `alert_recipients.alert_id REFERENCES alerts(alert_id)` and `foreign_keys = ON` (`apps/hub/src/db/connection.ts:8`). Retention deletes closed `alerts` rows older than 7 days but never deletes `alert_recipients`. The `alerts` delete fails with a foreign-key error. Retention runs inside the sweeper's `setInterval`, which has no try/catch (`apps/hub/src/auth/session-sweeper.ts:58–61`), so the error is uncaught and can crash the hub process in every maintenance hour. `alert_recipients` also grows without bound.

*Fix:* Retention deletes, in this order: `alert_recipients`, `alert_inbox`, `alert_receipts`, `request_seen` (rows of alerts closed more than 7 days ago, or before the previous business day for the three receipt and inbox tables), then `alerts`. Batches of 500, one `writer.run` per batch (00 M66). Add a retention test with foreign keys on.

**8. MAJOR — §3.6, §8.3, §4.2 — "seen on one device stops the repeat on all of them" (G1-14a) is not delivered.**
*Problem:* G1-14a stops the 10 s urgent repeat once the person has seen the request **on any of their devices**. `RequestSeen` is "Pushed to: —" (§4.2), and `alert` frames are sent only once per step. A second tablet, or the background service of a session-less tablet, keeps repeating every 10 s until the next step frame (up to 75 s in the approval tier). §8.3 refers to `seen_by_me` on `alert` frames, but no frame is sent at the moment of seeing.

*Fix:* Add a frame `{ type: 'alert_seen', alert_id }`, sent after commit to the staff-session sockets and alert-mode sockets of that person (person and binding) whenever `RequestSeen` is written. Add it to H-2 and to batch 3, and add a test (two devices bound to Ali: seen on A → B gets `alert_seen` in the same publish).

**9. MAJOR — §3.9 (per-request `no_approver`), §3.3 rule 5, test 10 — underspecified.**
*Problem:* "Also open, per request, while an open request has no eligible answerer signed in". There is no `dedupe_key` (the only key given is `'no_approver:' + permission`), no subject, no text, no close rule (does it close when the request closes?), and the flag evaluation needs every **open request**, not only the due ones, which is a read missing from the fixed `batchReads` list. The only case that this alert covers and the permission-level alert does not is "the only branch-scope approver signed in is the requester". Even then the requester already sees "Waiting 2 min — ask in person".

*Fix (pilot lesson):* Drop the per-request variant to §12.4 and keep the permission-level alert. Test 10 then expects: request pending, step 0 written with no answerers, "ask in person" at `approval_branch_ms`. *Or*, if it is kept: `dedupe_key = 'no_approver:req:' + alert_id`, subject = the request's subject, closed `done` when the request closes or an eligible answerer signs in, plus one batched statement over open requests in `batchReads`.

**10. MAJOR — §8.4, C-00 H-5, §6, §12.2 — app update endpoints have no endpoint spec.**
*Problem:* `GET /app/android/latest`, `GET /app/android/<version_code>.apk` and the CLI `app-release promote <version_code>` are mentioned only in the client contract. There is no auth (device token? none on the LAN?), no response or error shapes, no "staged" state model (where "chosen tablet" and "marked good" are stored), no APK storage path or limit (≥ 2 versions), no test, and no checklist row. H-5 places them in 00 with no section.

*Fix:* Specify them as endpoints. The cheapest place is 01d §6 batch 4, marked "lands in 00 v1.6 via H-5". Cover: device-token auth; `latest` per device (the staged device gets the candidate, the others the promoted version); CLI `app-release add <apk>` / `promote` with the state in a small hub table or the config file; 404 / 409 cases; tests. Otherwise cut staging to "promote only" for the pilot and say so (G1-15c amended).
