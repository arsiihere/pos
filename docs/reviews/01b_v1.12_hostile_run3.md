## BLOCKER

### R3-B-1 — B-5 silently widens the persisted `AlertRaised` permission enum

**Location** — B-5 l. 32, §4.2 ll. 583–585 and §11 step 11 l. 1534.

**Problem and evidence** — Adding the key to `PERMISSIONS` changes the existing event schemas. `packages/events/src/events/alert/AlertRaised.v1.ts:28–29` builds both request permission enums from that list, and v2–v5 inherit those fields (v5 ll. 10–12). 02b §6.12a l. 687 feeds the new key to a `holders` right, which `apps/hub/src/alerts/raise.ts:176–179` stores in `request.base_permission`. The writer uses the latest registered schema version (ll. 421–422). The change as scoped would write the new value under v5 and mutate the historical validators, contrary to Foundation v1.18 §4.1 D46 l. 436.

**Fix** — Carry a prerequisite into 01d and the shared-contract lane. Freeze the existing request permission enums at their pre-B-5 values, add `AlertRaised` v6 with `hand-over-unpaid` in the permission enum and an identity v5→v6 upcaster, and register v6 before enabling the request. Add a v6 fixture and replay checks for prior versions and the new `holders` request. Update the request payload types used by the hub writer and readers.

### R3-M-2 — An older hub can discard the grant and keep that directory version after upgrade

**Location** — §4.2 l. 598, §5.1c ll. 937–947 and §10 test 119 l. 1464.

**Problem and evidence** — The release note calls the skip harmless “until it is upgraded.” An old hub drops the unknown permission (`apps/hub/src/auth/apply-directory.ts:253–255`) but stores the incoming `directory_version` with the filtered roles (ll. 194–195, 420–422). After the binary upgrade it still polls with that version (`apps/hub/src/sync/config-poller.ts:114–124,159–160`). With equal versions the cloud has no directory to resend (`apps/cloud/src/modules/config-sync/service.ts:73–76`). The Manager can therefore remain unable to answer after upgrading, until an unrelated directory change occurs.

**Fix** — Require hubs that will use OR-7 to have the new permission catalogue before they receive the backfill directory. For any hub that consumed it on the old binary, explicitly bump the affected tenant's directory after the hub upgrade and confirm a listed Manager resolves the grant before enabling OR-7. Add the old-apply → upgrade → refresh case to test 119. Keep the migration's single bump.

### R3-M-3 — The stale owner editor can drop B-5 after its in-page reload

**Location** — B-5 l. 32, §5.1c l. 947 and §10 test 119 l. 1464.

**Problem and evidence** — “Reloading fixes it” is wrong for the current stale banner. When an editor receives a permission it cannot round-trip, block grant replacement and prompt for a full reload. Make the stale banner reload the whole application across this release. Specify the `perm.hand-over-unpaid` label in the client dictionaries. Pin a stale-tab test that refetches Owner/Manager and verifies an unrelated grant edit preserves B-5.
