## MAJOR

### R3-M-1 — Socket caps leave sustained public request work unbounded

**Where:** M97 l. 591, §7.12 l. 2117, §7.13 l. 2133, §10 test 201 l. 2491.

**Problem and evidence:** M97 explicitly leaves guard and unmatched replies outside all buckets. The cap is on concurrent sockets and `maxRequestsPerSocket` is per connection, so a guest can keep the shared hub process parsing and rendering replies even after exhausting M99. The timeout options alone also miss the stated slow-request protection. Fastify 5.12.7 sets `server.requestTimeout` after Node constructs the server, leaving Node's default 60 s header timeout and 30 s expiry scan unless explicitly set. `connectionTimeout` measures inactivity. Test 201 covers idle sockets only. The current hub uses the same process for listen, tick and print (`apps/hub/src/lib/boot.ts:225,249–257`). [Fastify HTTP setup](https://github.com/fastify/fastify/blob/v5.12.7/lib/server.js#L335-L345) · [Node timeout defaults and enforcement](https://github.com/nodejs/node/blob/v22.22.2/lib/_http_server.js#L461-L503)

**Fix:** Set Node's public HTTP options `headersTimeout: 10000`, `requestTimeout: 10000` and `connectionsCheckingInterval: 1000` at construction. Put a separate cheap ingress budget before Fastify route lookup, keyed by an actual guest source IP on routed networks (start at burst 40, 20 requests/s, including rejected and unmatched requests). Close over-budget connections before routing or rendering. Reject GET request bodies before dispatch. Extend 201 to cover a continuously active partial header, connection refill after close, and sustained guard/unmatched traffic while a separate client gets healthy main-port responses and valid public polls. State the allowed timeout tolerance.

### R3-M-2 — NAT makes the per-IP socket cap a guest-wide cap

**Where:** M97 l. 591, §7.12 ll. 2114–2117, §7.13 steps 3 and 9 ll. 2127, 2133, §10 tests 197 and 201 ll. 2487, 2491, MQ15 l. 2628.

**Problem and evidence:** §7.13 says “Routing or NAT … both work.” Sixteen open sockets from any one phone behind NAT fill the only source-address allowance. The next phone is disconnected before Host, HMAC or M99 runs. Test 197 promises that 50 NAT'd guests succeed and specifies neither real sockets nor contention for their shared cap.

**Fix:** Make routed guest IPv4 with distinct source addresses the installation default. Permit NAT only when the router enforces the per-client connection and request caps before translation. For that verified configuration, set the hub's cap for that router address to the public aggregate cap and keep the per-IP M99 invalid bucket. Leave the feature off at NAT-only sites without those controls, consistent with OD-5. Use real concurrent sockets in test 197 and commissioning. Verify one abusive phone is capped upstream while another gets a valid poll, and preserve test 201's limit for routed guests.

### R3-M-3 — Guard and error traffic can still consume the service log budget

**Where:** M97 l. 591, §7.2 ll. 2017, 2023–2025, §10 tests 187 and 202 ll. 2477, 2492.

**Problem and evidence:** The summary has no category for guard errors or parser/handler failures. A URL-free serializer controls fields only. Fastify logs the incoming request before `onRequest`, so a reply's classification cannot suppress that line after the fact. Test 187 still requires per-request lines for the same classes §7.2 and test 202 suppress. The main hub logger is `info` and its generic error handler can also emit per-request errors (`apps/hub/src/server.ts:151–170,346–365`). [Fastify log-before-guard order](https://github.com/fastify/fastify/blob/v5.12.7/lib/route.js#L527-L573)

**Fix:** Disable automatic request logging on the public instance. Use a single summary counter path for every completed outcome, with explicit `guard_denied`, `malformed`, `overload` and `failed` counters alongside the existing four. Count each outcome once. Keep URL, headers, request buffers and raw error data out of public request-path logs. Rewrite 187 to inspect summaries and captured logs for MAC/URL absence, keeping the main-port assertion. In 202 use a controlled clock and add guard, parser and success replies to the flood. Assert exact counts, silence in an empty interval and no per-request lines.

### R3-M-4 — Early HTTP replies bypass the promised public headers and can reflect the URL

**Where:** §6.40 l. 1976, §6.41 l. 1988, §7.13 l. 2122, §10 tests 184 and 198 ll. 2474, 2488.

**Problem and evidence:** `onSend` covers normal Fastify replies only. Fastify's bad-URL and max-parameter-length paths write raw responses with the supplied path in the body. Node also writes a raw 503 when excess pipelined requests cross `maxRequestsPerSocket`. These paths can return without the public headers or counters, and the URL paths can echo a supplied bearer link. [Fastify URL errors](https://github.com/fastify/fastify/blob/v5.12.7/fastify.js#L645-L690) · [Node request-limit path](https://github.com/nodejs/node/blob/v22.22.2/lib/_http_server.js#L1148-L1164)

**Fix:** Define the response boundary. Use a sanitized public framework-error handler for bad URLs and overlong parameters, with fixed 400/414 bodies, the same headers and zero DB work. Close the socket silently on Node's `clientError` and `dropRequest` events with the corresponding summary counter. Apply the promised headers to every HTTP reply actually sent. Extend 198 with a malformed path containing a valid link, an overlength parameter, and a socket crossing the request cap. Assert no URL echo and the specified headers or silent close.

### R3-M-5 — A denied poll can consume the budget for other orders

**Where:** M99 l. 593, §7.12 ll. 2110–2116, §10 test 185 l. 2475.

**Problem and evidence:** “Charged to the valid … pair” leaves debit order undefined. A builder can debit the global bucket before rejecting the exhausted order bucket, allowing sustained use of one leaked link to consume other customers' budget. The same ambiguity affects the invalid pair. The statement ceiling also says “at most 100 SQLite statements a second” despite a 500-token initial burst and two statements per successful read (§6.41 l. 1987).

**Fix:** Refill and inspect both buckets on the same monotonic timestamp, then debit both only on admission. On denial debit neither. Report the scope of the bucket with the longer wait (ties prefer IP/order) and derive both retry fields from that wait. Add sustained denied traffic on one leaked link to test 185 and assert a different order remains available. State the sustained 100 statements/s refill budget and up to 1,000 statements against a full initial burst, plus subsequent refill.

Group live parts by `(order_id, parent_order_item_id)` in memory and derive each header's state from its own live parts. Skip headers with no live parts. Keep the relation out of StatusView. Extend 183 to include two deals in the same order in different states and a removed part, still with two statements.

### R3-M-7 — Commissioning asks for a live response before the listener starts

**Where:** M97 l. 591, M98 l. 592, §3.10 l. 910, §4.2 l. 952, §7.13 steps 4–6 ll. 2128–2130, §10 tests 179 and 204 ll. 2469, 2494.

Turn the flag off and restart on any failure, before issuing slips. Make successful bind on the provisioned hub an explicit `statusLink` condition in M98 and §4.2. In 179 distinguish guard-order injection (wrong Host first, then unprovisioned) from real setup boot (public port closed). Keep 204's port-taken QR assertion.

### R3-M-8 — Reopening a bill can revive an expired printed link

**Where:** M98 l. 592, §6.41 l. 1985, §10 test 182 l. 2472, §12.3 OD-9 l. 2644.

**Problem and evidence:** The deadline uses mutable `day_closed_at`. The `OrdersUnbilled` fold clears it (`apps/hub/src/orders/projection.ts:135–140`). If the only order in a group closes four hours after business-date midnight, the link expires two hours later. Reopening the bill one hour after expiry restores access until the 36-hour ceiling. Test 182 reopens at three days, when the ceiling hides the regression.

**Fix:** Define a tracking deadline in the 02b export backed by replayable close history. Preserve the accepted close + 2 h and 36 h bounds, and make an elapsed deadline irreversible for that link across reopen and restart. Project the tracking cutoff with the existing order fold and return it in the existing orders SELECT. Add a reopen after the two-hour grace but before the ceiling in test 182, including reload from the projection.
