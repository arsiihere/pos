## BLOCKER

### B-1 — "Not paid" is decided by the device and by the clock, so a card charged once is charged twice
**Where:** P7 (l. 78), P9 (l. 80), state machine l. 103–105, §3.7 "Device step" (l. 178), §5.1 `PaymentIntentCancelled.reason` (l. 273), §6.3 (l. 390), §6.4 "ready, now ≥ expires_at" (l. 400), §8 items 4–5 (l. 478–479), tests 10, 15, 33.
**Problem:** P7 says a device result is "never proof". That is applied only to **approved**. `declined` / `cancelled` / `error` from the page append `PaymentIntentCancelled` straight away (§6.3), and the PayError panel tells the cashier **"Nothing was charged. Try again"** (§8 item 5, "device decline"). On a SoftPOS SDK, `error` and `cancelled` are exactly what the device reports when the online authorisation outcome is **unknown**: a timeout after the card was read, the app going to the background, a Wi-Fi drop mid-tap (test 35 does this on purpose). The authorisation may have succeeded at Paymob. The sequence is: tap → SDK `error` → intent `cancelled` → "Nothing was charged, Try again" → second intent → second tap → approved. The first charge then comes in late. If the split is still open it is applied (P8, `after_state 'cancelled'`), the second becomes `exceeds_due`, and the customer has paid twice with one charge on a manager's alert. Expiry has the same flaw. `ttl_ms` 120 000 (l. 182) runs from `created_at`, not from the tap. A card tapped at 1:55 whose authorisation takes 20 s is `Expired` at 2:00 while the SDK is still waiting. The panel says "No payment arrived. Try again", and the same double charge follows. Two smaller gaps make it worse. `ReportPaymentIntentResult` checks neither that the caller's device is the intent's `device_id` nor the bill scope, so any `take-payment` session (or a LAN-injected script, O-14) can cancel another device's card intent. And a late success while a **new** intent is open on the same bill is undefined: does `providerPaymentDrafts` hit row B-2's own `PAYMENT_INTENT_PENDING` guard? `unapplied_reason` has no value for it.
**Fix:** (a) A device result never ends an intent. `declined` / `cancelled` / `error` store the hint and wake the worker, as `approved` does. The intent goes to a new open state **`confirming`** (still open, still holding the bill). The worker ends it only on the provider's server answer (`failed` / `expired` / not found), or after a confirm window (e.g. 60 s for SoftPOS) with `last_check 'unknown'`. (b) While the intent is `confirming`, or ended with `last_check 'unknown' | 'unreachable'`, the panel shows **"Checking with the bank… do not charge again"** and never "Nothing was charged". "Try again" is disabled until the provider has answered `failed` / `expired`. (c) For `device_sdk`, `expires_at` is a deadline for the **tap**. Once the device reports a tap, or the provider reports `pending`, the intent may not expire before the provider answers. (d) §6.3 refuses a report from a device other than `payment_intents.device_id` (`403 DEVICE_ACCESS_DENIED`) and runs `billAccess`. (e) State the late-apply rule while another intent is open: the worker's apply **does not** consult row B-2's guard (the guard exists to keep staff from changing the bill). Add tests: SDK `error` then provider `paid` → one `PaymentAdded`, no "Nothing was charged"; tap at `expires_at − 5 s` → no `Expired` until the provider answers; report from another device → 403.

### B-2 — Once an intent ends, nobody watches for its money; a second payment is filed as a "duplicate"
**Where:** P6 (l. 77), P8 (l. 79 "Money the customer paid is never silently lost"), P9 (l. 80), P14 (l. 85), P15 (l. 86), §3.6 `status` / `cancel` (l. 164, 166), §6.2 (l. 386), §6.4 relay row and Apply row (l. 401–402), §7.1 "hub internet down" (l. 451), tests 16, 18, 21.
**Problem:** (1) Polling (P15) runs only for `ready` intents. After `cancelled`, `expired` or `failed`, a payment is seen only if a webhook arrives. §3.6 says it is still to be confirmed whether Alfalah has a webhook at all, and that a dynamic QR probably **cannot be withdrawn** (`cancel → not_supported`). So the default UI path ("Cash instead" / "Pay later" → `CancelPaymentIntent`, §8 item 2) leaves a payable QR in the customer's banking app. A customer who scanned before the cancel and pays 30 s later has paid money that no poll will ever see. The same happens after a hub internet outage: "a payment made meanwhile is picked up by the relay pull" (l. 451) is true only for providers with a webhook. (2) In the relay pull (l. 401), a `paid` item whose confirming `status` call returns `retry` is still followed by "then cursor update". The notification is passed and never re-read. (3) The Apply row treats any confirmation on a `succeeded` intent as a `duplicate` no-op, without comparing `provider_txn_ref`. A **second, different** payment against the same intent (a QR paid twice from two phones, a customer who retries in the bank app, a provider that lets a dynamic QR be paid more than once: to confirm) is real money logged as `duplicate`, with no event and no alert. P8's promise is broken in three places.
**Fix:** (a) Keep watching after the end. An intent that ended **without** a server-final answer (`cancelled` with cancel `not_supported` or `retry`, `expired` with `last_check ≠ 'expired'`) stays on the worker's list with a **watch-until** = the provider's QR or authorisation validity + margin (a capability, e.g. `late_window_ms`). It is polled every 15–30 s until then. This needs a `watch_until` column and an index next to `payment_intents_open_due`. (b) A `paid` relay item whose confirmation did not complete stays **pending on the hub**. Either the cursor stops at the first such item, or (simpler) the item is copied into a hub table `payment_relay_pending` and retried. Never advance past it. (c) In Apply, if `state = succeeded` and `provider_txn_ref` differs from the stored one, record it as a second, unapplied success: `PaymentIntentSucceeded { applied: false, unapplied_reason: 'second_payment' }` + alert. This needs a payload field `provider_txn_seq` or a separate event, because "Succeeded twice" must be allowed by the fold. Only an equal ref is a `duplicate`. (d) While an intent of a non-cancellable provider is inside its watch window, a new `StartPaymentIntent` on the same bill shows "The last QR may still be paid — wait N s or confirm" (`409 PAYMENT_INTENT_PENDING { intent_id, reason: 'previous_live' }`, overridable with `confirm_previous_void: true`). Tests: paid 30 s after cancel on a status-only provider → late success; relay item with status `retry` → retried next tick; second txn ref on a succeeded intent → unapplied + alert.

### B-3 — Raast cannot be configured on the pilot branch; OQ-1's default is impossible and test 6 cannot be set up
**Where:** P16 (l. 87), §3.6 "Mode" (l. 170), §6.1 edge l. 376, test 6 (l. 522), §7.3 X-4 (l. 468), OQ-1 (l. 638); `packages/events/src/admin/billing.ts:377–384` (`billingSettingsReferenceIssue`); 05 row A-1 (3) "with the jurisdiction's adapter ≠ `none`, an active mode offered on a fiscalized order type needs a code for that adapter → `422 CONFIG_REFERENCE_INVALID`"; README R37 (PRA live in the pilot).
**Problem:** The billing settings `PUT` already refuses, on a branch whose adapter is not `none`, **any active mode without a code for that adapter as soon as one order type is fiscalized**. Payment modes are not offered per order type (`PaymentMode` has no order-type field), so "Raast refused on fiscalized order types, allowed on the others" (OQ-1 (a), the stated default) cannot be expressed. On a `PK-PB` branch with any fiscalized type, the Raast mode cannot be saved as active, and `StartPaymentIntent` never reaches P16's gate. Test 6 ("the same mode **accepted** on a non-fiscalized order type") cannot be set up on such a branch. The pilot branch is PRA-live from day 1 (R37, 05 Appendix P), and A13 has had no answer since 05 v0.6. So **half of G-12 has no pilot path** unless the owner picks (b) (contradicts R37) or PRA answers in time (c). This is not an open question with a default; it decides whether 05c-2 belongs to milestone A at all.
**Fix:** (1) Rewrite P16 / OQ-1 against the real rule: on a PRA branch, Raast is possible only once the mode carries a `PRA` code. Option (a) is removed, or becomes "all order types non-fiscalized", which is a fiscal decision the owner must sign. (2) Move OQ-1 into §7.3 as a **STOP** that gates 05c-2 for milestone A, with a date by which the owner decides (b) or (c). Otherwise the §1 fallback (Raast stays manual) applies, and manual Raast is refused on PRA too, so it is "Raast not accepted at the pilot". (3) Test 6 is rewritten: a `PK-PB` branch with a Raast mode without a code → the settings `PUT` returns `422 CONFIG_REFERENCE_INVALID`; with a code → Start passes the gate. P16 stays as defence in depth for a code removed later.

## MAJOR

### M-1 — `StartPaymentIntent` skips 05's bill scope (C8), and the worker's apply then bypasses it for good
**Where:** §6.1 script (l. 369), P5 "without session, permission or shift resolution" (l. 76), §4.5 B-1 (l. 243); `payments.ts:153` (`billAccess(...)`, "C8: the scope last").
**Problem:** `AddPayment` ends with `billAccess(…, ['take-payment'])`: a waiter with `take-payment` scoped to own tables cannot take money on another waiter's bill. The §6.1 script has no scope step. `CancelPaymentIntent` has one, `StartPaymentIntent` does not. `providerPaymentDrafts` then deliberately skips session and permission at apply time. Result: any `take-payment` holder can start a provider payment on any bill in the branch, and the money is booked to them (`taken_by = started_by`) and to their own shift. That is a permission bypass on a money command.
**Fix:** Put `billAccess(ctx.directory, config, staff_id, { seating, scope, placed_by }, ['take-payment'])` last in §6.1, as in `AddPayment` (0 statements: the orders read already gives `placed_by`). Test: a waiter scoped to own tables starts on another's bill → `403`. State in P5 that the scope was checked at start, which is why apply may skip it.

### M-2 — The "bill held while an intent is open" list misses most of the ways the bill can shrink; OQ-4's premise is wrong
**Where:** P11 (l. 82), §4.5 B-2 / B-3 and "02b, 04, 03a, 03c: No change" (l. 244–256), test 24–25, OQ-4 (l. 641); `apps/hub/src/orders/line-guard.ts:5–13, 34–45` (`registerLineGuard`, already called by `RemoveItems`, `CompLine`/`applyComp`, `SetLineWeight`, 04 `VoidItems`, void-preview, 05 `RemoveComp`); `apps/hub/src/tables/commands/{merge-tables,split-seating,move-table}.ts`; `commands/close-business-day.ts:20` (`registerDayCloseGuard`).
**Problem:** OQ-4 says guarding the line commands costs "three more spec bumps". It does not. 02b already has an ordered line-guard list that 04 and 05 register into, and one `registerLineGuard` by 05c covers every line command. The only change is widening the `LineGuardResult.code` union (`'VOID_PENDING' | 'LINE_IN_CLOSED_SPLIT'`) by one code: one 02b row. Paths left unguarded that lower `card_due` or move the bill while the customer is paying: `RemoveItems`, `VoidItems`, and **the approval of a void requested before the intent** (04's kind `apply`, not a command); `CompLine`; `SetLineWeight`; **approval of an `ApplyDiscount` / `RemoveServiceCharge` request raised before the intent** (row B-2 guards the commands, not the kinds' `apply`); `ReopenBill` of a PARTLY_PAID bill (an intent on split 2 while split 1 is closed); 02a `MergeTables` / `SplitSeating` (bill absorbed, orders moved); order cancel → 05's `BillClosedEmpty` hook. Delete OQ-4, or keep it only for the kinds' `apply`. Tests per path.

### M-3 — A provider payment can be removed like a typed one; the customer is then charged again
**Where:** §2 l. 53, P5 (l. 76), §4.5 B-1 / B-4 (l. 243, 246), §12.4 refunds (l. 652); `payments.ts:271–276` (`RemovePayment`: allowed when `taken_by_staff_id === staff_id`, any open split, open shift).
**Problem:** `RemovePayment` exists to correct a mistyped manual entry. A provider-applied `PaymentAdded` has `taken_by = started_by`, so the cashier who started the QR can remove it, with reason `wrong_mode` or `other`, while the bank has settled the money. The bill is then due again, the customer pays cash, and the Z shows one payment for two. Nothing in 05c marks these payments as different (`source 'provider'` lives only in `payment_references`).
**Fix:** row B-1 adds a rule to 05 §6.10: a payment whose reference `source = 'provider'` cannot be removed (`409 PAYMENT_PROVIDER_FINAL { payment_id }`, a new code). The only way back is the documented refund: portal refund + manual `AddPayment { direction: 'out' }`. Alternatively it can be removed only by `close-shift-for-others` with a note, and it raises `payment_unapplied`. Test.

### M-4 — Cloud dedupe and routing keys will drop or misroute real notifications
**Where:** P6 (l. 77), §5.3 `payment_notifications` (l. 342–352), §6.9 (l. 429), §6.11 (l. 435–437), P13 (l. 84), §3.6 / §3.7 webhook rows (l. 165, 180).
**Problems:** (1) `UNIQUE (tenant_id, provider_key, provider_event_id)` with `provider_event_id` = "the provider's own notification / **transaction** id". Card and wallet gateways commonly send several callbacks for one transaction id: pending then success, or a failure then a retry on the same order. Keyed on the transaction id, the **later, decisive** callback hits `ON CONFLICT DO NOTHING`, gets `200`, and is lost. (2) `intent_id TEXT NOT NULL` assumes the provider echoes our ULID. If it echoes only its own QR or order id (`provider_intent_ref`, which only the hub knows), the extractor has no intent id and the row cannot be stored. For a Raast dynamic QR, the EMVCo additional-data references are typically ≤ 25 characters while a ULID is 26 (to confirm against the SBP spec). (3) The webhook secret and endpoint are **per branch**, but many providers hold one signing secret and one callback URL per **merchant account or integration**. If the restaurant uses one account for several branches, a notification for branch B arrives at branch A's endpoint, verifies, is stored under A, A's hub "skips unknown intent", and B never sees it. (4) The verifier is `verify(headers, rawBody, secret)`. Some gateways sign a **query parameter** computed over selected fields rather than the raw body. The signature fixes a contract before the documents exist.
**Fix:** (1) Dedupe on `(tenant_id, provider_key, provider_event_id, outcome)`, or on the provider's notification id when the docs give one. Never on the transaction id alone. (2) Allow `intent_id` **or** `provider_intent_ref` (both nullable, CHECK one present). The hub resolves the ref through `payment_intent_provider`. Add an index for that lookup. (3) Make the endpoint and secret per **(tenant, provider account)**, and filter the pull by tenant, with the hub ignoring intents it does not own. Or record in §3.6 / §3.7 that a per-branch merchant account is a pilot precondition (an X-row). (4) `verify(request: { headers, query, rawBody }, secret)`. Tests for (1) and (3).

### M-5 — The public webhook route does not fit D54 / M55 as written; it needs a Foundation change, not only an HPA row
**Where:** row H-1 (l. 251), §5.3 index `payment_webhook_endpoints_endpoint` (l. 340), §6.9 (l. 429), §7.2 (l. 459); Foundation v1.17 §6.4 "Auth groups" (l. 1621 of F); HPA v1.12.4 M55 (b) (`db/credential-lookup.ts` importable only by `plugins/tenant-scope.ts` / `owner-credentials.ts`, lint + test); `apps/cloud/src/plugins/tenant-scope.ts:9–15, 17` (allowlist; scopes `jwt | branch-key | registration-code | none`).
**Problem:** H-1 puts the route "on the tenant-scope allowlist (resolved by `endpoint_id`, like the registration-code routes)". Registration codes are not on the allowlist. They are a **credential type** resolved by the guard through `credential-lookup.ts`. An allowlisted route has no `TenantContext`, the repository base class throws without one, and the handler may not import `credential-lookup` (M55 (b)). The unique index on `endpoint_id` alone does not lead with `tenant_id` (§6.8 index rule), and only M55 (a)'s named credential indexes are excused. Foundation §6.4 also fixes the auth groups (`/v1/sync/*` branch key, `/v1/owner|admin/*` JWT, `/v1/auth/*` + `/v1/health` allowlist). `/v1/payments/webhooks/*` is a fifth group. That is a Foundation change, and R34 requires a version bump, not a §6.2 append.
**Fix:** add a guard scope **`webhook-endpoint`** to `tenant-scope.ts` (lookup by `endpoint_id` in `credential-lookup.ts`, then `setTenant`), name the new pre-tenant index as an M55-style override in HPA, and add a Foundation row (F-2, version bump) for the §6.4 auth group. Route-inventory and cross-tenant tests: an endpoint of tenant A never writes a row for tenant B.

### M-6 — A dead relay or a wrong webhook secret is invisible; the counter keeps starting intents that cannot be confirmed
**Where:** P12 (l. 83), §3.8 health rows (l. 194–195), §6.4 Health (l. 403), §6.9 `401 … logged with endpoint id only` (l. 429), §7.1 "cloud down" (l. 452), §8 item 5 (l. 479), test 19.
**Problem:** `health()` probes the provider only. For a webhook-only provider (P15 allows it, and Alfalah may be one), confirmation depends on the cloud relay: the cloud is up, the hub's pull works, and the webhook signature verifies. None of that is in the health record. A mistyped webhook secret makes **every** real notification fail with `401`. The provider retries and gives up, the owner sees nothing, every intent expires with "No payment arrived. Try again", the cashier retries, and the customer pays twice (B-1, B-2). Health is also checked every 60 s and trusted for 120 s, so for up to two minutes after the internet drops, Start is accepted.
**Fix:** (1) The health record per provider = provider probe **and** (for `webhook` providers without `status_query`) the last successful relay pull ≤ 30 s ago. (2) The cloud counts `401`s per endpoint. Three in 10 min raises a cloud-side flag, returned by the pull (`{ endpoint_unhealthy: true }`), which the hub turns into a 01d alert to the owner/managers. (3) Health age ≤ 60 s, or 2 × the probe period. (4) The cashier screen gets a "Customer says paid" button on Expired that keeps the intent watched (B-2) and pages a manager, instead of offering only "Try again". Tests.

### M-7 — Unapplied money: the alert kind cannot be declared as written, it disappears at day close, and the resolution is not linked
**Where:** P8 (l. 79), row D-1 (l. 250), §5.2 `resolved_alert_id` (l. 290), §6.5 `unapplied=1` "last 30 days" (l. 411), §8 item 7 (l. 481), OQ-6 (l. 643), §12.4 (l. 654); 01d v1.3.6 l. 584 (families `urgent | action | info`), l. 606 (`expires_at_day_close: false` only with `closes_on: 'seen'`), l. 38 (05's `fiscal_outbox_stuck`: target `managers`, `closes_on: 'owner'`, `expires_at_day_close: true`), §3.12 (lock-safe `display` vs signed-in `details`).
**Problem:** (1) D-1 says "family money" and "audience `close-shift-for-others`". 01d has no `money` family, and an action kind has a `target`, not a request `right`. (2) Copying `fiscal_outbox_stuck` (`closes_on: 'owner'`) forces `expires_at_day_close: true` (startup error otherwise). The alert for money the customer paid **expires at the day close**, the very moment the manager reconciles. After that it lives only in a 30-day list. (3) Resolution is "manual `AddPayment` with the reference + close the alert", with no link between the two. 07 counts "payments by provider" from `PaymentAdded` + `applied: true` and "unapplied" from `applied: false`. The resolved payment is then in both, and the unapplied list never empties. (4) "Last 4 of the provider reference" on the alert body belongs in `details`, not in the lock `display`. With B-1 and B-2 fixed this case gets rarer, but with Raast's non-cancellable QR it will happen every week of the pilot, so OQ-6 is not "rare".
**Fix:** declare the kind correctly (family `action`, target `managers` or a holders target that 01d supports, raised again at each day open while unresolved, as `fiscal_outbox_stuck` is raised again while stuck). Add the small command now: **`ResolveUnappliedPayment { intent_id, resolution: 'applied_to_bill' | 'refunded' | 'kept', payment_id?, note }`** → `PaymentIntentResolved`. It closes the alert and lets 07 subtract. That gives `resolved_alert_id` a source event (m-4). Move OQ-6 to "decided" or make it a pilot STOP.

### M-8 — SoftPOS: PCI scope and the host-app constraints are not analysed; the page chooses the amount charged to the card
**Where:** §3.7 (l. 176–185), row T-1 (l. 253), row T-2 (l. 254), §6.6 `sdk_params` (l. 415), §7.3 X-2 / X-5 (l. 466, 469), §1 "no card data must touch our system" (implied by l. 165, 447); 05b H-3 (global cleartext on the LAN), M-17 (device owner, lock task, sideloaded release-signed APK updated from the hub), O-14 (LAN script injection accepted).
**Problems:** (1) `startCardPayment({ intent_id, amount_minor, currency_code, sdk_params })` takes the **amount from the page**. A buggy page, or a LAN-injected script (O-14), charges the card a different amount than the intent's. P7 records it as `amount_mismatch`, but the customer has been charged it. (2) `sdk_params: Record<string, string>` is returned by `GET /queries/payment-intent` to **any** `take-payment` session, over cleartext HTTP (H-3). If Paymob needs a server-created payment token (§3.7 `create`, "to confirm"), that token is a bearer credential for the payment and is exposed to the whole LAN. (3) There is no whitelist for the SDK result: PAN, masked PAN, expiry, cardholder name and EMV tags must never cross the bridge, be logged or be stored. The spec says this for webhook payer data (l. 165) but not for the device. (4) SoftPOS (MPoC / CPoC) SDKs attest the host app and device. The 05b app is sideloaded, self-updated from the hub, device-owner, lock-task, global cleartext, WebView bridge. Whether such a host passes attestation decides whether 05c-3 exists, yet it is one "to confirm" cell, and X-2 is "Not started" three months before the pilot. Some SoftPOS offers are a **separate app** called by intent, not an embeddable SDK. That would change T-1 and native_api completely. (5) T-2 "SDK dependency pinned in `apps/tablet` (own lockfile)": `apps/tablet`'s lockfile is npm. An Android SDK is a Gradle / Maven artefact, often from a private repository with credentials, which `tablet.yml` would need as a CI secret.
**Fix:** (1) Native takes the amount and currency only from `sdk_params` fetched by native itself from the hub, or signed by the hub. The page passes `intent_id` only. (2) `sdk_params` is returned only to the intent's own `device_id`, is never logged, and the spec classes it (secret or not) per provider once the docs come. (3) Write the result whitelist (`outcome`, `device_txn_ref`, `error_code`) and a Gradle test that any other field is dropped. (4) Add X-6 "SoftPOS host-app eligibility (sideload, device owner, WebView, cleartext) confirmed in writing by Paymob" as a STOP before 05c-3, and an owner question: "if SoftPOS needs Play distribution or a separate app, is card on the tablet still wanted for the pilot?" (5) T-2: Gradle dependency, repository credentials as a CI secret, licence file.

### M-9 — The port, tables and state machine are fixed before any provider document exists; "does not invent provider API details" is not true of the shape
**Where:** l. 3 ("this spec does not invent provider API details"), P1 (l. 72), §3.4 (l. 117–152), §3.6 / §3.7, §5.3, §4.3 / §11 05c-1 (11 tasks, l. 591–602), §7.3.
**Problem:** Every field is marked "to confirm", but the **architecture** assumes facts: that Alfalah creates dynamic QRs through an API and answers a status query by our reference; that both providers echo our ULID; that per-branch webhooks exist; that Paymob SoftPOS is an embeddable SDK returning a transaction id the server can look up; that QR validity is a fixed TTL. B-2, M-4 and M-8 show how each wrong guess changes tables, events or the plugin API. 05c-1 is 11 tasks built against this guessed port before X-1 / X-2. The events are v1 and append-only, so a wrong `PaymentIntentReady` / `Succeeded` shape costs an upcaster or a new event type.
**Fix:** keep 05c-1, but cut it to what is provider-neutral and certain: the 05 guards (M-2), the reference `source` column, the unapplied resolution (M-7) and the client panels on `fake`. **Freeze the event payloads and the port only after X-1 or X-2 delivers a document**, with a re-review of §3.4 / §5 at that STOP. State in l. 3 that the port shape is itself a guess to be re-checked.
