## MAJOR

### R2-M-1 — Provider `pending` moves a card intent to `confirming` before any tap. Cancel and the tap deadline are lost
**Where:** P9 (l. 156), state machine l. 170, §6.4 `ready / confirming` row (l. 475) vs Deadlines row (l. 476), port `status` (l. 200–202), tests 15a / 15b (l. 637–638).
**Problem:** Three texts disagree:
- l. 170 says "provider 'pending' **after a tap**".
- l. 475 says `pending` on a `device_sdk` intent in `ready` → `Confirming { provider_pending }`, with no condition.
- l. 476 and test 15a say that at the tap deadline a final `pending` → `Expired { unknown }`.

The hub cannot know "after a tap" before a device hint arrives. The port has one `pending` for two meanings: "created, nothing attempted" and "an authorisation is in flight". A gateway order is normally `pending` from creation. If so, the first 3 s poll moves every card intent to `confirming`. From there:
- Cancel is refused (§6.2).
- The 120 s tap deadline no longer applies.
- After 90 s the intent ends `Expired { unknown }` and is watched for 10 min.
- Every retry on that bill then needs a manager (P9a).

A customer who walks away, or who switches to cash, blocks the counter.

**Evidence:** l. 475 vs l. 476; P9 "Once … the provider reports `pending`, the clock no longer ends the intent".
**Fix:**
- Split the port answer: `{ outcome: 'pending' }` means no attempt is known, and `{ outcome: 'in_progress' }` means an authorisation attempt exists.
- Only a device hint or `in_progress` moves `ready` → `confirming`. `pending` in `ready` is a no-op until the tap deadline (then l. 476 as written).
- Rename the trigger to `PaymentIntentConfirming.trigger: 'device_hint' | 'provider_in_progress'`.
- Test: `pending` polls in `ready` keep `ready`; Cancel is still allowed; `in_progress` → `confirming`.

### R2-M-2 — A server `failed` is not proven order-final, and a late payment on a failed intent cannot be recorded
**Where:** P7 (l. 154), P9 `creating` text (l. 156: "If the provider created it after all, the watch of P9a covers it"), P9a (l. 157: only `cancelled` / `expired`), §5.1 `PaymentIntentSucceeded.after_state: null | 'expired' | 'cancelled'` (l. 334), §6.4 relay row "`failed` / `expired` on an open intent → as a status answer" (l. 478), §8.5 (l. 567).
**Problem:**
1. "Nothing was charged. Try again" is shown on any `Failed`. Card gateways often report failure **per transaction**, and one order can hold a declined attempt followed by an approved one. The relay dedupes on `outcome` (l. 429) and keeps both rows. A relayed `failed` row ends the intent as "not charged". The cashier then takes cash, and the later `paid` row arrives for a `failed` intent.
2. That late payment has no schema: `after_state` has no `'failed'`. P9a gives a failed intent no `watch_until`, and the `PaymentIntentFailed` payload has no field for one. The relay apply path for an ended intent is defined only for `expired` / `cancelled`.
3. P9's sentence "the watch of P9a covers it" is false, because P9a excludes `failed`.

The run 1 B-1 rule ("not paid only from the server") holds only if "server `failed`" means "this intent can never be paid".

**Fix:**
- Port contract: `failed` / `expired` mean **the provider guarantees that this intent can no longer be paid** (the adapter maps a per-transaction decline to `in_progress` / `pending`, never to `failed`). Write this in §3.4 and as an X-2 question.
- A relayed `failed` / `expired` row on a provider with `has_status` triggers a status call. It never ends the intent by itself.
- Add `'failed'` to `after_state`. A `paid` for a failed intent goes through the normal apply (P8).
- Delete the P9 clause, or say "a device_sdk intent that never reached `ready` cannot be paid".
- Tests: a relay `failed` followed by `paid` on the same intent → one success, and the client never showed "Nothing was charged" before the status call; a late `paid` on a `failed` intent → `Succeeded { after_state: 'failed' }`.

### R2-M-3 — A device report that arrives after the intent ended is discarded, along with the only key the status lookup may need
**Where:** §6.3 "`succeeded` / ended → result `{ state }` (no error, no write)" (l. 466); port `status(… device_txn_ref)` (l. 200); §3.7 `status`: "by our reference **or the SDK's transaction id**" (l. 226); test 35 "Wi-Fi off mid-tap → … the real outcome after reconnect" (l. 695); §6.2 cancel from any device (l. 462).
**Problem:**
- *Wi-Fi drop:* the tablet loses Wi-Fi mid-tap for more than 120 s. The tap deadline gives `Expired { unknown }`, which is watched.
- *Cancel from the kiosk:* a cashier on the kiosk cancels while the customer taps on the tablet. That gives `Cancelled`, which is watched.

In both cases the SDK result, with its `device_txn_ref`, reaches the hub after the end and is dropped without a write. If Paymob's inquiry works only by the SDK transaction id, the watch polls can never find the charge. The money then appears only through a webhook, if Paymob has one. Otherwise it is never recorded: the customer is charged and no unapplied row or alert exists.
**Fix:** In §6.3, a report on a **watched** intent (`watch_until > now`) stores the hint and `device_txn_ref` in `payment_intent_provider` (hub state, no event, as today) and wakes the worker for an immediate status. The answer stays `{ state }`. Only `succeeded` and unwatched ended intents are no-write. Test: cancel from the kiosk, then an `approved` report with a txn ref → status by that ref → late success applied.

### R2-M-4 — Relay "not ours → skip" cannot tell another branch's row from this hub's lost intent; paid money is dropped silently
**Where:** P14 "ignores the intents it does not own" (l. 162), §6.4 relay row "intent by `intent_id` or `provider_intent_ref` (1); not ours → skip" (l. 478), §5.3 (no branch on endpoint or notification, l. 411–431), §4.3 06 "After a restore, the worker resumes from the projections" (l. 284), Q-D accepted per-branch accounts (l. 778).
**Problem:** "Ours" means "found in my `payment_intents`". A hub restored from the nightly USB backup has lost the day's intents, but the provider has the charges. The restored cursor re-pulls those rows, and each one is skipped as "not ours" before the cursor moves on. The same happens to a row that carries only `provider_intent_ref` before its Ready tx exists. The result is a customer charged with no record and no alert. P8 ("paid money is never silently lost") is broken on the relay path.
**Fix:**
- Store `branch_id` (nullable; null = a tenant-wide account) on `payment_webhook_endpoints` and copy it onto `payment_notifications`. Q-D accepted per-branch accounts, so this is free.
- The pull returns the rows for the key's branch, plus rows with a null branch.
- A `paid` row for this branch whose intent is unknown is recorded and alerted: either a provider payment with a new reason `unknown_intent` and no intent (this needs a nullable `intent_id` on `provider_payments` and a hub-stream event), or at minimum `payment_relay_unhealthy { reason: 'unknown_intent' }`. It is never skipped.
- Only rows of another branch are skipped.
- Tests 18 and 27c are updated to match.

### R2-M-5 — OWNER — The counter card machine (the stated fallback) charges again with no check while an intent is "unknown"
**Where:** P9a (l. 157), P11 "A watched (ended) intent holds nothing except a new start" (l. 159), §7.1 "Unknown outcome … a new charge on the same bill needs a manager" (l. 535), §8.5 "Do not charge again" (l. 568), OQ-5 (l. 786), header "the card machine with a typed reference stays the fallback" (l. 3).
**Problem:** After "We could not confirm this payment", the obvious next step at the counter is the card machine (manual `AddPayment` on the card mode) or cash. Neither is held while the intent is watched. So §7.1's claim is false for every path except `StartPaymentIntent`. With Raast gone, the card machine is the main retry path. If the tablet charge then settles, the late success becomes unapplied `exceeds_due` and a manager has to refund it. The customer has been charged twice in the meantime.
**Fix (recommended default):**
- 05 `AddPayment { direction: 'in' }` on the intent's split while it is watched with `outcome = 'unknown'` or `cancelled` → `409 PAYMENT_INTENT_PENDING { reason: 'previous_watched' }`.
- The same manager override as P9a (`override_watched`, `close-shift-for-others`) applies.
- This is added to row B-2, with tests 24e and 9b.
- Alternative: the owner accepts the double charge plus a refund, and §7.1 is reworded to say so.

### R2-M-6 — OWNER — With one provider left, 05c-1 and 05c-2 are built before the condition that decides whether card-on-tablet exists
**Where:** §11 05c-1 tasks 1–2 "now" (l. 715–717), STOP-0 = only "the Paymob document is in hand" (l. 721), STOP-C = X-6 in writing (l. 738), Q-B accepted: "only if Paymob confirms the 05b host in writing; otherwise the counter card machine stays" (l. 776), CLAUDE.md "Build only what the spec asks … no … 'for later'".
**Problem:** Paymob is now the only provider, and Q-B makes the whole feature conditional on X-6. Two consequences:
- 05c-1 would merge now items with no use if X-6 fails: a hub migration (`0030`), a 05 behaviour change (B-6), a permission in the roles editor (R-1), and two alert kinds that nothing raises.
- 05c-2 (migration `0031`, frozen events, guards in five other modules) can merge after STOP-0 while X-6 is still unanswered.

Migrations are never edited and events are never removed, so a "no" from Paymob leaves permanent dead schema.

**Fix (recommended default):**
- STOP-0 = X-2 document **and** X-6 written confirmation **and** proof of a server confirmation (Q-C).
- Before STOP-0, 05c-1 keeps only the provider-neutral **code that is not a contract**: the pure state machine and apply decision (task 3) and the client mocks (task 4).
- Tasks 1–2 (codes, permission, alert kinds, `0030`, B-6, B-7) move behind STOP-0.

### R2-M-7 — Foundation v1.18 and HPA v1.13 already carry 05c rows as normative text, but 05c says its rows apply only "when 05c is approved"

**Fix:**
