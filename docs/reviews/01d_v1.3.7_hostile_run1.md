### B-2 — Refusing a board's alert-mode socket with `4403` makes the kiosk page wipe its pairing
**Where:** changes row D-5 (l. 10, "alert-mode connection from a board is refused (`4403`)"); §6 batch 3 (l. 1726); §3.7 alert mode (l. 765, unchanged) and revoke (l. 801: `4403` = `DeviceRevoked`); test 112 (l. 2018). **Problem:** every client reads `4403` as "this device is revoked". The path is a normal one. A manager turns a signed-out counter kiosk into the board (05a B-3). Its `/staff/` page stays on the sign-in screen with its alert-mode socket open: 05a ends staff sessions only, and an alert-mode socket gets no `device_profile` frame. (a) v1.3.7 does not say whether that open socket is closed at the `DeviceProfileSet`, so until then it keeps getting device frames. (b) At the next reconnect (Wi-Fi blip, hub restart) the hub answers `4403`, and the browser page **wipes the device keys and shows Pair again**. The TV board then needs a fresh pairing. On a tablet board running the 05b app (05a T-1 is still open), the native service gets `4403`, its HTTP check says the token is valid, and it reconnects, gets `4403` again and loops with one HTTP check per round.
**Fix:** do not reuse the revoke code. Close a board's alert-mode auth with `4401` and reason `display_device`, or with a new constant in `WS_CLOSE`, a Foundation §6.5 / 00 §6.21 row. Write the client rule in §8.1 (the page follows `display_device` to `/board/`, as the sign-in already does, 05a l. 629) and the 05b row (the service stops, no token check, no loop). State that the `DeviceProfileSet` that makes a device the board closes its open alert-mode socket after commit with the same code (the alert-mode list's own after-commit check, as l. 801 does for revoke). Test 112 checks the close code and reason, and a client test checks that the page keeps its keys.

Otherwise add `via TEXT` to `alert_recipients` through a new migration and change the "no migration" line. Either way, tests: a Pass tablet with only a 2× `point` row and a signed-in runner gets `lock` in both the frame and the catch-up; a point-bound kiosk with `takeaway` gets the card; a counter tablet re-profiled to `dine_in` after step 0 gets `lock` in the catch-up.
