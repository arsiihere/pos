## Part 2 — New issues caused by the fixes

### Major

#### N1. A login or refresh that holds the owner row while a change or reset waits issues an access token that survives the change (M1 reopened in the race)
- **Where:** 01b §3.7 L283 ("every other access token stops working at once"), §6.11 step 5 L717, §6.13 L740–742, §6.14 L746; 00 §6.22 L1176, §6.23 L1190, §6.24a L1208; test 74 a, d (L950).
- **Mechanism:** change-password and the reset compute `$now` **before** they send the `UPDATE` (§6.11 step 5: `password_changed_at = $now`), so they compute it before they get the row lock. A login or refresh holding the owner row `FOR SHARE` computes its own `now` **after** taking the lock (`issueTokens` and `refreshTokens` read the clock after the first query, `service.ts:88`, `:198`).
- **Failure scenario:** an attacker holds a stolen refresh token and refreshes. The refresh takes `FOR SHARE` at t=0. The owner's change-password computes `now = 1` and blocks on the `UPDATE`. The refresh computes `now = 2`, signs a JWT with `iat_ms = 2` and commits. The change commits `password_changed_at = 1` and revokes the successor. The attacker's access token has `2 ≥ 1`, so the guard accepts it for up to 1 h of `/v1/admin/*` access: PINs, roles, marking staff as left. Test 74 (a) is this exact interleaving but asserts only on the refresh token. The same applies to 74 (d) when the login wins the lock. A second path: if `reset-owner-password` runs on a host whose clock differs from the API's, every ms comparison is off by the skew. If the CLI's clock is ahead, the owner's fresh temporary-password login loops on `JWT_INVALID` → `REFRESH_TOKEN_INVALID`. If it is behind, tokens from the last minutes before the reset survive.
- **Smallest fix:** replace the time comparison with a counter. Add `owner_users.credential_version INT NOT NULL DEFAULT 0`. Change and reset increment it **under the row lock**. Login and refresh read it under their own lock and put it in the JWT (claim `cv`) and on the refresh token row. The guard and refresh require equality. A missing claim counts as 0, which covers tokens from before the release, and D-10's ms rule goes away. If the time rule is kept, the minimum is: change and reset first `SELECT … FOR NO KEY UPDATE` the owner row, **then** take `now`. Even then, a token issued in the same millisecond passes strict `<`. Extend test 74 (a) and (d) to assert that the **access** token issued by the racing refresh or login gets `401 JWT_INVALID`.

#### N2. Login and refresh upgrade `FOR SHARE` to `UPDATE` on the owner row, so two concurrent logins deadlock
- **Where:** 01b §6.13 L738 (login: `FOR SHARE`, "then reads and clears `lock_notice_at`"), L740 (refresh: `FOR SHARE`; the rotating path "read and clear `lock_notice_at` in the same transaction"); 00 §6.22 L1176, §6.23 L1190; B5 L178 ("no lock cycle forms").
- **Code:** login's success transaction calls `issueTokens`, which always runs `resetLoginFailures`, an unconditional `UPDATE owner_users` (`service.ts:89`, `repository.ts:305–311`). v0.4 puts a `FOR SHARE` on the same row in front of it.
- **Failure scenario:** the owner taps **Sign in** on the laptop and the phone at once (or double-submits). T1 and T2 both hold `FOR SHARE`. Each one's `UPDATE` needs `FOR NO KEY UPDATE`, which conflicts with the other's share lock. After `deadlock_timeout` (1 s), PostgreSQL aborts one with `40P01`, which reaches the client as `500`. The same happens for a login racing a rotating refresh, or two rotating refreshes from two devices, whenever `lock_notice_at` is set: exactly after a lockout, when the owner is most likely to be signing in everywhere. Test 74 (e) only runs refresh against change-password.
- **Smallest fix:** login and refresh take the owner row `FOR NO KEY UPDATE` instead of `FOR SHARE`. This serialises one owner's logins and refreshes, which is trivial with one owner. It does not conflict with the `owner_refresh_tokens` FK's `KEY SHARE`, and it keeps the M2 ordering. Add to test 74: login ‖ login, and refresh ‖ refresh with a pending notice, both completing without `40P01`.

#### N3. `link-owner-staff` can be used to bypass the own-admin guard
- **Where:** 01b §6.15a steps 3–4 (L766–767), B7 L180, §7.5 L804, tests 72, 95, 97.
- **Failure scenarios:**
  1. **The first link is unchecked.** Step 4 checks qualification only for "a different `staff_id` already set". `null → Y` needs only an active row. If support links the owner to a Cook row (no PIN), `O_before` is always empty and the own-admin guard never fires. The owner can then strip their real row of admin, and only the last-admin guard remains.
  2. **The superset check is vacuous** when the old row qualifies nowhere (`Q_old = ∅ ⊆ anything`). That is exactly the case §6.15a exists for: "correct a link support made to the wrong row". So the re-link check passes for any target, including another non-admin row. Test 95's "re-link to a row with no PIN → exit 1" holds only when X qualifies somewhere, which contradicts the rule as written.
  3. **No tenant lock.** The CLI locks only `owner_users`. A concurrent staff `PATCH` (tenant lock, then `owner_users.staff_id` read **without** a lock, which still returns X) can remove Y's admin after the CLI computed `Q_new` and before it commits. Y is not protected yet and not the last admin, so the write succeeds. Result: the link points at a row that qualifies nowhere (case 1 again).
  4. **A re-link to someone else's qualifying row** (for example the manager's, which qualifies at every branch) moves the guard onto that person. The owner can now strip their own row. When the manager quits, `PATCH is_active:false` on them → `409 OWN_ADMIN_ACCESS`, and the leaver stays in every directory as an admin. Support can re-link back only if the owner's own row still qualifies everywhere. Until then, R14's staff-revoke guarantee fails. The CLI cannot tell the owner's row from another person's, and the runbook's identity check is the only barrier.
- **Smallest fix:** for every link (first or corrective), the target must be a qualifying admin at **every branch of the tenant**. The owner covers every branch (B8), and `issue-registration-code` assigns qualifying admins, so the owner's real row always meets this. That closes cases 1 and 2 and replaces D-15's superset rule with something stricter and simpler. Case 3: the CLI takes `tenants … FOR NO KEY UPDATE` first (B11 order: tenants → `owner_users` → `staff`). Case 4: the CLI prints the target's display name, roles and branches and requires `--confirm-name "<display name>"`. The runbook states that the target must be the row the owner signs in with on the hub, and that a link to another person makes that person impossible to remove. Tests 72, 95 and 97 gain: first link to a non-admin → exit 1; re-link from a non-qualifying row to a non-admin → exit 1.

#### N4. B23 `version` gives false `CONFIG_STALE` in the main edit flow and can give a permanent `409`
- **Where:** B23 L196, §5.3 L587–603, §6.3 L641–643, §6.8 L688–690, §3.6 L274, §8 L822 ("keeping nothing of the stale form").
- **Failure scenarios:**
  1. **PIN set changes the version, and the PIN route returns no version.** `StaffWire` hashes `has_pin` and `pin_set_at`, and `PUT …/pin` returns only `{ staff_id, pin_set_at }`. The owner opens a person (D02), resets the PIN in D01, changes their role and saves. The form's `expected_version` predates the PIN set, so the save gets `409 CONFIG_STALE` and the edits are discarded. The owner's own previous action causes it, every time.
  2. **The responsibilities PUT can be stale forever.** §3.6 keeps the rows of an archived station. The GET leaves them out and hashes only active stations. The PUT compares against "the stored set read inside the transaction" and then "replace[s] the branch's rows". Read literally, the stored set includes archived-station rows, so once any station that has responsibilities is archived, every PUT for that branch returns `409` with no way to clear it. If the version check passed, the replace would delete those rows and break "restoring it brings them back". §6.8 also defines no PUT response, so the page cannot get the new `version` for a second save.
  3. **Canonicalisation is not defined well enough for two code paths to agree.** `canonicalJson` (`packages/domain/src/hash.ts`) sorts object keys but **not arrays**, and it throws on an `undefined` value. `pg` returns `BIGINT` (`pin_set_at`, `left_at`, `archived_at`) as **strings**, and no type parser is set (`db/client.ts`). The spec says only "lists sorted". If the GET builder and the in-transaction builder differ in array order (no sort key is given for `reports_to`, `floors`, `grants`), in `"1730…"` versus `1730…`, or in `null` versus an absent key, every save of that entity is `409` forever.
- **Smallest fix:** (1) The hash covers only the fields the write replaces. Leave `has_pin` and `pin_set_at` out of the staff hash, and have `PUT …/pin` return `StaffWire` anyway. (2) §6.8: the PUT compares and replaces only rows of **active** stations of the branch, the same set the GET hashes, and returns `{ responsibilities, version }`. (3) B23 names **one** wire-builder function used by the GET, the in-transaction compare and the response. All `BIGINT`s go through `Number()`. Nullable fields are always present as `null`. Sort keys are defined: `role_ids`, `branch_ids`, `denied_permissions`, `floor_ids`, `approver_role_ids`, `staff_ids` lexically; `reports_to` and `floors` by `branch_id`; `grants` by `permission`. Test 80 gains: PIN set and then a save from the same response → `200`; archive a station that has responsibilities, then PUT → `200`, and restoring it brings them back; GET version equals the version in the write response for the same row.

### Minor

- **N5. Roll-forward only is documented, not enforced** (B22 L195, §7.4 L801; review 1 M7). `db/migrate.ts` checks checksums only for files it has and ignores stored versions above its own. v1.4 boots on a `0005` database. After the first person is saved without a PIN, its `loadDirectory` returns `pin_hash: null` and every poll fails for that branch's hub (S06 still says "checked in"). v1.4 cannot be changed retroactively. **Fix:** in this release, the runner refuses to start when `schema_migrations` holds a version above its highest file. That protects every later rollback. For v1.4, add an explicit deploy-runbook step ("do not redeploy a build older than 01b").
- **N6. The `default_key` backfill fails silently** (§5.1 L458–467). A default role the owner renamed before the release ("Manager" → "Incharge") gets no key. A role the owner created reusing a default's name gets the key if its ULID is the smallest one left with that name. 02, 03b and 05 migrations `WHERE default_key = …` would then skip the tenant or grant to the wrong role, with no error. B6 makes this dev-only today. **Fix:** after the backfill, a `DO` block raises an exception naming any tenant that lacks one of `owner`, `manager`, `cashier`, `order_taker`, the same "abort loudly" rule as m10. Test 77 gains a renamed-role case.
- **N7. The cloud cannot see which hubs run v2** (B18 a, B19, §7.4, §12.4 "every hub runs v2"). A v1.4 hub applies the additive directory, reports the current versions, gets `304` and shows "Up to date". On that hub, though, `my_stations` (owner-confirmed Q6) and D-6 are not enforced, and only the first approver works. The §12.4 trigger for dropping `approver_role_id` cannot be checked either. **Fix:** the hub sends its directory schema version on the poll (one header), the cloud stores it on `branches`, and S06 shows "Hub needs update" below 2.
- **N8. B19 warns during normal editing** (B19 L192, 01a §6.7b). Every config or directory bump makes the next poll a `200`. An owner who keeps editing (setting up 30 staff, re-pricing the menu) for more than `hub_stale_after_ms` sees "not up to date" on a healthy hub, because `hub_synced_at` moves only on `304`. **Fix:** also set `hub_synced_at` when a poll reports the versions the cloud sent in its previous `200` to that hub. That means storing the sent pair, two columns. Test 67 gains the case.
- **N9. A database error in the JWT guard has no defined result** (00 §6.24a L1208). The guard now runs a query before every owner route. The spec defines only `401` outcomes. If an implementer maps a query failure to `JWT_INVALID`, a slow database signs the owner out (the client tries a refresh, then goes to sign-in). **Fix:** one sentence: a failed guard read is `500` (or `503`), never `401`. The read is outside the route's transaction, so a request that passed the guard just before a change commits finishes. That is acceptable and should be stated.
- **N10. The reset erases the lockout notice** (§6.14 L746 `lock_notice_at = NULL`). If an attacker caused the lock and the owner then asks for a reset for another reason, the owner is never told that 10 failures happened. **Fix:** the reset clears the counters and the lock but keeps `lock_notice_at`, so the next login shows the notice.

## Checked and fine
- **JWT guard performance:** one primary-key read per owner request, single owner, plain `SELECT` with no row locks, so it never waits on a change or refresh. Every `jwt` route already uses the pool, so no route gains a new dependency on the database.
- **Starvation:** `FOR SHARE` readers could in theory starve a waiting exclusive locker. With one owner and a few devices refreshing hourly, that cannot happen in practice. N2's fix (`FOR NO KEY UPDATE`) removes the question.
- **Tokens from before the release:** no `iat_ms` and `password_changed_at` null (no default in `0005`), so they are accepted until the first change or reset, then refused once and refreshed. Refresh tokens from before the release compare against null and are accepted. Correct.
- **ms precision itself:** one cloud instance (D57, 00 §6.22), one clock. Strict `<` handles the token the change issues itself. The defects are the ordering in N1, not precision.
- **Temporary-password expiry and the counter:** a match after expiry is counted on the account and per IP, with the same response and timing as a wrong password. Repeated tries lock the account for 15 min, which is the existing M73 behaviour. Reset clears the lock (but see N10).
- **Dual-written approver:** the CHECK and FK are kept. B14 refuses archiving any approver through the list table, so the column never points at an archived role.
- **The `issue-registration-code` lock order** (tenants → branches insert → `staff_branches` → `owner_users`) against refresh: the CLI waits on the share lock, and refresh waits on nothing the CLI holds.
- 00 v1.5 §6.22–§6.24a and 01a v1.3 §6.0, §6.1, §6.7b match 01b v0.4 text.

## Verdict
**FIX THEN APPROVE.** No redesign. N1 and N2 are security and availability defects in the M1/M2 fix itself: switch to a credential counter and `FOR NO KEY UPDATE`. N3 is a one-rule change to `link-owner-staff` plus the tenant lock. N4 is three sentences in B23 and §6.8. Fix all four before approval. N5–N10 are small spec edits that can go in the same version bump.
