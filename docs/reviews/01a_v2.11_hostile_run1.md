## MAJOR

### M-1 — "Name taken and code taken → `CONFIG_NAME_TAKEN`" contradicts the script the spec writes
**Where:** l. 600 ("`SHORT_CODE_IN_USE` joins group (4) beside R5, checked after the name index"), l. 1182 (§6.14 step (b): the code pre-read runs "after 01c's reference steps and **before the inserts**"), l. 1193 (edge row), l. 1207 (§6.15 pre-read), test 213 (l. 1818, last clause).
**Problem:** the name rule has **no pre-read**: the active-name check is the unique index at the write (`nameTaken('menu_items_active_name', …)` wraps `insertMenuItem` / `updateMenuItem`, `apps/cloud/src/modules/restaurant/service.ts:1513`, `:1935`, mapper `:2221-2227`). A code pre-read placed before the insert therefore answers **`409 SHORT_CODE_IN_USE`** for a body whose name and code are both taken, which is the opposite of the edge row and of test 213. Making the edge row true needs either a new name pre-read (one more statement, and a behaviour change for every item write) or moving the code check after the write. In the race path it is worse: both indexes can fire on the same INSERT and which `23505` Postgres reports depends on index order, so the precedence is not a property of the spec at all.
**Fix:** run the code check **after** the item `INSERT` / `UPDATE` succeeded (name index passed): a pre-read `WHERE short_code = $2 AND archived_at IS NULL AND item_id <> $id` after the write, still inside the transaction, gives the `409` with the holder; the index stays the race backstop. State that the mapper matches `pgError.constraint === 'menu_items_active_short_code'` (the name index keeps its own mapping) and which code wins when the race violates both (name, by checking `menu_items_active_name` first in the catch). Rewrite §6.14 (b) and the §6.15 sentence; keep test 213's clause and add the race-with-both case.

### M-3 — PATCH statement accounting is wrong, and the stored list must be read on every PATCH
**Where:** l. 1207 ("for that it reads the stored list (one statement, only when `companions` is sent)"; "Queries: + 0 – 4 (stored-list read, target read, delete, insert; the code pre-read)"), l. 1013 (audit `before` / `after` carry `companions`), l. 15 ("returned by … every item answer").
**Problem:** (1) the list names **five** statements and says "+ 0 – 4"; a restore adds the restore pre-read on top. (2) Every non-no-op item PATCH writes an audit row whose `before` / `after` "carry `companions`" (l. 1013), and every PATCH answer (no-op included) returns `companions` (l. 15, `itemWire`, `service.ts:1898`, `:1928`): both need the stored list even when the body does not send `companions` — today's code reads goes_with links unconditionally for the same reason (`selectGoesWithOf`, `service.ts:1893`). ### M-6 — OQ-v2.11-7 is a blocker: the `ItemSheet` frame shows companions as pre-filled linked options, the spec delivers separate lines
**Where:** l. 601 (To 02b: "The item sheet shows the hint … from the same list"; "a tap adds an ordinary line"; hide a chip "once the cart already holds a line of that item"), l. 2046 (OQ-7, "Blocks: —").
**Problem:** in `ItemSheet.dc.html` the hint "Half karahi usually: 4 naan" sits **inside the "With it" modifier group**, whose rows are priced options ("Roghni Naan + Rs 70 each", "Raita + Rs 120 each") with quantity steppers pre-set to **4** and **1**, and the sheet total "Add to order · Rs 1,850" = 1 450 + 4 × 70 + 120 includes them — i.e. the frame models naan as a **linked option** (01c V-linked options, `option_child` lines) with a default quantity. `CartSuggest.dc.html` shows the same naan as a **separate cart line** chip.
