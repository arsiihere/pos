## BLOCKER

### B-1 — On a PATCH, the holder read matches the item being patched, so every short-code conflict on an active item answers `CONFIG_NAME_TAKEN`
**Where:** C-2 l. 934 ("after a `23505` the holder read answers by that order, whichever index Postgres reported (01a §6.15)"); C-1 l. 904; 01a §6.14 (b) l. 1243–1244 (the holder read: "the active item with this name, the active member of the variant group with this variant name, and the active item with this code"); 01a §6.15 l. 1280 ("inside the §6.14 (b) savepoint with the same `23505` handling"); 01a test 213 l. 1899; run-1 review M-1 Fix (`docs/reviews/01a_v2.11_hostile_run1.md` l. 27: "`… AND item_id <> $id`"), which the applied fix dropped.
**Problem:** the holder read is written for the `POST`, where the new row does not exist. On a `PATCH` the item row exists and stays **active** after `ROLLBACK TO SAVEPOINT item_write` (the update is undone, the row is not). Take the main case: active "Half karahi" (`name` unchanged) sets `short_code: 'hk'`, which "Full karahi" holds. Postgres reports `menu_items_active_short_code`; the holder read's first subquery, "the active item with this name" = the merged name, finds **Half karahi itself**; by the fixed order name → variant name → code the answer is `409 CONFIG_NAME_TAKEN { entity: 'menu_item', name: 'Half karahi' }`. The same happens through the variant-name subquery for every variant member (the row is its own holder of `(variant_group_id, lower(variant_name))`). So on an active item a code clash is **never** reported as `SHORT_CODE_IN_USE`; the owner app shows "name already used" for its own name, and 01a test 213's PATCH half cannot pass. The restore path is not hit (after the rollback the row is archived again), which is why the POST and restore tests hide it.
**Fix:** in 01a §6.14 (b) and in C-1 / C-2, define the holder read with an exclusion of the written row: each of the three subqueries carries `AND item_id <> $item_id` (on a `POST` the new id, harmless; on a `PATCH` the path item). State it in C-2's "Precedence" bullet, and add to 01a test 213: "active item PATCH `{ short_code: 'hk' }` while another active item holds `hk` → `409 SHORT_CODE_IN_USE` naming the other item (not `CONFIG_NAME_TAKEN`); the same for a variant member".

## MAJOR

### M-1 — The shape of `companions` in write answers is undefined, while the menu read and the write answers share one wire type
**Where:** C-3 l. 896 (menu read: `companions: [{ item_id, name, quantity, status }]`); C-1 l. 904 and 01a §6.14 l. 1248 ("The response `item` carries both fields"); C-2 l. 932 and 01a §6.15 l. 1276 ("every item answer carries `companions`, the no-op answer too"); `packages/events/src/admin/restaurant.ts:546` (`MenuItem`, used by `MenuItemResponse` l. 594 **and** `MenuResponse` l. 597); `apps/cloud/src/modules/restaurant/service.ts:1910` (the no-op answer is `itemWire(before, …)`); 01c §5.4 l. 773 (the wire file named there is `admin/menu-variants.ts`, not the one that holds `MenuItem`).
**Problem:** today one `MenuItem` schema types both the menu page and every item `POST` / `PATCH` answer. v1.5 gives the menu read `{ item_id, name, quantity, status }` and leaves the write answers unspecified. Either (a) the answers carry `{ item_id, quantity }` (the audit shape), so `AdminMenuItem.companions` becomes two shapes under one key and the form that replaces its cached item with the `PATCH` answer loses every "Not suggested" chip after a save; or (b) they carry `name` and `status`, which needs the target rows and an `EXISTS` on `item_routes` — not in the POST's target read (which returns `archived_at`, `sale_unit`, `requires_weighing` only, 01a l. 1241) and not in "+0 – 3" / "+1 always". Neither the shape nor the statement cost is written, and 01c §5.4 points at the wrong wire file.
**Fix:** decide (b): every item answer, the no-op answer included, carries the menu-read shape. On the `PATCH` the "+1 always" stored-list read returns `name` and `status` (one statement, joined, as the menu read's subquery); on the `POST` the answer is built from the target read extended with `name` and the `EXISTS` (+0 statements). Name the schema (`packages/events/src/admin/restaurant.ts` `MenuItem.companions`, `short_code`) in C-1 / C-3 and the audit shape `{ item_id, quantity }` separately. Add a 01a test row: the `PATCH` answer's `companions` equals the menu read's for the same item.

### M-2 — The POST companion check is placed "after the A-13 goes_with check", which the POST does not have; its position among the POST's 422 rules is undefined
**Where:** C-1 l. 904 ("after the reference reads above (and 01a's A-13 goes_with check)"); 01a §6.14 (a) l. 1241 ("After the other reference checks (01c's, then A-13 goes_with)"); `packages/events/src/admin/restaurant.ts:424–468` (`CreateMenuItemBody` has no `goes_with`); `service.ts:1536` (`itemWire(…, [])` "goes_with: §6.15 PATCH only"); `service.ts:1494–1511` (after the reference reads the POST runs `category_mismatch`, the V4 `unit_mismatch`, `weighed_item_stock_draw`, then `too_many_groups`).
**Problem:** the only anchor given for the new `422` does not exist on the `POST`, and the two specs word it differently ("after the reference reads" vs "after the other reference checks"). A body with a bad companion **and** a `category_mismatch` / `unit_mismatch` / `weighed_item_stock_draw` / `too_many_groups` answers either one, depending on where the builder puts the read. 01c fixed one precedence for exactly this kind of collision (Q2, l. 929); the `POST` now has none for the new rule, and test 208 cannot pin it.
**Fix:** drop the A-13 reference from C-1 and 01a §6.14 (a) and state the position: "the companion target read and its `422` run **after** the §3.3 item rows (`category_mismatch`, `unit_mismatch`, `weighed_item_stock_draw`, `too_many_groups`), i.e. last before the insert, mirroring the PATCH where it is the last rule of group (3)". Add to test 208: a body with a bad companion and a `category_mismatch` → `422 category_mismatch`.
