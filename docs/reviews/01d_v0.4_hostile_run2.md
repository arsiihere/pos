## 2. The author's own calls (v0.4 changelog)

1. **`RequestPinFailed`, `checkPin` precheck / `onMismatch` (00 H-3).** Not sound yet. A PIN can still be confirmed without leaving any trace for the correct guess, in three ways (N1). No way to skip a lockout was found: staff lockout is per person across devices; `preRead` failures verify no PIN and count nothing; `checkPin` checks both locks before argon2 and again inside its transaction (`pin.ts:47–54`, `:77–84`).
2. **In-person listing carried to 05.** The data is almost enough. Missing: (a) `RequestPinFailed` has no reader, so "visible per request" is not true until a query or view names it; (b) 05 can join an approval to its money effect only if 04 / 05 effect events carry `alert_id`; (c) the view should also flag answers given on the raising device, which `RequestAnswered.device_id` against the `AlertRaised` envelope `device_id` already supports (m4, N2).
3. **Stale binding, 2 h ruling.** The rule closes the evening-long shelf case down to at most 2 h. It **does** break one normal-service case: a runner who signs in once and then works only from alerts (no command needs a session for them). That runner silently stops being a route at +2 h while the header still says "Alerts: Ali". N6 gives the exact rule, a phone exemption, a visible deadline on the tablet, the extra statement and the tests.
4. **Endpoint count (H-11).** The wording needs fixing (m11): README's "Split a spec that grows above ~30 endpoints" still applies to 00 as a whole. "Hub endpoints added by module specs are counted here" reads as if 01b / 01d command routes count in 00. And the `.apk` route is not "static" in M81's sense, because it checks the device token.
5. **Remaining calls.** The `branch_scope` entry at step 2 adds nobody, and the step-0 shortcut narrows instead of widening (N4). The step on receipts is fine apart from `recordReceipt` (m3). Kiosk / phone alert mode only while signed out is sound; the tablet needs the same rule for its page and a rule against double sounds (m6). Dedupe by `(kind, dedupe_key)` is sound (index, `byDedupeKey`, the ship kinds' keys, test 59).

## 3. Findings

### MAJOR

**N1. MAJOR — §3.3 rule 4, §6.2 `preRead` / `pinCheck` / Processing, C-00 H-3 — the PIN oracle survives, and a correct guess leaves no trace.**
*Problem:* v0.4 makes the response independent of the PIN only for rules 1, 3, 5 and 6, and only before the PIN is checked or inside `precheck`. Anything that fails **after** a match still returns a different answer from `401`, and `checkPin` then resets the staff counter in a second transaction (`pin.ts:108–113`). Three paths:
- (a) **Decision outside the kind's `answers`.** `preRead` runs rules 1, 3, 5, 6 (§3.3 rule 4 (b), §6.2 `preRead`), but the decision check is Processing step (3), inside `onMatch`. Hamza raises a void, then sends `AnswerRequest { method: 'in_person', answerer_staff_id: <manager>, decision: 'accept', pin: X }`. A wrong X gives `401 PIN_INVALID`, counted, with one `RequestPinFailed`. A correct X gives `400 VALIDATION_FAILED`: rollback, counter reset (`pin.ts:113`), no `RequestAnswered`, no `in_person_answer`, nothing recorded. That is a deterministic oracle, one guess per request, and each wrong guess costs one count.
- (b) **`apply` throws after a match.** The requester can make 04's `apply` refuse, for example by getting the order billed before answering. A correct PIN then returns 04's error and a wrong PIN returns `401`. The same applies to the M39 re-check (`route.ts:99`): a requester whose own session ends while argon2 runs gets `SESSION_EXPIRED` instead of `PIN_INVALID`.
- (c) **The precheck race is controlled by the attacker, and `attempts_remaining` reveals it.** The requester can close the request himself with `WithdrawRequest` while argon2 runs. Then `precheck` returns `409` for both PINs (as designed), but a mismatch is counted and a match is not, and the next `401` carries `attempts_remaining` (`pin.ts:106`, `:117`). One known-wrong probe afterwards shows whether X was counted.
*Failure:* Hamza confirms the manager's PIN with path (a) on his own pending void. Nothing records the correct guess. He then signs in as the manager (N2) and approves voids with `method: 'pin'`, which raises no in-person notice. Test 54 passes all the same: it covers only unknown, closed and out-of-range alerts.
*Fix:* (1) Add the decision check to `preRead` and `precheck`. More generally, every rule that can be checked without the PIN runs in both. (2) **Any failure after a PIN match on `method: 'in_person'` notifies the named answerer.** The second transaction that `checkPin` already opens to reset the counter (`pin.ts:113`) also raises an `in_person_answer`-style notice ("Your PIN was used at Hamza's tablet; the answer failed: <code>"). A correct guess then always reaches the person whose PIN it is. (3) When `precheck` fails, count and record nothing about the PIN (the response is already the same for both PINs). This removes the `attempts_remaining` side channel. Tests: (a) `decision: 'accept'` on an approval kind returns `400` before argon2 (spy not called); (b) a correct in-person PIN with a throwing `t_approval.apply` returns the apply error **and** sends a failed-use notice to the named answerer; (c) the answer is withdrawn while argon2 runs (hook, m10), then a wrong PIN leaves `attempts_remaining` unchanged.

**N2. MAJOR — §3.3 "In-person answers are detected", §3.10 `in_person_answer`, §3.5 day close, §3.4.3 — two easy bypasses of the detection: sign in as the approver, or cheat while the approver is off shift.**
*Problem (a):* The controls fire only for `method: 'in_person'`. With a known PIN (shared, shoulder-surfed, or confirmed by N1), a waiter signs in **as the manager** on his own tablet (00 sign-in: roster plus PIN, any tablet) and answers with `method: 'pin'`. `RequestAnswered` says "Imran, pin, Tablet 3". No notice is sent, and the 05 view shows an ordinary PIN approval.
*Problem (b):* The notice is an `info` alert to the answerer's routes. If the manager is off today, they have no route, so the notice goes to their lead "for Imran" (§3.4.3), or to `managers`, which may be Imran again. That case is undefined, see N5. `info` alerts are closed `expired` at day close (§3.5). Inbox history is today-only (§6.7, §12.4). So the notice is never seen by the one person who can say "that was not me", exactly on the day a waiter is most likely to cheat.
*Failure:* Manager Imran is off on Tuesday. Hamza knows his PIN. He raises three voids, approves them "in person" naming Imran (or signs in as Imran), and pockets the cash. Imran's "notices" sit on another device as "for Imran" cards and expire at 23:59. Wednesday shows nothing.
*Fix:* (1) Raise the notice for **every money answer whose `device_id` is the request's raising device** (the `AlertRaised` envelope `device_id`), whatever the method. Signing in as the approver on the requester's own tablet then raises the same notice. Name the kind `approval_on_requester_device` or widen `in_person_answer`. (2) The notice is not expired at day close and closes only on `seen`. The answerer's next sign-in shows it (catch-up), and §12.4 "inbox history beyond the current day" gets an exception for this kind. (3) When the named answerer had no session today, or is marked absent, the notice also goes to `managers` and the 05 view flags the row "answerer not signed in today". (4) §4.3 To 05: the money section flags "approved on the requester's device" and "answerer not on shift". Tests: a sign-in as the approver on the requester's tablet followed by a `pin` answer raises the notice; the notice survives `BusinessDayClosed` and appears at the answerer's next sign-in.

**N3. MAJOR — §6.9 `requests-to-answer`, §6 batch 3 catch-up, §3.4.3 "For rows", §3.5 (no step after 2) — an approver who signs in later never sees the pending request.**
*Problem:* `requests-to-answer` and the `alerts` catch-up list only requests where the person is in `alert_inbox`. A person gets an inbox row only when a step resolves them **and** they have a route at that moment. Without a route, the row is the lead's "for" row ("Ali has no inbox row for it until a later step reaches Ali directly", §3.4.3). The approval tier has no step after 2 (120 s), and requests never expire.
*Failure:* At 15:00 Hamza raises a void while the manager is on a break: signed out, tablet in the office. Steps 0–2 run by 15:02 and find no manager route. At 15:10 the manager signs in. "Requests to answer" is empty, the catch-up has nothing, and no step is left to send. The void waits until Hamza walks over and asks in person. Busy service hits this every time the only approver steps out for more than 2 minutes. The same happens to a second manager who starts the shift after a request was raised.
*Fix:* `requests-to-answer` = open requests (a single statement over `alerts WHERE state = 'open' AND request_json IS NOT NULL`; requests are few) where `can_answer` is true **now** (§3.3 rules 5–6, in memory), plus the inbox rows (informed, "for" rows). The `alerts` catch-up part for a staff socket adds the same "can answer now" requests, and the client re-notifies them once (§8.1, m6). Also keep the spec's 2-statement bound. Test: a request raised with no approver route; the approver signs in after step 2; `requests-to-answer` and the catch-up list it with `can_answer: true`.

**N4. MAJOR — §3.5 approval tier, §3.4 `answerers` / `branch_scope`, §3.3 rule 5, Q3 — `branch_scope` ⊆ `answerers`, so the shortcut narrows step 0 and step 2's branch-scope entry adds nobody.**
*Problem:* `answerers` = everyone who passes rules 5–6 now (§3.4). Branch-scope holders pass rule 6 for every requester ("`branch` covers all", §3.3; G1-9c "branch-scope holders are in range for every request"). So `branch_scope` is a subset of `answerers`. That has three effects:
- The G1-9d shortcut ("no in-range answerer signed in → `branch_scope`") can only fire when no branch-scope holder is signed in either. When it fires, it **removes** the in-range leads from step 0 and keeps only branch-scope people, who are also not signed in. "Signed in" is the active-session read (3), and a lead's Order taker session idles out after 15 min. So at rush, a lead who carries a bound tablet in his pocket, with no current session, is dropped from step 0. He hears it only at step 1 (45 s), even though A9 exists to reach him.
- Step 2's `{ branch_scope, answerer }` entry adds nobody. The real addition at step 2 is `holders_informed` plus the volume step-up.
- The Q3 text "requester the only in-range approver signed in → step 0 goes to the other branch-scope approvers" describes nothing new: they were in `answerers` already.
*Failure:* At 20:30 lead Imran's session has idled out, and his tablet is in his apron (connected, bound, present). The manager is signed out in the office. Hamza raises a void. "No in-range answerer signed in" is true, so step 0 = `branch_scope` = the manager only, who has no route, so the step goes to the manager's lead or to `managers`. Imran's tablet stays silent until 20:30:45.
*Fix:* Pick one and state it. **(Recommended)** Drop the shortcut: step 0 = `answerers` already includes branch scope (G1-9c), so G1-9d is met at t0. Remove the `branch_scope` entry from step 2, or keep it with a note that it changes nothing. Rewrite Q3 / rule 5 as "requester excluded; if `answerers` minus the requester is empty, step 0 has no answerers". *Or*, if the owner wants leads first and managers only at 2 min, define `answerers` at steps 0–1 as "in range **and** not branch scope, when any such person exists", base the shortcut on "has a route" (screen, connected binding, registered route) instead of "signed in", and make the shortcut send step 2's list at once ("skip the waiting steps", G1-9d). Test 20 is rewritten either way: a lead with only a bound tablet gets step 0.

**N5. MAJOR — §3.4.3 "no route → lead", applied to permission-derived sets — off-duty approvers' urgent copies land on duty staff as "for X" cards.**
*Problem:* The no-route fallback applies to every person recipient, including `answerers`, `branch_scope`, `holders_informed`, `managers` and `permission` targets. These sets come from the directory, not from who is working: the owner, a manager on leave, and every order-taker lead with `approve-void` (`my_team`) for other teams. The presence filter (§3.4.1) covers only team and table-team targets.
*Failure:* Every void at step 0 resolves the owner, who is remote with no route. The owner has no lead, so the card goes to `managers`, which is the duty manager. At step 2 every out-of-range lead without a route adds a "for <lead>" informed card on *their* lead's device. The duty manager's tablet now holds "for Owner" and "for Manager B (on leave)" urgent cards, each repeating every 10 s until seen, for every void of the night. If the no-route person is themselves in `managers`, the fallback loops back to them, and the spec does not say what happens then.
*Fix:* The lead fallback applies only to targets meant for people who are working: `person`, `team`, `table_team`, `zone_order_taker`, `requester_lead`, and the raised target of a non-request kind. For `answerers`, `branch_scope`, `holders_informed`, `managers` and `permission`, a person with no route is written in the step's `recipients` with no route (so the receipt view shows "Owner: no route") and gets no "for" copy. The presence filter applies to them too. A fallback that would reach the same person again stops there. Test: an owner and a second manager with no route add no "for" rows; the duty manager gets one card per step.

**N6. MAJOR — §3.4.3 residual risk, §3.7, test 57 — the developer's 2 h ruling is not in the spec, and its plain form silently stops runners.**
*Problem:* v0.4 leaves "a connected shelf tablet of a present person stays a route" (§3.4.3). The developer ruled 2026-11-01: a binding whose person has had no session activity anywhere for 2 h is not a route. Stated only that way, it has three gaps. (1) It does not say what "activity" is or where it is read: read (3) holds only active sessions, while idle-ended sessions keep their real `last_activity_at` in `staff_sessions`. (2) It drops the phone owner binding: an owner who keeps the phone page open without signing in counts as idle. (3) A runner who signs in once at 12:00 and then works only from alerts (Ready-to-serve, carrying food; no command needs a session) stops being a route at 14:00 with no sign on the tablet. The header still says "Alerts: Ali" (G1-13c), and the alerts move to the lead as "for Ali".
*Failure:* Without the rule: Ali leaves at 16:00 and his tablet on the shelf takes his table-team alerts until day close. With the plain rule: Ali works lunch with the tablet in his apron, and from 14:00 he hears nothing while his header still names him.
*Fix — exact rule (§3.4.3 (c), new):* "A **tablet or kiosk** binding is a route only if, in addition to (a) and (b), the bound person's **last session activity** at this branch is within `ALERT_CONSTANTS.binding_route_idle_ms` = 7 200 000 of `now`. Last session activity = the greatest `last_activity_at` over that person's `kind = 'staff'` sessions in `staff_sessions`, active or ended. For active sessions, the in-memory `activity` value is used when it is newer. Phone owner bindings are exempt (rule (a) covers them: a phone has alert mode only while its page is open)." Read: one statement per tick and per raise, `SELECT staff_id, MAX(last_activity_at) FROM staff_sessions WHERE branch_id = ? AND kind = 'staff' AND staff_id IN (<bound staff>) GROUP BY staff_id`. The bound is then tick ≤ 1 + 8 + R + T and raise ≤ 6 + R + T. It needs a 00-table index `staff_sessions (staff_id, last_activity_at)` in `0006` and a C-00 row (same pattern as H-12). **Client:** the tablet header shows "Alerts: Ali · until 14:05", computed from the end of its own last session on that device plus 2 h. A session elsewhere can only make the hub deadline later, so the tablet never shows a deadline later than the hub's. At the deadline it shows "Alerts: Ali — paused, sign in to resume" with one `info` chime. §3.4.3's residual line becomes "a shelf tablet stays a route for at most 2 h after the person's last activity". **Tests (extend 57):** (i) Ali signs in on T at 12:00 and idles out at 12:05; T is connected and Ali present; an alert at 13:59 goes to T, and one at 14:06 goes to the lead with `for_staff_id = Ali`. (ii) Ali signs in on another tablet at 13:00, so at 14:30 T is still a route (activity anywhere). (iii) A `MarkAlertsSeen` on T at 13:50 extends it to 15:50. (iv) A phone owner binding with no session for 3 h, page open, is still a route. (v) Test 35's tick count is unchanged for 1 and 150 due alerts, with the new statement included. (vi) Client: the header shows the deadline, then "paused".

**m10. §10 test 54 race — needs a named hook.** "Answered by someone else while argon2 runs (hook)" needs a hook inside `checkPin` between `verify` and `writer.run` (`pin.ts:70–75`). *Fix:* `testHooks.betweenVerifyAndWriter`, like `betweenGuardAndWriter` (`route.ts:92`). ## 4. Attack summary (what held)

- **Races and restart:** answer vs answer, answer vs close, answer vs withdraw, answer vs tick all hold: one synchronous connection, `writer.run` has no `await` (`writer.ts:54–85`), and the selection inside the transaction is authoritative. `checkPin` awaits argon2 before its `writer.run` (`pin.ts:58–75`). Restart: persisted flags, latest step only, receipts seeded before sockets, bindings exact by `session_id`. Empty tick transactions run every after-commit hook (`writer.ts:90–91`), which is accepted as rare.
- **PIN storage:** `payload_hash` without the PIN (H-9) fits `decide()` (`route.ts:221`) if both callers use the stripped hash. `response_json` holds no PIN. Logs redact `pin` (`server.ts:84`). The queue is online-only (H-10). Holds.
- **Lockouts:** no skip found (see §2 item 1). Locking a manager out with 5 wrong PINs is possible from the sign-in screen today (00 §3.5), so it is not new in 01d. In-person failures are now recorded.
- **Device trust:** revoke / rotate close alert sockets; one alert socket per device with `4409`; the alert-mode payload is lock text only (test 49). A cloned token shows up only as log lines. That is acceptable for the pilot, and 01e device health can surface it.
- **SQLite load:** 01d writes about 1 transaction per second at rush (receipts) plus ticks only when due. The new N6 read and the m5 fix keep the per-transaction statement count fixed. The event-loop pause is measured by test 58.
- **§4.2 contracts:** enough for 02 (handover: `named`, `requester_lead`, typed `apply`), 03a (`registerTick`, `from_value` point, `window_ms`), 04 (`values_schema`, `details_schema`, `close 'overridden'`), 05 (`listOpen`), 01e (`registerRoute`, `recordReceipt` with m3). Gaps: m5, m9, m4.
- **Unlisted changes to other specs:** none found beyond m11 (README budget row) and N6's new 00 index (needs a C-00 row when added).
- **Pilot scope:** nothing to cut. Presence now carries the binding rule, and `details` / `in_person_answer` are anti-cheat.
