## MAJOR

### R2-M-1: "The request expires at day close like every request": 01d requests never expire
**Where:** §3.7a l. 292 ("the request expires at day close like every request (01d)"); §3.7a l. 293 ("an open request is left to its answer or day-close expiry"); test 88 l. 977 ("day close → the open request expires"); 01d v1.3.7 test 122 ("`BusinessDayClosed` expires it").
**Problem:** in 01d, `expires_at_day_close` has no effect on a request kind. Requests survive day close and stay open until they are answered, withdrawn or closed by the owning module. Test 88 therefore cannot pass. An unpaid, un-handed takeaway is not billed, so it stays open across the close (§3.3), and its request stays approvable the next day. Nothing in 02b ever closes the request: not after payment ("No longer needed", l. 293), not after Hand over, not at day close. Managers' inboxes keep stale "Hand over unpaid token N" cards that can still be approved.
**Evidence:** 01d v1.3.7 l. 579 "**No expiry for requests** … Requests survive day close"; l. 797 "sets `expire_due = 1` … on every open **non-request** alert … Requests stay open"; `orders/comp-kind.ts:22-26` ("The flag has no effect on a request kind … `request_json IS NULL`"); `billing/kinds/index.ts:46` ("no effect on a request kind … 05's appender closes them").
**Fix:** drop the expiry claim in §3.7a and test 88, and fix 01d test 122 in the same pass. Then pick a close path, for example: `MarkServed` that hands over the last live line of an order closes its open `hand_over_unpaid:<order_id>` `obsolete` (one `alerts.byDedupeKey`, +1 statement only when the order is takeaway / parking), and `RequestUnpaidHandover` with `needed: false` closes an open one. Or state that it stays open until answered or withdrawn and that an approve after payment is harmless, and test that. Either way, a test must cover a request left open across `BusinessDayClosed`.

### R2-M-2: Parking cannot be raised: `token` is required in `values_schema`, but parking has no token
**Where:** §3.7a l. 289 ("a takeaway / parking token"); §6.4a l. 573–574 (takeaway / parking accepted, `values { order_id, token, due_minor }`, `details.identifier '#<token>'`); §6.12a l. 638 (`token: z.number().int().positive()`); 03b v1.0.16 §3.4 greys "Handed to customer" on **parking** cards and sends `RequestUnpaidHandover` (test 113).
**Problem:** `orders.token` is takeaway only (§5 l. 458; §3.1 O12). A parking request builds `token: null`, the raise's values parse fails, and the command throws 500 inside the transaction. OR-7 says "Hand over unpaid **token** N" and R2 talks about takeaway, yet §3.7a and 03b both extend it to parking. Tests 85–90 have no parking case.
**Fix (OWNER, recommended default: keep parking, as 03b OQ-7 already treats parking like takeaway):** `token: z.number().int().positive().nullable()`; `identifier` = `'#' + token` for takeaway, `'PARKING ' + car_number` for parking (≤ 40); label params to match; a parking case in tests 85 and 87. The alternative is takeaway only: refuse parking in §6.4a and remove parking from §3.7a and from 03b §3.4's greying.

### R2-M-3: One bill, several orders: the approval unlocks only the newest order, so a root + addition token can never be handed over
**Where:** §3.7a l. 290 ("for the token's **newest** order"), l. 291 ("for **that order only**"); §6.16 `bill` row l. 708 (every unbilled row reads the **key's** `due_minor`); §8 l. 837 (Hand over sends the lines "of the order"); test 87 ("that order only"), test 89.
**Problem:** a takeaway root A and its addition B, both unpaid, share one `bill_key`. Both `open-orders` rows read `due` with the same key-wide `due_minor`. The request goes for B, and the approval sets the flag on B only. A stays `due` with `unpaid_handover_approved: false`, so A's Hand over (and the Pass's) stays greyed and the bag cannot go out. The manager also approves `values.due_minor` = the **whole key's** due (`keyBalances(db, [bill_key])`, §6.4a) while the flag lands on one order. Test 89 covers only an addition placed **after** the approval.
**Fix:** approve the group as it stands at the request. `values.order_ids` = the key's unbilled, uncancelled orders at request time, read by the same order statement (`bill_key = ?`, index `orders_bill_key`; still 1). `UnpaidHandoverApproved { order_ids, … }` sets the column on each. Orders added after the approval stay `false` (test 89 unchanged). Add a test: A and B unpaid → request → approve → both rows `true`.

### R2-M-4: `UnpaidHandoverApproved` reaches neither the Pass nor the open-orders refetch
**Where:** §6.19 l. 775 ("audiences as `OrderContactSet`'s order audiences (the placer and the counter devices)"); §6.16 l. 717 (the refetch runs on order frames); 03b v1.0.16 §3.4 l. 207 (the Pass refetches `open-orders` "on the order frames").
**Problem:** `OrderContactSet` goes only to cashier kiosks and the placer's sockets (§6.19 l. 800). The Pass tablet (03b OR-2, Cook session) and other counter devices (03b OQ-14: any device whose profile shows `takeaway`, a phone included) never get the frame. So "Handed to customer" stays greyed after approval until some unrelated frame triggers a refetch. The event is also not added to `ORDER_EVENT_TYPES` (`apps/hub/src/orders/audiences.ts:12-28`) or to the client `ORDER_FRAMES` (`lists/OpenOrders.tsx:29`), as `OrdersUnbilled` was (§3.3 l. 237). There is also no reason for the contact audience: the event carries no contact.
**Fix:** audience = staff sockets and cashier kiosks (the `OrdersBilled` set); add it to `ORDER_EVENT_TYPES` and the client `ORDER_FRAMES`; add a test: the Pass socket gets the frame and its row turns `true` without a reload.

### R2-M-5: §6.4a script contradicts `keyBalances` and the §6.16 `paid` rule
**Where:** §6.4a l. 574–576.
**Problem:** (1) "state not `due` → `{ needed: false }`", but `keyBalances` states are `'none' | 'projected' | 'open' | 'partly_paid'` (05 v1.0.35 §6.2a; 02b §4.1 l. 373). `'due'` is the `open-orders` row value. As written, every request returns `needed: false`. (2) `billed_at` is not checked. §6.16 says `paid` when the order's `billed_at` is set, but §6.4a goes straight to `keyBalances`. For a paid root whose addition is unbilled (same key, 05 #44e), `keyBalances` returns the addition's due, so a request is raised for a paid order. (3) `due_minor = 0` is the only "not needed" case. 05 §6.2a says `due_minor` "can be negative after a reopen that left an overpayment". A negative due then fails `values_schema` (`due_minor … positive()`, l. 638) and throws. (4) Errors list `409 BUSINESS_DAY_NOT_OPEN`, but no step checks the day. (5) `400 VALIDATION_FAILED { path: 'payload.order_id' }` is not the Foundation §6.1 shape that run 1 m-14 fixed (`issues: [{ path, message }]`).
**Fix:** order read → `billed_at` set → `{ needed: false }` → `keyBalances` → `due_minor ≤ 0` → `{ needed: false }`, with no `state` test. Either add a day step (`409 BUSINESS_DAY_NOT_OPEN`, 0 statements, `EngineState`) or drop it from Errors. Write the type refusal as `issues: [{ path: 'order_id', message: 'takeaway_or_parking_only' }]`. Test 86 gains: a paid root with an unpaid addition → `needed: false`; a negative due → `needed: false`.
