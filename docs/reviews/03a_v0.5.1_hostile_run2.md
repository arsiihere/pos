## 3. Attack results by area

### 3.1 Submit sequence (pass 1 → immediates → sync loop), hand-built

- **Capacity 1 (test 98's fixture).** Start state at `t` = 12:01: C was Done early, which frees `[12:01, 12:08)`. A is an older line, 5 min cook, `d(A)` = 12:03, keep = 0. N is a new immediate line, 5 min. The steps:
  - Pass 1 places A at `latestFit(hi = 12:03)`, which is `[12:03, 12:08)`.
  - N runs `earliestFit(12:01)`. `[12:01, 12:06)` conflicts with A, so the next candidate is 12:08 and N lands on `[12:08, 12:13)`.
  - Result: never 2 units on the station; A stays on time; N's `T` = 12:13. The fold, at `recorded_at` = 12:01 + ε with T taken from `OrderPlaced`, gives the same placement. **Correct.**
- **Capacity 2.** At `t` = 12:01, F is COOKING `[12:00, 12:40)` (1 unit). A is older: cook 10, `d` = 12:20, keep = max_early = 1 min, so its fire window is the single point 12:19. N is a new sync line, cook 10, with `T_min` = 12:11. Immediate I: cook 5. The steps:
  - Pass 1 puts A on `[12:19, 12:29)`.
  - I takes `[12:01, 12:06)` (the second unit).
  - The sync loop tries `T` = 12:11, which needs `[12:01, 12:11)`. That overlaps F and I (2 units), so `T` advances by the smallest step to 12:16 (`[12:06, 12:16)`), where it fits. A is untouched.
  - Result: the counts stay ≤ 2 at every boundary. **Correct.**
  - Also noted: with the defaults `max_early_ms = keep = 60 000`, pass 1's first window is a single point, so an older line can move at most 60 s per re-plan. That is fine, but worth knowing when you read #16.
- **The same examples with an unstarted fired line in place of C or F** break the promise. That is finding #1.

### 3.2 `liveEnd` in all four functions

The helper is used consistently in `applyEvent`, `planOrder`, `calculateETA` and `getTickIntents`, so they agree with each other. The problem is the formula itself (#1). `nextDueAt`'s planned-end item makes `fires` due on every pass (#9).

### 3.3 The two D15 exceptions and their slips

Boost and capacity change both re-place frozen lines against fired and COOKING lines, which fixes run-1 #4 and #5 for the stated paths. Gaps:
- The day-open reset path (#13).
- Frozen lines in §3.5.6 (#15).
- How far a frozen line moves (#16).
- "Every displaced order gets a slip" ignores the threshold (#14).
- Out of the box, `slip_threshold_ms` 300 000 is greater than the padding of 180 000 (A-12, S:612). The slip therefore fires 2 min **after** the promise has passed, which contradicts D11's own reason ("so the order taker hears before the padded promise is blown", S:370, g0 D11). I recorded this here rather than as a finding because the values are configuration (v0.3 ruling). I recommend the default `slip_threshold_ms` be ≤ the smallest padding, or a cross-field check `slip_threshold_ms < promise_padding_*_ms` in 01a A-12.

### 3.4 Day-close carry-over, with a checkpoint written later

- The checkpoint `last_seq` and body are consistent when they are written: `writer.lastSeq()` and the state are read in one `setImmediate`, and every commit is whole (`writer.ts:86`).
- Boot step 6's `taken_at < closed_at` works, because step 2 reads both tables.
- The day-close release stays in the close commit, so it is never folded twice.
- Broken: #2 (an abandoned line never exits, so the checkpoint is never written again), #3 (physical emptiness), #11 (frozen lines are switched), #12 (Q14), #19 (the slip raised for a carried order is lost).

### 3.5 `isOrderInEngine`

The pure predicate is correct for present orders and returns false for absent ones. `OrderLinesAdded` re-opens an order across the ms gap, and an absent order throws. Both are consistent with 02's check at `now`. The one hole is #2 (c): an order that never exits makes the predicate true forever.

### 3.6 Slip receiver by order type

A table key always contains `order_type` (S:172), so "a group mixing types" (S:374) cannot happen. The text is harmless. The gap is #17.

### 3.7 Return-line money

The money fields are zeroed, and To 05 states that a return line is never billed. The structural fields are not stated (#18).

### 3.8 `StockAdded` re-plan with batch loads

The forward switch to `stock_program_id` in a hidden load is correct, and frozen or fired loads are left alone. Missing: the reverse switch (#5), and the batch-end signal (#4).

### 3.9 `next_alert_due_at` recompute cost
