## 2. The author's own v0.5 calls

1. **`prepare` inside `checkPin` (§3.3 rule 4 (d), H-3).** The error shape is the same for both PINs, and so are `attempts_remaining` and the lock state. That part holds against the built code: `checkPin` checks both locks before argon2 and again inside its transaction (`pin.ts:47–54`, `:77–84`), and H-3 puts `prepare` after those checks and before the branch at `pin.ts:85`. Two problems remain, both in R1. (a) **Counters:** a `prepare` failure counts nothing, and the attacker controls when `prepare` fails. (b) **Timing:** a match on that path runs a second `writer.run` (`onMatchRefused`, an fsync under `synchronous=FULL`) and a mismatch runs none, so §3.3's claim "nor the timing" is false. **Contract "apply / onWithdraw only read and return drafts":** the contract is right, and the built pipeline already works this way (`handle` returns drafts; `route.ts:125–126` appends them). But nothing enforces it, since `ctx.tx` still has `append` and a writable `db`, and only To 04 says it; To 02 and To 05 mention just `alert_id` (m3).
2. **`answered_on_requester_device`, own routes and inbox only, no day-close expiry, closed on seen.** It can be dodged three ways (R2).
3. **Shortcut, steps 0–1 skipped, step 2 at once; `branch_scope` removed.** The behaviour is sound. When no answerer has a route, everyone who could be told is told at once, the request stays pending, and a late approver now finds it through N3. The removal is complete. Gap: the spec never says how `raise` knows a kind uses the approval tier and which step to jump to (m4).
4. **`lead_fallback`, `expires_at_day_close`; presence filter on permission sets.** The kind fields and their startup checks are sound. Personal notices that never expire also never close for a person who leaves (m12). The presence filter on `answerers` / `managers` makes a long-standing ambiguity matter: is "not ticked" the same as "absent"? (m14)
5. **Kiosk rows, `raiseMany` / `closeMany`, per-transaction cache.** A kiosk row is never a route, but it is still read for receipts, `alert_seen` and the "sent" check. `DevicePaired` carries the device type, so the row need not exist (m6). Batching is sound. The cache needs an invalidation rule (m10), and 03a's tick has no `ctx` to call `raiseMany` with (m5).

## 3. Findings

### MAJOR

**R1. MAJOR — §3.3 rule 4 (d), §6.2 `pinCheck`, C-00 H-3, tests 54 / 60 — a `prepare` failure counts nothing, and the attacker can trigger one on demand, so PIN guessing on that path has no lockout and leaves no record.**
*Problem:* When `prepare` throws, "nothing about the PIN is counted, reset or recorded". `prepare` runs **after** argon2, so the PIN has already been checked. The requester can make `prepare` throw whenever he likes, once `preRead` has passed:
- (a) **M39 path.** Hamza sends `AnswerRequest { method: 'in_person', answerer_staff_id: <manager>, pin: X }` on his own pending void, then logs out while argon2 runs (~100–300 ms; the HTTP handler awaits it, `pin.ts:58–70`). `SessionEnded` bumps the auth generation, so `prepare`'s M39 re-check (`route.ts:98`, `:218–221`) throws `SESSION_EXPIRED` for both PINs. He signs in again (his own PIN, no cost) and repeats. The request stays pending throughout.
- (b) **Withdraw path.** Raise a void, send the guess, send `WithdrawRequest` during argon2 (`409` for both PINs), raise again. Each step is one HTTP call and can be scripted.
- (c) **Refusing `apply`.** A void whose order has meanwhile been billed: 04's `apply` refuses on every answer, while `preRead` (01d rules only) still passes. 01d never closes the request (§3.3, M8), so from billing to day close it is an endpoint for guesses that are never counted.

On every one of these paths the staff lockout (5) and the device lockout (10 per 5 min, `config/schema.ts:6–8`) never move, and no `RequestPinFailed` is written. 10 000 four-digit guesses at the argon2 semaphore's rate take tens of minutes and leave **zero** audit rows. The oracle is timing: only a match opens the second `writer.run` (`onMatchRefused` → `pin_use_failed`, one more fsync plus the raise reads). Repeating a candidate costs nothing, because it is not counted. The attacker ranks candidates by latency, then confirms the top ones on the ordinary sign-in screen, where a hit looks like a normal `SessionStarted`. The single `pin_use_failed` the true hit produced can then be dismissed by signing in as the owner of that PIN (R2 (c)).
*Failure:* At 21:00 the void on T12 has been billed. Waiter Hamza runs a loop from his tablet against that pending void, naming the manager. The lockout never triggers, the 05 view shows no failed attempts, and by 21:40 he has the manager's PIN. From then on, voids approved in the manager's name are indistinguishable from real ones.
*Fix:*
(1) **Count on that path, whatever the PIN.** When `prepare` throws after argon2 (except `IdempotentReplay`, m1), run **one** write transaction for both outcomes. It counts one failure on the staff counter and on the device counter, as a mismatch does, and appends `RequestPinFailed { …, outcome: 'answer_failed', error_code }` (never the PIN). On a match it also raises `pin_use_failed` in that same transaction. The response is the `prepare` error. Both PINs then give the same status, the same `attempts_remaining` delta and the same number of transactions, and guessing is bounded by 00's lockouts again. An honest manager who loses a race pays one counted failure, which the next successful PIN resets.
(2) **Run the PIN-independent body before argon2 as well.** Since `apply` only reads (§3.5), `preRead` can run the whole of `prepare` — rules, `apply`, the raises — read-only on `db` before `checkPin`. A refusal that is decided by state (path (c)) then returns before any PIN is verified. Only real races reach the counted path of (1).
(3) **Tests:** extend test 60. (b′) The requester logs out in `betweenVerifyAndWriter`; a correct PIN and a wrong PIN each increase the staff counter by 1, each write one `RequestPinFailed { outcome: 'answer_failed' }`, and each run exactly one write transaction (writer spy); the correct one also raises `pin_use_failed`. (c′) A `t_approval` whose `apply` always throws returns the apply error from `preRead` with the argon2 spy not called. (d′) The fifth such attempt locks the manager out (`429 PIN_LOCKED_OUT`). Drop the phrase "nor the timing" unless (1) is adopted.

**R2. MAJOR — §3.3 rule 7 and "Answers on the requester's device", §3.10 personal notices, §3.5 `closes_on: 'seen'`, G1-7d — the notice can be dodged by switching devices, and on the raising device the cheater dismisses it himself.**
*Problem:* The notice fires only when `device_id = raised_device_id`, and it closes on the PIN owner's own `seen` "while signed in". Three ways around it, each cheaper than the cheat itself:
- (a) **In person on another device (a regression from v0.4).** v0.4 notified every `in_person` answer. v0.5 notifies only answers on the raising device. Hamza raises the void on tablet A and signs in as himself on tablet B: a person may hold sessions on several devices, one per device (00 M6). From B he answers `method: 'in_person'`, names the manager and enters the PIN. `device_id = B ≠ A`, so there is no notice and `on_requester_device = false`; 05 only shows "in person". G1-7d defines in person as "sent from the requester's device", but §3.3 rule 2 accepts it on any device ("on this device"), so the rule and its detection diverge from the G1 record.
- (b) **Sign in as the approver on another device.** With the PIN known (R1, shared, shoulder-surfed), Hamza signs in as the manager on tablet B or the cashier kiosk and answers `method: 'pin'`. To the system this is an ordinary approval: no notice and no flag. This is run 2's N2 (a) case, which v0.5 closes only on the raising device.
- (c) **On the raising device, the notice lands on the cheater's screen.** Hamza signs in as the manager on tablet A (00 M20 takeover) and answers with `pin`. The notice is raised to the manager's routes, and route 1 (screen) is the manager's staff session on tablet A, the very session Hamza holds. The card appears in front of him, and his `MarkAlertsSeen` is "that person's own seen while signed in", so §3.5 closes it `done`. Closed notices of an earlier day are not listed (§6.7 lists only *open* personal notices of earlier days), so the manager never sees it. `pin_use_failed` is dismissed the same way. Only `RequestAnswered.on_requester_device` in 05's view is left.
*Failure:* The manager is off on Tuesday. Hamza approves three voids for himself: one in person from the spare tablet (a), one signed in as the manager at the kiosk (b), and one signed in as the manager on his own tablet, where he taps the notice away (c). On Wednesday the manager signs in to nothing, and 05's view flags one row at most.
*Fix:*
(1) **In person only on the raising device** (G1-7d): `method: 'in_person'` with `device_id ≠ raised_device_id` → `403 PERMISSION_DENIED { reason: 'in_person_elsewhere' }` from `preRead` (no PIN verified). Every in-person answer is then a notified one. Alternatively, keep any device and raise the notice for every `in_person` answer, as in v0.4, as well as for the raising device.
(2) **A receipt for every money answer.** Raise the personal notice for **every** answer of a `needs_pin: 'always'` kind, not only on the raising device: "You approved the void on T12 · Rs 4 800 · Tablet 5 · 21:03". This is a few dozen a day and doubles as the approver's own record. Flag it "at the requester's device" when `on_requester_device`. If that volume is not wanted, the narrower rule is to notify when the answering session started after the request was raised. That catches (b) when the sign-in is made for the cheat, but not a sign-in made before the raise.
(3) **The notice is not shown to, and cannot be closed from, the session that made the answer.** No `alert` frame or catch-up row goes to the answering `session_id`. A `seen` from that session, or from any session on the answering device within the same business day, is recorded (`AlertSeen`) but does not close the notice.
(4) **A third party sees it.** 05's money section lists every personal notice with its state and who saw it ("seen by Imran on Tablet 3 at 09:12"). A dismissal by someone holding the PIN then shows to whoever reviews the day, since the PIN owner may be the very person being impersonated. Add to §4.3 To 05.
(5) **Tests (extend 55):** in person from a second device → `403 in_person_elsewhere` (or a notice, under the alternative); a sign-in as the approver on the kiosk followed by a `pin` answer on a money kind → notice; a sign-in as the approver on the raising tablet followed by `MarkAlertsSeen` from that session → the notice stays open and appears at the approver's next sign-in on another device.

### MINOR

**m1. §3.10 `pin_use_failed`, H-3 — false alarms on honest races and retries.** `prepare` includes the idempotency re-check. A client retry of the same `command_id` racing the first request (the fast path at `route.ts:81` passes for both; the second's `prepare` throws `IdempotentReplay`) and two managers approving at once (the loser's `prepare` → `409`) both fire `pin_use_failed` with a *correct* PIN on an honest action. Every lost race at rush tells a manager "Your PIN was used … the answer failed", which teaches them to ignore the one notice that matters. *Fix:* `IdempotentReplay` is not a `prepare` failure: return the stored response and do nothing else. For `method: 'pin'` (the PIN owner's own session), a `409 REQUEST_NOT_PENDING` raises nothing. `pin_use_failed` is kept for `in_person`, and for `pin` with any other error.

**m2. §3.3 rule 4 (d), H-3 — `onMatchRefused` failure.** If the second transaction throws (or the hub crashes between the rollback and it), the spec does not say which response is returned. A `500` instead of the `prepare` error would be an oracle. *Fix:* with R1 (1) this becomes one transaction that also does the counting. Otherwise catch and log `onMatchRefused` errors and always return the original `prepare` error.

**m3. §3.5, §4.2, §4.3 To 02 / To 04 / To 05 — the read-only `apply` contract is neither enforced nor stated to every user.** `ctx.tx` keeps `append` and a writable `db` (`writer.ts:62–76`), so an `apply` that appends or writes inside `prepare` would write before the PIN branch, and that write would roll back or commit with the wrong outcome. *Fix:* in `prepare` (and in R1 (2)'s pre-read), pass a `ctx.tx` whose `append` and `onCommit` throw and whose `db.prepare(sql)` throws when `stmt.readonly` is false (better-sqlite3 exposes it). After `apply` returns, assert that every draft's `payload.alert_id === alert.alert_id`, in tests and dev, as a startup-registered check. State both rules in To 02 and To 05 as in To 04. Also state that with `in_person` the effect events carry `actor_id` = the session staff (the requester, 00 §3.7), so 04 / 05 take the approver from `AnswerFacts.answerer_staff_id` / `RequestAnswered`, never from `actor_id`. Test: a `t_approval.apply` that calls `tx.append` fails in `prepare`.

**m4. §3.5 approval tier, §6.1 (6)–(7), §4.2 — the shortcut has no contract for owning modules.** `raise` "applies the G1-9d shortcut for approvals". The spec does not say whether that keys on `right.mode = 'approval'` or on a kind flag, which step is "step 2" for a kind whose steps 04 / 05 write themselves, or what §6.1 (7) returns: it says `[AlertRaised, AttemptSent(step 0)]` always. *Fix:* export `APPROVAL_TIER_STEPS` from `apps/hub/src/alerts/` (built from `ALERT_CONSTANTS`) for 04 / 05 / 02 to use. Define the shortcut as "kinds with `right.mode = 'approval'`: jump to the kind's first `escalation: true` step, writing `StepSkipped 'shortcut'` for every earlier step". §6.1 (7) returns `AttemptSent(0)` or the shortcut drafts.

**m5. §4.2 `raise(ctx, …)` / `raiseMany(ctx, …)` vs `registerTick.intents(tx, state, now)` — a tick has no `ctx`.** 03a must raise Ready-to-serve from its fires tick (To 03a) but gets only `tx`. *Fix:* export `alerts.tickCtx(tx, now)` (actor null, `device_id 'hub'`, `permission` null), or let `raise` take `{ tx, now }`. Test 50's fake kind raises through it.

**m6. §3.7 kiosk row, §5.2 `device_bindings`, §3.6 receipts, §6 batch 3 — the kiosk row is still used.** The row is "never a route", but the receipt rule ("the device's binding in alert mode") records a signed-out kiosk's receipts as `staff_id` = the last cashier. The "sent" check and `alert_seen` ("alert-mode sockets of devices bound to them") also use it. The premise "SessionStarted carries no device type, so the projection still writes a row" is unnecessary: the projection already consumes `DevicePaired`, which carries `device_type` (`packages/events/src/events/hub/DevicePaired.v1.ts:8`). *Fix:* keep a device-type map from `DevicePaired` in the projection and write no row for `cashier_kiosk` / `kds`. Test 65 also checks that a signed-out kiosk receipt has `staff_id = ''`.

**m7. C-00 H-4 — 01d needs to read 00's session-socket list, and no row gives it.** Route 1 (screen), binding rule (a) ("a session socket of that device in the hub's in-memory socket lists"), the shortcut's route test and N3's "`alert_closed` to every connected socket whose person may answer" all need to know which staff and devices hold session sockets. 00's list is private to `registerWs` (`apps/hub/src/ws/server.ts:50`), and H-4 adds only `sendToDevices` / `sendToStaff`. *Fix:* H-4 also adds `ws.connectedSessions() → Array<{ staffId, deviceId, kind }>` (memory, no statement).

**m8. §6.9, §6 batch 3, §8.1 re-notify — earlier days' requests ring at every sign-in.** Requests never expire, and 05 may "keep" some at day close (§4.3). With N3, every approver's catch-up includes them, and the client re-notifies `urgent` items once. Every morning sign-in then starts with urgent tones for last night's requests. *Fix:* re-notify only requests raised in the current business day; older ones are listed without sound and marked "from <date>".

**m9. §3.7 / §8.1 tablet header — "Alerts paused" while the hub still routes.** The tablet computes its deadline from its own last session. Activity elsewhere extends the hub's deadline (test 57 (ii)), so the tablet shows "paused" and then keeps buzzing. *Fix:* the hub sends `binding_route_until` in `alerts_open` and in a small frame whenever it changes (on each tick that routes to the device), and the header uses it.

**m10. §3.5 per-transaction cache — stale reads within one transaction.** The fixed reads are cached per `tx`. A transaction that appends `SessionStarted` / `SessionEnded` / `DeviceRevoked` / `PresenceSet` and then raises (for example a future takeover that raises a handover, or 01e) resolves routes from the pre-append rows. *Fix:* drop the cache entry when the transaction appends any of those event types (the projection apply sees them), and state it.

**m11. Test 43 vs §6 batch 3 — catch-up count.** Test 43 says "1 statement". The text says 2 (inbox / device rows plus the open requests the person may answer, N3). *Fix:* test 43 → 2, and include an open request the socket's person may answer.

**m12. §3.10 personal notices — never closed for a person who leaves.** `expires_at_day_close: false` with `closes_on: 'seen'` means a notice for someone who then leaves the directory stays open forever. It is never purged (retention takes only closed alerts) and stays in `listOpen` / the tick's world. *Fix:* the `no_approver`-style flag on `StaffDirectoryApplied` also closes `obsolete` the open personal notices of people no longer in `staff`, in the tick. Test it.

**m13. §4.2 "`raiseMany` required when a transaction raises more than one alert" vs §6.2.** `AnswerRequest` raises two alerts (`request_result` plus the notice) through `raise`, which §6.2 accepts ("reuses the cached fixed reads, + R + T"). *Fix:* "required when the number of raises depends on data (loops); a fixed small number of `raise` calls is allowed".

**m14. §3.4.1 presence — "absent" is undefined, and since N5 it drops approvers.** "Skip people marked absent" plus "nobody ticked → everyone present" leaves open whether an un-ticked person is absent once someone else has been ticked. Since v0.5 the filter also removes people from `answerers` and `managers`. If "not ticked" means absent, a duty manager who forgot to tick themselves, whose session has idled out, who carries a bound tablet, is dropped from every void's steps, and the tablet stops being a route under §3.4.3 (b). *Fix:* absent = a `presence_today` row with `present = 0`, nothing else. Test 5 covers "someone ticked, X not ticked → X present".

**m15. `docs/stories/01d-g1-decisions.md` G1-9f — record not annotated.** G1-9f still reads "2 min branch-scope approvers", but v0.5 puts branch scope at t0 (G1-9c, N4). *Fix:* append "[01d v0.5 N4: branch scope is in range from t0; 2 min adds the informed holders and the volume step-up]", the same pattern as m1 of run 2.

**m16. §6.2 payload — PIN length 4–8 vs 4–6.** `AnswerRequest.pin` is "string(4–8 digits)", but a PIN is 4–6 digits in 01b v1.3 §3 rule 4 and 00 §6.8 / §6.9, and in the code (`apps/hub/src/auth/staff-session.ts:165`, `admin-session.ts:152`). Graded MINOR: it changes no 00 rule, and a 7–8 digit value can never match; it is only counted as a failure. *Fix:* `pin: /^\d{4,6}$/`; a value outside that pattern → `400` from payload Zod, before `preRead`, so nothing is counted.

## 4. Attack summary (what held)

- **Races and restart:** the authoritative select inside `BEGIN IMMEDIATE`, one synchronous connection, and a `writer.run` with no `await` (`writer.ts:54–85`) still hold for answer vs answer, close, withdraw and tick. The shortcut and the computed requests-to-answer add no new race: the shortcut is decided inside the raising transaction, and the queries are read-only. Restart: flags persisted, latest step only, receipts seeded before sockets.
- **Event leaks:** `AlertRaised` (with `details`) and `pin_use_failed` live on the order stream, but no audience is registered for them. Event frames are filtered per event type (`ws/audience.ts:22–25`), so the requester's tablet never receives a `pin_use_failed` event as an oracle. 02 / 03a must not register a catch-all order-stream audience; this is worth a line in To 02 / To 03a at build time.
- **Lockouts outside R1:** `preRead` failures verify no PIN; both locks are checked before argon2 and again in the transaction; `attempts_remaining` is equal on the `prepare` path. The only gap is R1's "not counted".
- **Device trust:** revoke / rotate close alert sockets; one alert socket per device with `4409`; alert-mode frames carry lock text only; kiosk excluded from H-5.
- **SQLite load:** the tick is ≤ 1 + 8 + R + T, raise ≤ 6 + R + T, and the projection ≤ 2 per event. `requests-to-answer` reads the open requests only (few). The 2 h read is one indexed statement. R1's fix adds one transaction per refused answer, which is rare.
- **§4.2 contracts:** enough for 02 (named, `requester_lead`, `table_team`), 03a (`registerTick`, `raiseMany` once m5 lands), 04 (typed `apply`, `values_schema`, `details_schema`, `close 'overridden'`), 05 (`listOpen`, `closeMany`, `RequestPinFailed`, `on_requester_device`) and 01e (`registerRoute`, `recordReceipt` with `step`). Gaps: m3, m4, m5.
- **Unlisted changes to other specs:** only m7 (an H-4 read export). The in-person fallback is in README R22 ("an in-person PIN fallback that always works"), so 01b B10's "answered on the approver's own device" is the main path, not a contradiction.
- **Pilot scope:** nothing to cut. R2's fix (2) adds no kind, only a wider trigger for the existing notice.

## 5. Order for v0.6

R1 first (it feeds R2: a PIN guessed through R1 is what makes R2 (b) and (c) cheap). Then R2, picking (1) or its alternative and (2) or its narrower form. The MINORs go into the build plan as tasks with the tests named above. No run 4: the developer checks R1 and R2 in v0.6 against this review, then the spec goes to approval with the §4.5 bumps.
