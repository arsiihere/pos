## 2. New findings (introduced by the v0.4 changes)

### N-1 An admin session survives removal from a still-listed device, and the view cannot mask it — MAJOR, TXT

**Where:** 05a §6.4 step 6 ("a **staff** session of someone no longer allowed → end it"; admin sessions end only when the device becomes `everyone`); §3.3a (the mask applies only when the device is `everyone`).

**Problem:** the floor tablet is `listed [manager, Bilal]` and Bilal holds `access-hub-admin` with an admin session bound to the tablet. An edit removes Bilal and the device stays `listed`. Step 6 ends Bilal's staff session only. His admin session stays, and because the device is `listed` the view masks nothing. `requireAdmin` (`guards.ts:239-248`) checks the binding to the device and `hasAdmin`, not the list. So Bilal keeps hub admin until the idle TTL. The §3.5 check runs only at sign-in.

**Fix:**
- Step 6 ends **staff and admin** sessions bound to the device of anyone no longer allowed. This is the same filter `endStaff` already uses (`apply-directory.ts:426`: `kind === 'staff' || kind === 'admin'`).
- Test 9 gains the admin-session case.

### N-2 Test alert, printers and KDS setup need `manage-devices`, which is masked on kiosks and tablets — MAJOR, TXT

**Where:** 05a §5.3 ("What stays: Reports, Day close, **Test alert** …"), §3.6 (`manager` shows "test alert"), M-9.

**Problem:** these all declare or check `manage-devices`, which §3.3 lists as listed-only:
- `SendTestAlert`: `alerts/commands/send-test-alert.ts:79`;
- the printer commands: `print/commands/printer.ts:56`, `station-output.ts:25`, `bill-route.ts:38`;
- `print/routes.ts:111`;
- the KDS commands: `kds/commands/screen.ts:21`, `device-role.ts:35`;
- the queries `kds-config`, `print-queue`, `print-config` and `alert-receipts`.

So on every upgraded kiosk and tablet the test alert, its receipts and the printer and Kitchen screens setup are gone. 01d says test alerts are the installation tool for tablets (01d §3.10 `test_alert`).

**Fix (spec text):**
- §5.3 lists them under "What the upgrade takes away", and drops "Test alert" from "What stays".
- §3.6 `manager` shows "test alert" only where `manage-devices` is unmasked.
- If the owner wants the installer's test alert on shared tablets, that is a new permission, which needs an owner decision. Not proposed here.

### N-3 A downgraded request to an unreachable phone has no fallback — MAJOR, TXT

**Where:** 05a §3.9 rule 1(a) (named to the requester when they are "on ≥ 1 unrevoked listed device"), rule 3 (escalation).

**Problem:** with `right_mode: 'named'`, only the receiver may answer (`targets.ts:519-520`). If the requester's only listed device is a phone with a dead battery or left at home, nobody can answer. Escalation cannot help, because no other person can be "reached". The manager at the counter withdraws, retries and gets the same named request again (rule 1(a) still sees the listed device). So a manager without a working phone cannot void, discount, comp or reopen from the counter at all, while a cashier can (their request goes to approvers).

**Fix:**
- Rule 1(a) applies only when one of the requester's listed devices has an open socket **now**. That fact is in memory: 01d keeps the open sockets per device, and 00 M95 already tracks them. Otherwise apply rule 1(b), the holders.
- Add test 17a: phone not connected → the holders request.

### N-4 The directory-apply profile write does not bump `profile_version` — MINOR, TXT

**Where:** 05a §6.9.

**Problem:** the `DeviceProfileSet { cause: 'directory' }` is written without `profile_version + 1`. An admin's edit form opened before the sync still holds the old version, passes the §6.4 step 2 check, and writes its merged profile, which re-adds the removed person (until the next directory apply).

**Fix:** every `DeviceProfileSet` (cause `directory` and `upgrade` included) writes `profile_version + 1`. State it in §4.2.

### N-5 Upgrade of a non-tablet device that already has a `point_id` — MINOR, TXT

**Where:** 05a §5.3 table; code `kds/commands/device-role.ts:39-44` (`SetDeviceRole` sets a point on any device type today).

**Problem:** a kiosk or phone with a `point_id` gets screens without `pass`, which breaks the §3.6 invariant `pass` ⇔ `point_id`. The upgrade event's `point_id` value is not stated, and every later edit of that device fails `400 { field: 'point_id' }` unless it also clears the point.

**Fix:** the upgrade carries the device's `point_id`, and puts `pass` first whenever it is set, on any hardware. Test 15 covers it.

### N-6 "Every handler reads `resolution.masked`" contradicts "handlers do not change" — MINOR, TXT

**Where:** 05a §3.3a bullets 1 and 2.

**Problem:** seven sites throw their own details: `alert-receipts.ts:99`, `kds-config.ts:35`, `print-queue.ts:44`, `print-config.ts:77`, `print/routes.ts:112`, `credentials.ts:92`, and the audit query. Adding `reason` to each of them changes those handlers.

**Fix (simplest):**
- Only `authorize`, §3.5 and `AnswerRequest` add `reason: 'listed_device_only'`. Other sites keep their details.
- The client takes its text from `GET /queries/session`'s `masked` flag, which it already has.
- Tests 4b and 4c assert `403` only.

### N-7 Recovery route: the press loop, the route group and the envelope device — MINOR, TXT

**Where:** 05a §6.11.

**Problems:**
1. Each press runs `issueAdminBootstrap`, which expires every live token (M72, `auth/bootstrap-tokens.ts:9-44`). While the count is 0, any paired device can keep killing the owner's link. The accepted risk covers requesting a link, not this loop.
2. A route under `/admin/` falls in the `admin` group, which requires an admin session (`guards.ts:196-199, 239`). It must be in the `admin-device-public` group, like `/admin/auth`. "Auth as `/admin/login-roster`" implies this but does not name the group.
3. The event's `device_id` (the caller's device or `'hub'`) is not stated. M72 uses `'hub'` for the CLI.

**Fix:**
- A press while a `recovery` token is live answers `200 { already_issued_until }` and issues no new token. A new one is issued only after the live one expires.
- Name the group.
- `device_id` = the caller's device, so the audit shows where the link was taken.

### N-8 The counter check omits variance sign-off and over-limit petty cash — MINOR, TXT

**Where:** 05a §3.3 "Counter check".

**Problem:** every 05 request kind is `needs_pin: 'always'` (`billing/kinds/index.ts:53`). That includes `shift_variance` and `petty_cash`, whose right is holders of `close-shift-for-others` (05:656-657). Closing and counting a cashier's shift stays at the counter (O-11). The **variance sign-off** it raises, and an over-limit petty cash approval, are money answers, which need a listed device (§3.9 rule 2). This follows the owner's M-1 ruling ("answers … listed device only") but is not said.

**Fix:** one line in §3.3: "Changed: the variance sign-off and petty cash approvals are answered from a listed device." This is not an owner question, because the ruling covers it.

### N-9 A two-person phone emptied by one directory apply becomes an `everyone` phone — NIT, TXT

**Where:** 05a §6.9.

**Problem:** `listed [A, B]` with both removed in one apply → `everyone`, not revoked. That is consistent with the ruling, but a shared phone open to all staff may surprise the owner.

**Fix:** mention it in §6.9 (`needs_review` flags it).

### N-10 Binding code points D-1 should name — NIT, TXT

**Where:** 05a §3.8, D-1.

**Problem:** the binding rule needs three code changes that D-1 does not name:
- The phone tablet-rule needs `alerts/bindings.ts:97-99` (phone sessions skipped today) to change.
- The permanent-row routing should key on `session_id IS NULL`, not on `device_type = 'phone'` (`alerts/routes.ts:115-119`).
- `binding_route_until` is null for every permanent row (01d §3.7 says "always null for a phone").

**Fix:** list the three in D-1.

### N-11 Two folds write `devices.point_id` — NIT, TXT

**Where:** 05a §5.1 and K-1.

**Problem:** the `DeviceProfileSet` fold (in a projection with a `reset`) and `device_roles` (no reset, `kds/device-roles.ts:65-75`) both `UPDATE devices.point_id`. On a projection rebuild their replays are not interleaved, so the older value can win.

**Fix:** after K-1 the `device_roles` fold writes `lane_label` only. Historic `DeviceRoleSet` point values are superseded by the upgrade `DeviceProfileSet`, which carries the current `point_id`.
