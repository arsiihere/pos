## Verdict: REWORK

| Severity | Count |
|---|---|
| BLOCKER | 4 |
| MAJOR | 12 |
| MINOR | 16 |
| NIT | 4 |

The direction is right. Shell around `/staff/`, a native service on the 01d alert-mode socket, no FCM and no downloaded bundle are all sound choices, and the hub side really needs almost nothing. But four things must change before a plan is written:

- **Close codes unpair the tablet.** The spec treats every `4401` and `4403` as "token gone", but the hub also sends them for an auth timeout, a stray frame, a wrong Host header and the guest network. A router reboot or a typing mistake would wipe the token, and the tablet would need a manager to approve it again (B-1).
- **The staff page will not open in the app.** The page needs `device_id` and `device_type`, but in the app the pair page writes nothing to IndexedDB (B-2).
- **The bundled first-run and "hub unreachable" pages cannot do what §3.4 and M-16 say.** Their requests to the hub are blocked (mixed content, no CORS), and the bridge does not reach them once `server.url` is set (B-3).
- **The service is never told whether someone is signed in.** M-8, M-10, M-15 and M-17 all depend on that, and two install-window inputs have no native source either (B-4).

Most MAJORs are Android facts the spec states wrongly or leaves out (lock-task hides notifications, starting the service from the background, the process shared with the WebView, notification permission), plus §4.5 rows that are missing. Four need the owner: M-6, M-8, M-12 and B-1's re-pair rule.

`OD` = needs an **owner decision** (behaviour). `TXT` = a pure spec-text fix.

## BLOCKER

### B-1 Every `4401` and `4403` unpairs the tablet, but the hub sends them for transient and setup faults, and `4409` / `4426` silence it for good — OD + TXT

**Where:** 05b:115-117 (§3.4, "4401/4403 on the alert socket → token cleared natively"), 05b:204 (test 10: "4401 / 4403 clear the token and stop; 4426 stop; 4409 stop"), 05b:79 (M-4, "close codes as 01d").

**Problem:** on the alert-mode path the hub sends `4401` and `4403` for much more than "this token is dead":

- **`4401`:**
  - no `auth` frame within `AUTH_MS` = 5 s (`hub:ws/server.ts:25, 295-299`);
  - a first frame that is not `auth` (`:330-332`);
  - **any** non-`receipt` frame on an alert socket, for example a native bug or a malformed frame (`:426-437`);
  - an unknown token (`:373-376`).
- **`4403`:**
  - a revoked device (`:378-380`);
  - **before the auth frame**, a Host header the hub does not allow (`hub:auth/guards.ts:129-137`);
  - **before the auth frame**, a client on the guest network (`:143-151`).

00 §8.4 already tells these apart. `4403 (before auth)` from the guest network means "Connect to the staff WiFi" (00:1728). `HOST_NOT_ALLOWED` means "Open the hub by its address" (00:1737). Only `4403 (non-guest)` wipes the token (00:1727). The spike code clears on both codes and then sets `want_running = false` (`spike:AlertService.kt:215-219, 226-231`), and 05b copies that.

**`4409` and `4426`** stop the service for good as well (`:220-221`), so neither the watchdog nor a reboot brings it back (`spike:Watchdog.kt:46-48`, `spike:BootReceiver.kt:11-13`). 01d §8.4 says `426 CLIENT_UPGRADE_REQUIRED` "stays the hard trigger" for an update (01d:1739), not a stop.

**Failure:**
- After a router reboot (soak S4) a tablet that rejoins on the guest SSID gets `4403` and loses its token. The same happens to every tablet when the installer types the hub's IP while `advertised_host` is a name. The Host set is the advertised host **or** the IPs, never both, and the header must carry the port (`hub:lib/net.ts:56-63, 66-68`).
- Each wiped tablet needs someone with `manage-devices` at a listed device to approve it again (05a §6.3). A busy restaurant loses alerts on that tablet until then.
- A `4409` from a stray second socket, or from a page whose device type was edited (M-4), leaves the tablet silent with no alarm anywhere.

**Fix:**
- Native rule: on `4401` or `4403`, **do not trust the close code**. Make one authenticated HTTP call (for example `GET /app/android/latest` with the token). Wipe the token only on `401 DEVICE_TOKEN_INVALID` or `403 DEVICE_REVOKED`. On `GUEST_NETWORK_FORBIDDEN` or `HOST_NOT_ALLOWED`, keep the token, show the 00 §8.4 text in the status notification, and back off and retry.
- `4409`: log it and reconnect after a long backoff (60 s). Add a health row "Replaced by another connection" so a cloned token still shows up (01d m4) without silencing the tablet.
- `4426`: trigger `checkForUpdate` and keep retrying.
- Add `1011` and `1000` to the reconnect list (m-4).
- Rewrite test 10 to match. Owner: confirm that "token cleared" happens only after the HTTP check.

### B-2 The staff page cannot start in the app: it needs `device_id` and `device_type`, but M-2 and H-2 store only the token — TXT

**Where:** 05b:77 (M-2: "writes nothing to IndexedDB `pos-device` on the app"; "`readDeviceKey` gains a native branch"), 05b:137 (§4.2: only `getDeviceToken`), 05b:154 (H-2: `setDeviceToken` "instead of writing IndexedDB"), 05b:193 (test 1: only `readDeviceKey('token')`).

**Problem:**
- The staff entry reads three keys: `readDeviceKey('token')`, `('device_id')` and `('device_type')`. If any is missing it renders **PairAgain** ("This screen must be paired again") (`client:features/staff/main.tsx:30-34`).
- The pair page writes all three on approval (`hub:auth/pair-page.ts:216-218`). Its resume path reads `device_type` (`:131-133`).
- Under H-2 the app's pair page writes none of them, and `PosNative` has no id or type.
- The same pattern breaks the unpair path. `wipeDeviceKeys` (`client:api/hub-admin.ts:108`, called from `StaffApp.tsx:461` and `orders/queue/enqueue.ts:44`) has no native branch in D-2. A page that sees `DEVICE_REVOKED` would wipe nothing native.
- Two hub-served admin pages read `pos-device` directly with inline scripts: `/admin` (`hub:admin/page.ts:51`) and `/admin/approve` (`hub:commands/approve-pairing-request.ts:52`). On an O-5 approver tablet these show "Open this on a paired admin device". 05b §3.3 cites the spike finding "admin routes need the device token next to `X-Admin-Session`" (05b:101) but nothing in §8 deals with it.

**Failure:** after an approval, every tablet lands on "This screen must be paired again" and loops back to `/pair`. Test 14 fails on the first run.

**Fix:**
- Choose one of two options:
  - (a) keep `device_id` and `device_type` (not secrets) in IndexedDB as today, and only the token in native storage;
  - (b) `PosNative.getDevice()` returns `{ token, device_id, device_type }`, and every reader of `pos-device` gets a native branch.
- With (b), list every reader: `readDeviceKey`, `wipeDeviceKeys`, `admin/page.ts`, `/admin/approve`, the pair page's `readKey` and `resumePaired`.
- Extend test 1 to the three keys and the wipe.

### B-3 The bundled first-run and "hub unreachable" pages cannot reach the hub, and once `server.url` is set they have no bridge — TXT

**Where:** 05b:107-110 (§3.4: first-run page, `GET /health ok`), 05b:91 (M-16: the bundled page "retries `GET /health` every 5 s", "Change hub address" with a confirm), 05b:179, 05b:182 (§8 items 1 and 4), 05b:76 (M-1).

**Problem:**
1. **Origin.** The bundled pages are served from `androidScheme` `https` on host `localhost` by default (`cap:CapConfig.java:38-39`). A `fetch('http://<hub>/health')` from `https://localhost` is mixed content, and `allowMixedContent` is `false` by default (`cap:CapConfig.java:46`; `cap:Bridge.java:594-596`).
2. **CORS.** The request is also cross-origin. `/health` is in route group `health`, which is not in `CORS_GROUPS` (`hub:server.ts:272, 288-295`), and `cors_origins` defaults to `http://localhost` only (`hub:config/schema.ts:20`). So the page cannot read the answer, and the "Not a POS hub" check is impossible. O-10's "no CORS" holds only for the hub page.
3. **No bridge once `server.url` is set.**
   - The document-start bridge is added for **the app URL's origin only** (`cap:Bridge.java:266-269`), which M-1 makes the hub.
   - The only built-in way to show a bundled page after a failed load is `server.errorPath`. It loads `<scheme>://localhost/<errorPath>` (`cap:Bridge.java:553-563`; `cap:BridgeWebViewClient.java:55-58, 85-88`), a different origin with no bridge on the modern-WebView path.
   - So the M-16 page cannot call `PosNative.setHubUrl`, `getHubUrl` or `info()`. A JS retry from it fails for reasons 1 and 2.
4. **No mechanism.** 05b never says how the app switches to the bundled page when the hub is down (`errorPath`? a native probe before `load()`?). It also never says what happens when the hub stops **after** the page loaded and Android later recreates the activity.
5. **Blocked on purpose.** The 00 §8.1 workaround (`androidScheme: 'http'`, 00:1675) is not stated in 05b. Even with it, the CORS problem stays: `/health` is not a CORS route.

**Failure:**
- The first run never gets past "Hub address".
- A tablet that boots while the hub is down shows a WebView error or a bridge-less page that cannot change its address.
- Test 17 cannot pass.

**Fix:**
- Do the reachability check natively. Add `PosNative.probeHub({ url }) → { ok, status, provisioned, reason }`, an OkHttp `GET /health` that requires `status: 'ready'` and `provisioned: true` (`hub:lib/health.ts:19-33`). It maps `HOST_NOT_ALLOWED` to "Open the hub by its address" (m-6).
- Decide in `MainActivity` **before** `super.onCreate`: no address, or the probe fails → `config` without `server.url` (bundled page, bridge on `localhost`); probe OK → `server.url`. Use `recreate()` to switch either way.
- For a hub lost after load, add a `WebViewListener.onReceivedError` on the main frame that recreates into the bundled page.
- State the scheme (`http` or `https`) of the bundled origin, and that the bundled pages never call the hub from JS.

### B-4 The service is never told whether someone is signed in, but M-8, M-10, M-15 and M-17 depend on it; the install window has no native inputs — TXT

**Where:**
- 05b:83 (M-8: "Signed out … the service notifies alone");
- 05b:85 (M-10: "Urgent repeat in native while signed out");
- 05b:90 (M-15: install "only when no session is signed in, the business day is closed, or in the M66 maintenance hour");
- 05b:92 (M-17: lock task "when signed out");
- 05b:132-146 (§4.2 has no method for it);
- 05b:199 (test 7: "Update decision (pure, 01d §8.4)" is a **Vitest** test).

**Problem:**
- The alert-mode socket carries no session state (01d:710), and `PosNative` has no `setSession` call. So the service cannot tell "signed in, page paused" from "signed out" (M-8, M-10). It also cannot apply the first install window.
- "Business day closed": the alert socket gets no events (01d:710), and the page itself does not know when nobody is signed in.
- "M66 maintenance hour" is a hub setting in hub OS local time (00:418, `setMaintenanceHour`). The tablet knows neither the hour nor the hub's zone.
- 9b put the decision in JS (`app-update.ts`, pure; `docs/plans/01d-tablet-plan.md:30`), and test 7 is still a JS test. M-15, by contrast, describes a native client ("after each reconnect and hourly"). The two layers are mixed.

**Failure:** a builder has to invent the native signal, or the decision gets built in two places. M-15's "only when no session is signed in" cannot be checked natively. A tablet whose WebView is paused (screen off) never installs if the page decides.

**Fix:**
- Add `PosNative.setSession({ signed_in: boolean, staff_id?: string })`. The page calls it on every session change. Native keeps it in memory only; a process restart means signed out, which matches "session token in memory only" (00:1678).
- Decide where the install window lives. One option: the page computes `install_allowed` from data it has (session, `pos-hub-now-ms` meta, a new `maintenance_hour` / `day_open` field on `/health` or the page meta) and passes it to `checkForUpdate({ install_allowed })`. Then test 7 tests the JS that actually decides.
- Or move the window into native and drop test 7 from the gate. Either way, add the needed hub fields as an H-row.

## MAJOR

### M-1 `server.url = <hub>/staff/` puts a path into the bridge's allowed-origin list, so the bridge falls back to an interface open to every frame — TXT

**Where:** 05b:76 (M-1), 05b:237 (§11 step 1: "the server URL is added to the bridge's allowed origins (`Bridge.java:241`)", given as proof that it works).

**Problem:**
- `setAllowedOriginRules` adds `getServerUrl()` **as is**, path included (`cap:Bridge.java:241-243`). `MessageHandler` passes that set to `WebViewCompat.addWebMessageListener` (`cap:MessageHandler.java:26-38`).
- Under the androidx.webkit contract an origin rule is `scheme://host[:port]` with no path, and an invalid rule throws `IllegalArgumentException`. The `catch` then uses `webView.addJavascriptInterface(this, "androidBridge")` (`:37-41`). That interface has no origin check and no main-frame check, so any frame of any origin in the WebView can call `PosNative`.
- The same file shows that Capacitor knows the origin must have no path: the document-start script strips the path (`cap:Bridge.java:267`).
- `allowNavigation` with the hub host is not needed: same-host navigation is always allowed (`cap:Bridge.java:413-416`). `HostMask` matches the host only, so an entry `192.168.1.10:3000` would never match.

**Failure:** the plugin's main-frame and origin guard is silently lost. Any iframe the hub page ever renders, or an injected cross-origin frame (M-2), can read the token. Nobody notices on the device, because the bridge still "works".

**Fix:**
- `server.url = http://<host>:<port>` (origin only) and `server.appStartPath` / `Builder.setStartPath("/staff/")` (`cap:CapConfig.java:252, 639`; `cap:Bridge.java:647-650`). No `allowNavigation`.
- Add to §11 step 1's device check: confirm in logcat that the "Invalid url, using fallback" line does not appear and that `addWebMessageListener` did not throw.

### M-2 `PosNative` is open to every page on a cleartext hub origin, including `setHubUrl`, `setDeviceToken`, `clearDeviceToken` and `exitLockTask` — OD

**Where:** 05b:132-146 (§4.2), 05b:172 (§7 Security), 05b:77 (M-2 "Prevents: … the token readable from WebView storage").

**Problem:**
- The bridge is injected into **every** document of the hub origin: `/staff/`, `/kds/`, `/pair`, `/admin/*`, `/admin/approve`, `/setup`.
- The hub is plain HTTP on the LAN (05b:172). Anyone on the LAN who can ARP-spoof the hub can inject script into those pages. That attacker gets:
  - `getDeviceToken()`, which M-2 says it protects. The protection is cosmetic, since the token is in page memory and in every `Authorization` header anyway.
  - `setHubUrl()`, which moves the tablet **for good** to a rogue "hub" that collects PINs.
  - `clearDeviceToken()`, which unpairs every tablet at once.
  - `exitLockTask()`, which lets staff out of the kiosk.
- None of this is in §7. The APK path is safe only because Android requires the same signing key on update. §7 should say that, since `sha256` comes from the same unauthenticated channel (05b:90).

**Fix:**
- Per-method origin and path checks in the plugin, using `bridge.getWebView().getUrl()`:
  - `setHubUrl` / `getHubUrl`: only from the bundled origin;
  - `setDeviceToken`: only from `/pair`;
  - `clearDeviceToken`: only after native confirms the revoke (B-1);
  - `exitLockTask`: only with a native confirm, or never from the page (OQ-2's "manager PIN later").
- State in §7 that APK integrity rests on Android's same-signer check and the release key, and that `sha256` only catches a corrupt download.
- Owner: accept the residual risk that LAN script injection can read the token (same as today's browsers).

### M-3 Cleartext, the scheme and the version header are left out, and 00 §8.1 contradicts the build; there is no §4.5 row for 00 §8.1 — TXT

**Where:** 05b:172 ("cleartext HTTP on the LAN as every client today"), 05b:148-158 (§4.5), 05b:9.

**Problem:**

- Both the WebView and OkHttp follow the cleartext policy (`ws://`), so the choice matters for M-4 as well as M-1.
- 00 §8.1 also says:

The foundation's reason for the header is "the Capacitor app is the only client that can be older than the hub (its assets are bundled on the device)" (F:1546), which O-10 makes false.
  - "Admin screens in the tablet app" (00:1680); see B-2.
- None of these 00 lines has a §4.5 row. F-1 does not touch F:1546 or the command-queue lines (F:1350, F:1715). `CLAUDE.md`'s stack row (`CLAUDE.md:18`) has the same Android text as F §1, and F-1 does not list it.

**Fix:**
- New row **H-3** against 00 §8.1:
  - transport = a global cleartext permit (the owner accepts the LAN risk) and a bundled-page scheme per B-3;
  - pairing per 05a / 05b;
  - token storage = 05b M-2;
  - headers: the hub page sends what the browser page sends; `X-Client-Version` only from native (OkHttp) calls, with its meaning restated;
  - admin screens per B-2.
- Extend F-1 to F:1546 and F:1715, plus `CLAUDE.md`'s stack row.

### M-4 The "page never opens alert mode" check keys on `device_type`, which 05a lets the approver change — TXT

**Where:** 05b:45 ("The shared client already checks the device type"), 05b:154 (H-2 sends `hardware_hint: 'tablet'`).

**Problem:**

- Add a test.

### M-5 Native notifications have no text: alert-mode frames carry i18n keys, and the silent, outcome and earlier-day rules live only in the web client — TXT

**Where:** 05b:27 (rule 2), 05b:84 (M-9), 05b:85, 05b:86 (M-11 "shows the lock text").

**Problem:**
- `lock` is `{ kind_label_key, table_code, point_code, requester_name, device_name? }` (`hub:alerts/ws-frames.ts:303-311`). The text is made on the client from the `EN` / `UR` tables (01d §3.12).
- The spike proves it: the first live lock line was "Arif · spike-tablet-a · **alert.test_alert.lock**" (spike `NOTES.md:12`).
- Native also needs three rules that today live only in the web client:
  - the hand-kept `SILENT_KINDS` (lock views carry no `silent`, AD-23; 01d:1693);
  - the outcome chime for `request_result` (01d:1705);
  - "earlier business day → no sound" (BF-4, 01d:1700). `alerts_open` rows carry no `from_business_day` (`hub:alerts/alert-sockets.ts:205-207`).
- 05b names none of these.

**Fix:**
- Pick one source of text:
  - (a) the hub adds a rendered `lock_text` in the device's language to alert-mode frames (an additive 01d field; a D-row and a version bump);

### M-6 Urgent repeat: a signed-in tablet with its screen off rings once, a restarted service never resumes the repeat, and the always-on and escalation rules are missing — OD

**Where:** 05b:83 (M-8), 05b:85 (M-10, "While signed in the page owns the repeat"), 05b:82 (M-7).

**Problem:**
1. 01d §8.2 hands the alert to the service when the page "reports nothing within 1 s (screen off, WebView paused)" (01d:1717). That is the common signed-in case at night: the manager is signed in and the screen is off. M-10 still leaves the repeat to the page, whose timers are paused or throttled in the background (Chromium hidden-page throttling; Capacitor's Cordova pause path, `cap:Bridge.java:1370-1380`). Nothing repeats every 10 s.
2. After a process restart (S5, B-1's reconnect, an APK install), `alerts_open` replays the unseen urgent alert. M-7's persisted dedupe then "posts nothing", so the repeat is never re-armed. 01d:1700 says "the urgent 10 s repeat then resumes".
3. 01d §8.3: on always-on screens (point tablets) "one sound per step, then a badge only" (01d:1730). M-10 repeats every 10 s on any signed-out tablet. A Pass tablet with an `everyone` profile (05a §5.3) would ring every 10 s.
4. The escalation step drops to the 2-min reminder with one volume step-up (01d:1726, 1732). M-10 does not say this.

**Fix:**
- Rule: **whoever posted the notification owns the repeat.** If the page reported the pair within 1 s, the page owns it. Otherwise the service does, signed in or not, until `alert_seen` or `alert_closed`.
- Keep a persisted set of "open urgent alerts unseen" next to the dedupe keys, so a restart re-arms the repeat without a second first-ring.
- Apply the always-on rule by device: the service needs `point_id`, from `info` or `setSession`, or from a frame field.
- Add the escalation step-up.
- Tests 12 and 15 gain these cases.

### M-7 Starting the service from the background on Android 12–15, and notification permission on 13+, are not covered — TXT

**Where:** 05b:81 (M-6: "`setAndAllowWhileIdle` when exact alarms are refused … restarts the service"; "2 s after `onTaskRemoved`"), 05b:92, 05b:107-118 (§3.4 first run).

**Problem:**
- From Android 12 a foreground-service start from the background is refused unless an exemption applies. The ones that matter here:
  - an exact alarm fired for an app allowed to use exact alarms;
  - the battery-optimisation allowlist;
  - device owner;
  - `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED`.
- **The inexact `setAndAllowWhileIdle` fallback is not an exemption.** So on a non-device-owner unit without the battery exemption, the watchdog's `startForegroundService` throws `ForegroundServiceStartNotAllowedException`. The spike only logs it (`spike:Watchdog.kt:49-54`), and the spike's own notes record the refusal (spike `NOTES.md:9`).
- On Android 14+, `SCHEDULE_EXACT_ALARM` is **denied by default** for new installs that target 33+. The spike targets SDK 36 (spike `NOTES.md:5`) and declares only `SCHEDULE_EXACT_ALARM` (`AndroidManifest.xml:16`). So the fallback is the **normal** path on a fresh Android 14 tablet.
- **POST_NOTIFICATIONS** is a runtime permission on Android 13+. §3.4 has no step that asks for it, and test 14 does not check it. Without it no alert notification shows; the foreground-service notification is hidden too.
- The pilot model is TBD (O-8), and the only unit tested runs Android 11 (05b:98), where none of this applies.

**Fix:**
- Declare `USE_EXACT_ALARM` (API 33+, granted at install; the Play policy does not apply to a sideloaded app) as well as `SCHEDULE_EXACT_ALARM` for 31–32.
- State the exemption M-6 relies on. Make the battery exemption a **hard** first-run step on non-device-owner units.
- First run: request `POST_NOTIFICATIONS` (13+). On device owner, grant it with `DevicePolicyManager.setPermissionGrantState`.
- M-18 gains a row "can start in background", from `canScheduleExactAlarms()` and `isIgnoringBatteryOptimizations()`.
- §10.3 runs on one Android 14+ unit at least.

### M-8 Lock-task mode hides notifications and the status bar by default, exactly when the service is the only one notifying — OD

**Where:** 05b:92 (M-17: "starts lock-task mode when signed out on a `everyone` device; status bar locked"), 05b:256 (OQ-2: "Lock (staff cannot wander off)"), 05b:93 (M-18 "Fix" buttons).

**Problem:**
- With the default lock-task features (`LOCK_TASK_FEATURE_NONE`), the system shows no notification icons, no heads-up notifications and no shade. `LOCK_TASK_FEATURE_NOTIFICATIONS` turns them back on. M-17 locks the tablet only when it is **signed out**, which is when the service notifies alone (M-8). The signed-out page also shows no banners (01d:1693). So in lock task an alert rings at most: no banner on screen.
- M-18's "Fix" buttons open system Settings, a different package. Lock task blocks it unless Settings is allowlisted.
- "Lock when signed out" also means signed-in staff can leave the app, which is the opposite of OQ-2's reason.
- On an approver tablet (O-5, `listed`), M-17 never locks. 05b does not say whether its status bar is locked.

**Fix:**
- `setLockTaskFeatures(NOTIFICATIONS | KEYGUARD | GLOBAL_ACTIONS?)`.
- Owner: lock **always** on `everyone` tablets (signed in too), with the manager-PIN exit deferred as OQ-2 says, or confirm that signed-in exit is fine.
- Fix buttons: call `exitLockTask` first, or allowlist `com.android.settings` with a timeout.
- Add tests: in §10.3 test 20, a signed-out locked tablet shows the heads-up banner and the FSI.

### M-9 APK update: nothing restarts the service after the self-install, `4426` stops instead of updating, and the install permission is missing — TXT

**Where:** 05b:90 (M-15), 05b:81 (M-6 names boot and swipe only), 05b:204 (4426 stop), 05b:217 (test 19: "alerts come back after the install").

**Problem:**
- Installing an update of your own package kills its process, the service included. The spike restarts on `MY_PACKAGE_REPLACED` (`BootReceiver`, spike `AndroidManifest.xml:60-68`), but 05b names only boot and `onTaskRemoved` (05b:81). So test 19's "alerts come back" has no stated mechanism.
- `4426` → stop (05b:204) contradicts 01d §8.4 "`426` stays the hard trigger" (01d:1739).
- `PackageInstaller` sessions need `REQUEST_INSTALL_PACKAGES` in the manifest (API 26+). The spike does not declare it. The non-device-owner path also needs the user to allow "Install unknown apps" for the app; neither the checklist (§8.5) nor M-18 says so.
- Android 12+ (`setRequireUserAction`) is not mentioned for the non-device-owner path.

**Fix:**
- M-6 / M-15: `MY_PACKAGE_REPLACED` re-arms the watchdog and starts the service (an exempt start). `want_running` survives the update.
- `4426` → `checkForUpdate`, keep reconnecting.
- Declare `REQUEST_INSTALL_PACKAGES`. Add an M-18 row "can install updates" (`canRequestPackageInstalls()`) and a checklist line.

### M-10 The alert service shares a process with the WebView, so a renderer crash or page OOM kills the alerts — TXT

**Where:** 05b:27 (rule 2: "Alerts never depend on the page"), 05b:79.

**Problem:**
- Capacitor's `onRenderProcessGone` returns `false` unless a listener says otherwise (`cap:BridgeWebViewClient.java:92-103`). With `false`, Android kills the **app process**.
- The spike declares `AlertService` with no `android:process` (spike `AndroidManifest.xml:52-58`), so the service dies with the WebView.
- A heavy React page on a cheap tablet is the most likely OOM candidate. After the kill, recovery waits for `START_STICKY` (OEM-throttled) or the 10-min watchdog (M-7).

**Fix:**
- Run `AlertService`, the watchdog receiver and the boot receiver in `android:process=":alerts"`. The plugin then talks to the service across processes (a bound `Messenger`, or broadcasts). M-8's 1 s `reportShown` window must survive that hop, so measure it.
- Add a `WebViewListener.onRenderProcessGone` → return `true` and recreate the activity.
- S-test: kill the renderer (`chrome://crash` in a debug build) while an urgent alert repeats; the repeat continues.

### M-11 Revoke and unpair have no native-to-page channel: the signed-out page never learns, and the page's wipe skips native — TXT

**Where:** 05b:115-117 (§3.4: "token cleared natively → WebView → `<hub>/pair`"), 05b:146 ("Events to the page: none in v1"), 05b:156 (D-2), 05b:219 (test 21).

- The 01d tablet header gap (AD-T42-1–3, 01d:730: "Closing it needs an additive frame or field … or 9b") is also left open. 05b replaces 9b, but the service's `binding_route_until` never reaches the page.

**Fix:**

- D-2 gains the `wipeDeviceKeys` native branch.
- Either close AD-T42 with the event or carry it explicitly in §12.4.

### M-12 The staff-build reload reaches past the tablet: wrong hash on `/kds/`, no reload on an always-signed-in kiosk, and old pages kept past `ship-client`'s own guarantee — OD
