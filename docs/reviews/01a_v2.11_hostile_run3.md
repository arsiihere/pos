## New findings

### R3-B-1 — Archiving a routing-only Pass strands work (OWNER)

**Location** — PT-6 l. 158, §6.9a l. 1293 and §10.5l test 220 l. 2024.

**Problem and evidence** — PT-6 permits archiving a point whenever no active station names it as the default, and freezes existing lines on that point. With Main as station default and TA as the unique takeaway match, the archive returns 200 even with a live line at TA. After sync, `livePoint` throws `POINT_NOT_FOUND` for TA, blocking Ready and Handover (`apps/hub/src/kds/commands/ready.ts:33–35,252`, `apps/hub/src/kds/commands/handover.ts:126`). A served TA line still eligible for return can also produce new work at the archived point (`apps/hub/src/orders/commands/return-to-kitchen.ts:129–136,215–222`; 03b test 130 l. 799). The cloud guard checks station rows only (`restaurant/service.ts:1051–1055`).

**Fix** — Owner decision on retiring a Pass while its orders remain actionable. Default for the pilot: keep the Pass active, move station defaults off it, and set it to delivery-only to stop new pilot routing. Confirm the hub has applied that version, then keep the Pass and its device operational until its live work and eligibility for returns have cleared. Require explicit operator confirmation of that sequence before allowing the owner archive action for a routing-only Pass. Pin both live and returnable cases in tests 220/130. Preserve the accepted rule that existing lines keep their point.

### R3-M-2 — Routing edits leave the optimistic-lock token unchanged

**Location** — PT-2 l. 154, §6.9a ll. 1291–1293 and §10.5l test 220 l. 2024.

**Problem and evidence** — `expected_version` is checked under the point lock, but `toPointWire` hashes point ID, name, sort and archived state only (`restaurant/service.ts:1037–1050`, `restaurant/versions.ts:5–19`). With two editors on version V, a routing-only save leaves V unchanged, so the second editor can overwrite it with another routing-only save. The current test checks the branch bump, never the point token.

**Fix** — Add the canonical sorted explicit set to the R30 hash input. Omit the hash member for legacy SQL `NULL` so all-existing rows retain their old tokens. Keep an explicit four-element set distinct from `'all'` in both the token and the no-op comparison. Test a changed token after a set edit, the same token after a reordered no-op, and `409 CONFIG_STALE { entity: 'point', id }` for the second writer.

### R3-M-3 — A pre-release create replay breaks on the added field

**Location** — PT-2 l. 154, §6.9a ll. 1291–1293 and §10.5l test 220 l. 2024.

**Problem and evidence** — The create hashes the parsed body and stores the success body for replay (`restaurant/service.ts:988–990,1019`, `apps/cloud/src/lib/idempotency.ts:60–62,80–105`). Adding a Zod default of `'all'` to an omitted request member changes the pre-release hash and yields `IDEMPOTENCY_KEY_MISMATCH` for the same request. Preserving the hash alone leaves old successful bodies missing the new required member of `PointResponse`, used by the route serializer (`packages/events/src/admin/restaurant.ts:207–213,230–247`, `restaurant/routes.ts:235`).

**Fix** — Keep an omitted member absent in the parsed/hash input, default at persistence, and add `'all'` in memory when serializing a legacy replay body. Preserve its original token and result and avoid a row reread. Seed a pre-release key/hash/body in test 220, retry with the same name and omitted types, and assert replayed 201 with `'all'`, zero new writes and no version bump.
