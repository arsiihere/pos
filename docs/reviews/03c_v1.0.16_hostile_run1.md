**Verdict: FIX THEN RE-REVIEW.** 2 BLOCKER, 6 MAJOR, 13 MINOR. The slip itself is right: it never carries money, names or fiscal data, needs no migration, uses the existing `document` job and `billPrinterFor` route, and the "never for a billed order" rule sits on the hub. The fiscal boundary holds (checked: `InvoiceIssued` and `fiscal-snapshot.ts` carry no token). What breaks is the **trigger**: a client-sent second request, with an undefined "live vs queued" rule, so in the cases that matter (a Wi-Fi blip, a reload) the pay-later customer walks off with no paper at all. The spec also leans on three dependencies that are not written, and its statement count is wrong for the default path.

### B-2 — The client-sent trigger loses the slip in the cases it exists for, and "live" vs "queued" is undefined
**Where:** §3.11 l. 210–216 (items 1–2, "A `SubmitOrder` that was **queued** offline and replays later gets no automatic slip"); P15 l. 67; §6.14 l. 429 ("not queueable"); §8 l. 471 ("after a live **Send · pay later** … sends … once"; "a queued Send that replays later sends none"); §12.3 OQ-C2 l. 619; 02b v1.0.24 §3.12 l. 230 (every `SubmitOrder` is written to the queue **before the first send**; after a reload every queued entry goes to the queue log "Send again").
**Problem:** For a pay-later takeaway customer, the slip is the **only paper with the token number**: there is no receipt, and R3 keeps names off the board. With this design the slip is lost in these cases:
1. **The first send times out** (hub busy in a rush, a 2 s Wi-Fi blip) and the drain resends it. By 02b §3.12, every `SubmitOrder` is a queue entry from the start, so "live" vs "queued" has no client-side meaning that the spec defines: 2xx on the first attempt? No `X-Queued-At` header? The same page life? If "queued" means "it carried `X-Queued-At`", a two-second retry counts as a queued replay and prints **no slip** while the customer stands at the counter.
2. **The page reloads, or the kiosk browser crashes,** between the `SubmitOrder` 2xx and the slip request. The slip command is not queued and not stored, so nobody knows it was owed.
3. **The slip request itself fails** (5xx, timeout, `SESSION_EXPIRED` at the idle edge). §8 gives no retry rule. "A retransmit is D32-safe" helps only if the client retransmits with the same `command_id`, and nothing says it must.
In all three cases nothing tells staff a slip is owed. "Reprint from the token view" assumes someone notices, and in a rush nobody will. OQ-C2 rejects a `SubmitOrder` flag as "a 02b contract … change for a print choice". But R6 is a binding owner ruling, an additive optional field is the normal R29 path, and the flag removes the second request, the lost-request window and the live/queued question together. The "grace timer" option was rightly rejected (AD-32); the flag is deterministic.
**Fix:** Move the *Send · pay later* slip into the `SubmitOrder` transaction. Add a 02b row (02b → v1.0.25, which 02b-TK bumps anyway): an optional `takeaway.slip_on_send?: boolean` that the client sets on the pay-later button. 03c registers a **command-time hook**, not a fold (as `printDocument` is called inside 05's close), that runs §6.14's rules (setting, root / `slip_held`, printer) in the same transaction. D32 then covers retransmits for free. A queued replay prints only when `now − queued_at ≤ takeaway_slip_replay_ms` (a constant, e.g. 120 000, compared against the stored `queued_at`, not against arrival timing, so it is deterministic). Keep `PrintTakeawaySlip` for two cases only: `reason: 'reprint'` and the Send & pay panel closed unpaid. If the owner keeps the client trigger, then at minimum: (i) define "live" precisely (2xx to the first attempt, no `X-Queued-At`); (ii) on any `SubmitOrder` 2xx for a pay-later cart still on screen, send the slip whether or not the order was queued; (iii) persist the owed slip in the client `QueueStore` next to the order and retry it with the same `command_id` until 2xx or 4xx; (iv) show "Slip not printed — Print slip" on the token tile when it fails. Then take OQ-C2 to the owner as a real decision, not a review note.

## MAJOR

### M-1 — The statement count "≤ 4" is wrong on the default (routed) path
**Where:** §6.14 step 5 l. 434, Result l. 437 ("≤ 4 (1 read + 1 printer + 2 print …; 2 on `no_printer`)"); §3.11 l. 254 (`buildTakeawaySlipDoc(…, width_cols)`); §12.2 row 14 l. 613; test 59 l. 530; code `apps/hub/src/print/bill-routes.ts:22-33` (`billPrinterFor` returns `string | null`, the id only), `apps/hub/src/print/api.ts:13-21` (`printDocument` = active check + insert).
**Problem:** The builder needs `width_cols` (32 / 48), and §3.6's QR default module size needs the printer's `paper_width_mm`. `billPrinterFor` returns only an id, so every existing caller reads the printer row afterwards: `print-check-bill.ts:236-237` ("billPrinterFor … 1) and its row (1)"), `print-docs.ts:165-166`, and `close-split.ts:135` (joined into its post-fold read). The routed slip therefore costs 1 (token) + 1 (route) + 1 (printer row) + 2 (`printDocument`) = **5**. Only the payload-`printer_id` path, where step 5's "active check" can also return the width, is 4. Test 59 asserts "≤ 4" and will fail on the default route, or someone will "fix" the code by guessing the width.
**Fix:** State **≤ 5** (routed), 4 (payload printer), 2 (`no_printer`) and 1 (skip before the printer), and fix §12.2 and test 59. A cheaper option: have step 5's read return `paper_width_mm` together with the route, e.g. a 03c-internal `billPrinterRowFor` that joins `printers` in the same statement, which gives 4 again. Do not change `billPrinterFor`'s exported shape, because 05 calls it.

### M-2 — Nothing on the hub stops duplicate slips: double tap, two triggers, two kiosks
**Where:** §3.11 l. 212–214, l. 218 ("With `reason: 'reprint'` the slip always prints"); §6.14 l. 429 (D32 is the only guard), l. 437 ("No event"); §8 l. 471; `apps/hub/src/print/api.ts:18` (`order_id` inserted as `NULL` for every `document` job).
**Problem:** D32 dedupes only one `command_id`. Each of these prints a second "PAY AT THE COUNTER" slip with the same token: a double tap on *Print slip* (two `command_id`s); a Send & pay panel closed, reopened and closed again (trigger 2 fires twice); trigger 1 followed by staff pressing *Print slip* because the first slip is still in the printer's buffer; two kiosks with the token view open. Two slips for one token is how a second person collects someone else's order. Because the job is written with `order_id NULL` and no event, nobody can later see that a slip for token 57 was printed twice, or by whom.
**Fix:** (a) Have `printDocument` take an optional `order_id` (an additive meta field, stored in the existing `print_jobs.order_id` column, so no migration) and write the token's root `order_id` on slip jobs. (b) For `reason: 'send'`: if a non-cancelled `document` job labelled `Token slip` already exists for the token's root → `skipped: 'already_printed'`. That is 1 statement on a 7-day table, inside the count of M-1. (c) For `reason: 'reprint'`: the REPRINT header (`is_reprint = 1` → "REPRINT" at the top), so two slips are distinguishable at hand-over, and a client debounce on the button. (d) Optional: a `TakeawaySlipPrinted { order_id, reason, job_id }` event so 04's audit shows reprints, the way `CheckBillPrinted` does for check bills. If the owner rejects the event, record that in §12.

### M-3 — Permission scope is stated by reference to a rule that refuses the second kiosk
**Where:** §3.10 l. 206 ("`take-order` (`allowed`; the scope rule of 05 §6.3 `PrintCheckBill` for a takeaway order)"); §6.14 step 2 l. 431 (the token read selects no `placed_by`); errors l. 437; code `apps/hub/src/billing/queries/bill.ts:286` (`covers`: a key bill under a non-`branch` scope is covered only when `placed_by.includes(staffId)`), `:269` (`requires_approval` also passes); `packages/domain/src/permissions.ts:70` (`take-order` scopes `branch | my_floors | own_tables`).
**Problem:** Under 05's rule, a cashier whose `take-order` scope is `own_tables` or `my_floors` can print a slip only for tokens **they** placed. On a two-kiosk counter, kiosk B cannot reprint token 57 that kiosk A took, even though R3 makes the queue a shared kiosk view. The spec does not choose between the two readings. The SQL in step 2 has no `placed_by`, so the rule as cited cannot run within the stated statement. `PERMISSION_DENIED { reason: 'outside_scope' }` is not described. "(`allowed`)" also conflicts with 05's `billAccess`, which accepts `requires_approval`: may an approval-grant holder print without an approval, or is the command refused?
**Fix:** Decide and write it out. Recommended: **any `take-order` holder at the branch**, scope ignored, as the token view is shared (R3) and the slip carries no money or contact. Otherwise select `o.placed_by` / `t.placed_by` in step 2 (same statement) and call `covers()` over the token's orders, giving `PERMISSION_DENIED { reason: 'outside_scope' }`. State how `requires_approval` behaves (recommended: treated as allowed, as `PrintCheckBill` does; the command is not approvable). Add a test for each branch of the rule.

### M-4 — The "Ready around" time can be early, can contradict R4, and does not match the receipt as claimed
**Where:** §3.11 l. 249; §4.2 l. 287; test 58 l. 529 ("an order with `pickup_at_ms` → the pickup time (+ padding)"); 05 l. 753 ("so slip and receipt cannot disagree"); code `apps/hub/src/billing/print/ready-times.ts:18-24` (`landOf` returns `null` for a line with no fire time), `:36-37` (such a line is skipped), `:49` ("Ready ~").
**Problem:** (1) **Early time.** The slip prints the latest `customerReadyAt` over the live lines. A line whose time is `null` (not yet planned or fired, no booked load) is silently left out, so a token whose slow karahi is still unplanned shows the naan's time. The customer is told "1:42" for food ready at 2:05. (2) **Pickup.** R4 says the whole order lands *for the pickup time*. Test 58 expects "pickup + padding", which prints e.g. "Ready around 7:10 PM" for a 7:00 pickup. Either the padding does not apply to a pickup order or the test is wrong, and the 03a bump that would decide it is unwritten (B-1). (3) **"Cannot disagree" is false.** The receipt prints the **together** lines' latest time plus one line per **as-ready** item. The slip prints one maximum over every serve mode, worded "Ready around" against the receipt's "Ready ~". For the same order the receipt can say "Ready ~1:30 PM · Karahi: ready ~1:42 PM" while the slip said "Ready around 1:42 PM". That is defensible, but it is not what 05 l. 753 says.
**Fix:** (1) If any live line of the token has `customerReadyAt = null`, leave the Ready line out (better none than a wrong one), and add a test. (2) Ask the owner whether a pickup order prints the pickup time itself, with no padding (recommended, per R4), and fix test 58. (3) Reword 05 l. 753 to "same line-time function; the slip shows the token's latest time, the receipt shows per-group times", and pick one word ("Ready ~" or "Ready around") for both.

### M-5 — R6's "Print check bill on the cart" is silently narrowed to "once sent"
**Where:** §8 l. 471 ("the **cart** shows Print check bill once its order is sent (an unsent cart has no order, B16)"); §4.3 l. 301; 05 l. 738, l. 1186, l. 1472; rulings R6 ("A 'Print check bill' action is on the cart and the token view").
**Problem:** On a takeaway counter the cart is the unsent order. After Send the cart is cleared for the next customer, and the sent order lives on the token view. "Cart once sent" is therefore an addition cart at best, so R6's cart action effectively disappears. The usual case R6 covers, a customer asking "how much?" before deciding to pay now or later, has no paper. The spec calls the change "no hub change, used as is", which is true only because it dropped the case. Neither spec raises an OQ.
**Fix:** Take it to the owner as an open question (03c OQ-C8 / 05 OQ). The options are (a) "the cart of a sent token only" as written; (b) a client preview of the cart total on screen, with no paper; or (c) a hub print of an unsent cart (a new `PrintCartEstimate`, with no bill and no event, through the pure `computeBill` with the cart's lines). If (a), write it in both specs as an owner-ruled narrowing of R6.

### M-6 — Required per-command tests are missing (F §6.7), and the race tests are missing
**Where:** §10 tests 57–61 l. 528–533; acceptance l. 545; README checklist line "§6.7 tests: per hub command, happy path + one test per error code + retransmit test".
**Problem:** There is no test for `PERMISSION_DENIED` (M-3) or `VALIDATION_FAILED` (a bad `reason`, a 65-character `order_id`). There is no race test: a slip and a `CloseSplit` of the same order in one writer turn, both orders; two `command_id`s for the same order and `reason: 'send'` (M-2); `slip_held` when the root is **cancelled** (m-1). No statement-count test covers the routed path (M-1). No test covers the client half (§8): the live / queued / reload rules of B-2, `ORDER_BILLED` → hide the action, and the toasts. No test checks that `TAKEAWAY_SLIP_NOT_ALLOWED` is appended to `packages/domain/src/errors.ts` and F §6.2. 05's tests #60c and #60d contain no 05-side test of the move itself; the only check is that "#92–#97b pass unchanged".
**Fix:** Add tests 62–66: the per-code refusals; slip-then-close and close-then-slip; double `send` → one job (with M-2); routed-path statements = the corrected bound; a client test (02b-TK client plan) for B-2's rules. Add the errors-catalogue entry to task 31's test list.

## The asked checks, one line each

- **Is a client-sent slip command reliable enough?** No (B-2). A lost request, a reload or a timed-out first send each lose the slip, and "queued replay" is undefined against 02b §3.12.
- **Offline queue replay:** "no slip on replay" is stated but not defined; a two-second retry can count as a replay (B-2).
- **Double tap / two kiosks:** each tap or kiosk prints again; D32 covers only one `command_id` (M-2). The second kiosk may also be refused by scope (M-3).
- **Race slip vs Send & pay closing the bill:** sound. The single writer orders them; a slip after the close → `409 ORDER_BILLED`; a slip just before the close → slip + receipt, harmless. A partly paid bill still gets the slip (m-2).
- **Addition / `slip_held`:** the logic is right for the 05 #44e bill rule (an addition joins an open bill, else opens a new one). The root is undefined when it is cancelled or on a tie (m-1).
- **Idempotency key semantics:** D32 works with no event (`route.ts:158-190` writes `processed_commands` with `event_ids: []`); 7-day prune fine.
- **Statement count ≤ 4:** wrong on the routed path, which is 5 (M-1).
- **Module boundaries:** 03c imports no 05 code (`customerReadyAt` moves into 03c, and 05 already imports 03c's `clock12`). The formula is now written twice, and 03c's task edits a 05 file (m-6).
- **Fiscal leakage of the token:** none. `InvoiceIssued` (`invoice-parts.ts`) and `fiscal-snapshot.ts:4` carry no token; there is no `bill_print_jobs` row; the receipt's `#57` `order_label` is print-only, as before.
- **PC437 / `?` substitution:** the fixed strings are ASCII; dynamic Urdu becomes `?` (m-4).
- **QR size / length on 58 vs 80 mm:** fits at the defaults up to 400 code points on 384 / 576 dots, but not on 512-dot printers at 400. Bound the link (m-5).
- **Permission choice (`take-order`):** the right key, but the scope rule is wrong for a shared counter (M-3).
- **Missing tests:** M-6.
- **Open owner questions that are really blockers:** OQ-C2 (B-2). M-5 should be a new OQ.
- **Contradictions with R6:** the cart check bill is narrowed (M-5); the `takeaway_slip` pointer (m-13); "no Urdu" is enforced as `?` (m-4); "receipt on payment by default" and "slip only for pay-later" hold (test 61, #60c).
