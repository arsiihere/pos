### B-1 — `takeawayProgress` is owned by nobody, and the line `ready_at` rule it claims does not exist
**Where:** 00 l. 68 ("02b **v1.0.25** provides `takeawayProgress`"), l. 14, §6.41 l. 1861–1891, §11 v1.13 row l. 2405 ("After 02b v1.0.25's `takeawayProgress`"); 05a §4.5 row Q-1 l. 325, §3.11 l. 255–269 (esp. l. 256 "02b v1.0.25's rule: a Pass `ReadyToServe` not undone, or engine stage `done`, or a line that needs no station"), §6.12 l. 566–587, §11 step 13; 02b v1.0.25 §12.4 l. 945 ("the read it serves comes with **that bump** [00 v1.13], **not in v1.0.25**"), §6.16 row `ready_at` l. 591, TK-Q6 l. 937; `grep -c takeawayProgress 02b_Ordering_Spec_v1.0.25.md` = 0.
**Problem:**
1. **Nobody owns the export.** 00 and 05a say 02b v1.0.25 exports `takeawayProgress`, but 02b v1.0.25 never mentions it and its §12.4 says the read comes with 00 v1.13. Each DRAFT points at the other. Both new reads depend on it: §6.12 `pickup-board` (TV) and §6.41 (status page). Both claim "2 statements", which nobody can check. The approval checklist §4 ("later modules rely only on what is listed here") fails for all three files.
2. **The readiness rule is attributed to a spec that says the opposite.** 05a attributes a per-line `ready_at` to 02b ("Pass mark, or engine `done`, or no station"). 02b v1.0.25 has only a per-order `ready_at` from 03b `readyAtOf`. It is set only from Pass marks and is explicitly null in a kitchen without a Pass (TK-Q6). Under 02b's rule, a branch without a Pass point never shows a token in Ready, so the board and the status page are dead there. Under 05a's rule, the engine's `done` makes a token Ready before the Pass bags it. The board then calls the customer to the counter early, which breaks 05a §8's own "never shows a wrong Ready" (l. 626). The two specs disagree on the one fact the board exists to show.
3. **The board's sort and ETA depend on the missing export too.** `promise_ms` per order "from the engine state in memory" and the group key (`business_date`, `token`) are specified only inside the missing export's signature.

**Fix:** Pick one owner and write the export there in full: signature, both filters, the SQL of the 2 statements, the indexes they use, and a test with the statement counter. 02b is the natural owner (it owns `orders`/`order_lines`, `readyAtOf` and §3.11 groups). - In a kitchen with no Pass point, the engine's `done` counts as ready, and it is never used where a Pass exists.

Until the export's text exists in the owning spec, none of the three files can be approved.

## MAJOR

### M-1 — The display kind is named in one place, but the session code hard-codes two kinds in about 74
**Where:** 00 M96 l. 510 (the reader list: "the restore reconcile (M40, `projections/access-reconcile.ts` `isKind`), the admin lists, `SessionStarted` / `SessionEnded`"), §4.2 events row l. 869 ("or `hub` / device_id for `kind: 'display'`"), §6.39 l. 1831–1847, test 173 l. 2334. Code: `auth/session-store.ts:185, 207–208, 310–311` (`stream_type: kind === 'station' ? 'station' : 'staff'`, `stream_id: … staff_id ?? ''`); `projections/access-reconcile.ts:60–70` (`WHERE stream_type IN ('staff','station') AND event_type = 'SessionStarted'` / `'SessionEnded'`), `:155` (`isKind`), `:162–169` (`sessionEndedDraft` maps non-station to `staff` / `staff_id ?? ''`); `auth/session-store.ts:242–243` (revoke ends every session through `endSession`); `packages/domain/src/enums.ts:3`; `packages/events/src/events/staff/SessionStarted.v1.ts:6`; `grep "kind === 'staff'|kind !== 'staff'|kind === 'station'|kind !== 'station'"` → 74 sites.
**Problem:**
1. **Every `SessionEnded` lands on the wrong stream.** The spec puts display session events on `hub` / device_id. But every path that ends a session goes through `endSession` / `sessionEndedDraft`: `replaced`, `forced`, `device_revoked`, `hub_restored`, `logout`. Both map any non-station session to stream `staff` with `stream_id = ''`. Changing `isKind` alone, as M96 says, writes display `SessionEnded` events onto a phantom `staff/''` stream, with `SessionStarted` on `hub/<device>`.
2. **The restore reconcile cannot see display sessions.** It selects only `stream_type IN ('staff','station')`, so after a restore a display session stays open in the table. Test 173 ("the restore reconcile reads a display session") then fails or passes by accident.
3. **Denylist checks treat display as staff.** Several sites are written as checks against `station`, for example `kind === 'station' ? null : staff_id` (`commands/route.ts:111`, `session-store.ts:185`). Any such site reached by a display session silently treats it as a staff session with a null `staff_id`. M96 lists none of these sites.
4. **There are three separate session checks, not one.** They are `guards.ts:218–231`, `queries/registry.ts:140–145` and `commands/route.ts:281`. §11 step (3) says "`allowDisplay` in the guards and query registry", but the WS `authenticate` (`ws/server.ts:465–480`) and `POST /auth/logout` (which must accept the kind) are a fourth and fifth.

**Fix:**
- Add a "session-kind readers" table to M96. List every writer (`createSession`, `endSession`, `sessionEndedDraft`, revoke) with its stream mapping, written once as a function `sessionStream(kind, ids)` in `session-store.ts`.
- List every reader: the reconcile's `stream_type IN ('staff','station','hub')` filtered by `event_type`, `isKind`, the three guard paths, the WS `authenticate`, logout, the sweeper (safe today: `idle_ttl_ms IS NOT NULL`), the admin lists, and `SessionKind` in `@pos/domain`.
- Require an exhaustive `switch (kind)` with a `never` default at every site that branches on kind.
- Tests: a display session ended by each of the five reasons writes its `SessionEnded` on `hub` / device_id. A restore with an open display row ends it `hub_restored`. Running `grep` for `=== 'station' ?` finds no fallthrough site.

### M-2 — Boards are still alert targets and can still hold an alert-mode socket; the fix is pushed to bumps that do not exist
**Where:** 05a §4.5 rows D-5 l. 326 ("01d (next bump)") and T-1 l. 327 ("05b (next bump)"), OQ-B7 l. 749, §8 l. 627 ("The board opens **no** alert-mode socket"); 00 §6.21 l. 1609, §4.2 l. 849, test 175 l. 2336 ("an `always_on` alert … reach no display socket"); code `alerts/targets.ts:449` (`cashier_kiosk` → always on), `alerts/receipts.ts:14–17` (a receipt is accepted only from a device the alert was "sent" to; `alert_recipients` holds the target devices), `apps/client/src/features/alerts/socket.ts:6–7` (a kiosk page with no session opens alert mode), 05b v1.0.1 l. 31 (AlertService holds the alert-mode socket "whether the page is open … signed out"); 02b-TK R8 ("the takeaway ready alert must reach the kiosks too").
**Problem:**
1. **The alert engine still targets a board PC.** 00 only stops the frames from reaching a display socket. The alert engine still resolves a board kiosk PC as an `always_on` target, writes it into `alert_recipients`, and expects receipts that never come. The 03b R8 "not collected" alerts and the 01d approval escalation steps (01d l. 659–660, `{ always_on, recipient }`) all widen to the board. - (c) 05b: the AlertService stops when the approved profile is the board.

### M-3 — `statusLink` does not match 03c, has no "off" state, and builds links that fail for non-ULID order ids
**Where:** 00 §4.2 l. 841 (`statusLink(order_id)` → `{ path, url }`, pure), M98 l. 512 (check: "`order_id` must be 26 characters of that alphabet"), §3.10 l. 787 (`advertised_host` optional in the schema), §7.13 step 6 l. 2005 (the page is LAN-only); 03c v1.0.16 l. 250 ("`statusLink(order_id): string | null` … `null` (status page off or not built) … the QR block **and** both scan lines" are dropped), l. 271, l. 298 ("`null` while the public status route is off"); 05a §4.5 row P-1 l. 328 (`statusLink(order_id).url`); code `orders/commands/submit-order.ts:58` (`order_id: z.string().min(1)`: client-chosen, not ULID-checked), `lib/net.ts:52–56` (host matcher without `advertised_host`), `config/schema.ts:30`.
**Problem:**
1. **The two DRAFTs disagree on the type.** 03c (string or null) and 05a P-1 (`.url`) cannot both be right.
2. **There is no "off".** 03c drops the QR when the status page is off, but 00 has no off switch. A branch whose router cannot route guest Wi-Fi to the hub (MQ15), or that has no guest SSID, prints on every pay-later slip a QR that times out on the customer's phone.
3. **Non-ULID order ids produce links that never validate.** `order_id` is client-generated and only `min(1)`. A queued order from a client that sends a lower-case ULID, a UUID or anything with a `.` gets a slip link that §6.40 always answers "not valid".
4. **No address, no URL.** With `advertised_host` absent, the `url` is undefined.

**Fix:**

- Better still, have 02b `SubmitOrder` validate `order_id` against `ULID_RE`: it is a breaking change, allowed before the pilot by R29, and it removes the case.
- Tests: flag off → `null` and no QR; a non-ULID id → `null`.

### M-4 — The runbook opens the hub's only port to the guest network, so one CIDR string becomes the only barrier
**Where:** 00 §7.13 steps 1–3 l. 1995–2002 ("guest → **the hub's IP, TCP `http_port` only**: allow"), M97 l. 511, §3.7 table l. 755, l. 763; F §5.7 D28 l. 1260–1261 ("The router lets the guest network reach only the hub's IP and port"); code `auth/guards.ts:144–153` (guest guard = `guestNet(request.ip)`), `lib/net.ts:5–19` (IPv4 CIDR match only), `lib/boot.ts:144` (one listener, `0.0.0.0:http_port`), M58 l. 484.
**Problem:**
1. **The guard becomes the only control.** Before v1.13 an installer could keep guest Wi-Fi off the hub at the router, and the guest guard was defence in depth. R5 now requires the router to pass guest → `hub:http_port`, and that port also serves `/pair/requests`, `POST /auth/pin`, `/ws`, every command and `/admin`. Separation of the restaurant's untrusted network then rests on one app-level check: an IPv4 CIDR typed at `/setup`.
2. **A common setup mistake fails open.** If the guest VLAN is renumbered, the ISP router changes its DHCP range, or the installer types the wrong CIDR (M58 checks only that one exists), the guest network silently becomes staff network, with pairing and PIN guessing exposed. It never fails closed.
3. **The exemption is hard to see in the code.** It is "a route group without one guard" on the same listener, so the inventory test is the only thing stopping it from widening.

**Fix (T2-sized):** Serve the `public` group on a **second listener**, `public_port` (default `http_port + 1`), that registers only the two `/t/*` routes, the security headers and the limiter. The router opens only `public_port` to the guest network; `http_port` stays closed to it.
- The main listener keeps its guest guard on every route, the `public` group included. Defence in depth comes back, and "exactly two routes" becomes structural.
- `statusLink.url` uses `public_port`. The host guard on the public listener accepts `advertised_host:public_port`.
- This is one more `Fastify()` instance in boot. It needs no new dependency.

If the owner rejects it, add a boot self-check at minimum: warn in `/admin` when `guest_network_cidrs` overlaps `advertised_host`'s own subnet or the hub sees requests from an unlisted private range. Also record in §12.4 that the guard is now the only control.

### M-5 — Under NAT, or with a rotated IP, the limiter becomes one shared bucket that one device can drain
**Where:** 00 §7.12 l. 1982–1993, M99 l. 513, §7.13 step 3 l. 2002 ("If the router can only masquerade, set `ip_burst` / `ip_per_min` to the global values"), MQ15 l. 2483, MQ16 l. 2484.
**Problem:**
1. **NAT collapses the per-IP bucket.** Under masquerade every phone is one `request.ip`. The documented fallback turns the IP bucket into a copy of the global one, so one script on one phone spends the whole budget and every polling customer gets `429`. A wrong link costs extra only in the IP bucket, so guessing traffic and real polls draw from the same global pool (l. 1989).
2. **The global bucket fails without NAT too.** On a /24 guest subnet a guest can set static addresses. 254 addresses × a 20-token burst is about 5 000 tokens, against a global burst of 500. The global bucket fails closed for everyone.
3. **Real customers can trip the limit.** 05a and 00 §8.6 fetch "at once" on every `visibilitychange`, so a customer switching apps 20 times in a minute hits `429` on a valid link.

**Fix:**
- Split the global bucket in two. **valid**: requests whose MAC checked, 50/s. **invalid**: everything else, small, for example 5/s. Charge invalid cost there too, so guessers can never starve customers who hold a valid link.
- Add a per-**order** bucket on §6.41, for example 12 per minute per `order_id`, which stays meaningful under NAT. Drop the "set IP = global" fallback; under NAT, rely on the order and invalid buckets.
- Rate-limit the client's visibility fetch to one per `poll_ms`.
- Tests: a NAT run (one IP, 50 phones polling while a guesser runs at full rate) → every valid poll gets 200.

### M-6 — Errors, headers and logs on the public route take the generic JSON path
**Where:** 00 §6.40 l. 1849–1859 ("its own two render as the page with `data-code`"; `429` with `Retry-After`), §7.13 headers l. 1997, §7.2 note l. 1904, test 184 l. 2345, test 187 l. 2348; code `server.ts:338–367` (`installHubErrors`: a `DomainError` → JSON envelope; not-found → JSON with no headers), `server.ts:158–165` (the request serializer logs `req.url` for every request), `lib/client-dist.ts:21` (a different CSP for client files).
**Problem:**
1. **The limiter's 429 comes back as JSON.** The limiter is an `onRequest` guard (M97 `guardsFor('public')`), and a guard throws a `DomainError`. That error goes to the app-wide error handler, which sends `{ error }` JSON. So `GET /t/:link` over its limit shows the customer raw JSON, not the page. The same happens to `TRACKING_LINK_INVALID` unless the handler renders it itself, which the spec does not say.
2. **Security headers are set nowhere specific.** §7.13 says they go on "every `public` response" but not where, and error replies leave through `setErrorHandler`.
3. **Near-miss URLs log the MAC.** A trailing slash (`/t/<id>.<mac>/`, which Fastify does not match by default) or a scanner appending a character hits the not-found handler. That handler runs no route config, so the request serializer logs the full URL, MAC included. Test 187 checks only the valid case.

**Fix:**
- §6.40/§6.41: the `public` group sets its headers in an `onSend` hook (so errors are covered). It has its own `errorHandler` that renders the page for `GET /t/:link` (status 404/429 with `data-code`) and the JSON envelope for `/status`.
- The request serializer drops `url` for any path that starts with `/t/`, matched or not, and the not-found reply for `/t/*` gets the same headers.
- Tests 184 and 187 add: `429` on the page route (HTML, CSP, `Retry-After`), `/t/<valid>/` (404, no MAC in the log), `/t/<valid>/status/x`.

### m-9 — Every board retry is a new session plus two events, with no limit
**Where:** 00 §8.4 l. 2086 ("WS `4401` (other reasons), `401 SESSION_*` → call `POST /auth/display` again after the backoff"), M96 ("A force-logged-out board signs in again by itself").
**Problem:** Each retry writes a `staff_sessions` row and `SessionStarted`/`SessionEnded` to the immutable log. If a fault repeats, for example a WS `auth` that fails after `/auth/display` succeeds, or a manager pressing Force logout repeatedly, the log grows without limit. Nothing caps it.

- After 10 failed rounds, stop and show "Board needs attention" (a new key).
- Test: a WS that always fails creates at most 10 sessions.

- At minimum, state the risk in OQ-B.

### m-13 — The status link travels in clear text on a shared Wi-Fi
**Where:** 00 M98 "Accepted leak" l. 512, MQ14 l. 2482.
**Problem:** On a WPA2-PSK guest SSID, anyone with the passphrase who captured a handshake can read other phones' HTTP traffic. The link, the token and the items are then visible to them.
