## MAJOR

### R2-M-1 — The public listener has no transport limits; the limiter does not cover not-found / guard replies, and every request writes a log line
**Where:** M97; §7.12 ("after the link check"); §7.2 (public logger logs every request incl. `unmatched`); §7.13 runbook; code `lib/boot.ts:144,225` (`app.listen({ host: '0.0.0.0', port })`, no server options); `grep -r "maxConnections|requestTimeout|keepAliveTimeout|connectionTimeout"` over `apps/hub/src` → nothing.
**Problem:** R5 opens a TCP port on the hub to an untrusted network for the first time. The limiter is per request and in the handler, so: (1) one guest phone can hold hundreds of idle/slow sockets (Node defaults: `headersTimeout` 60 s, `requestTimeout` 300 s, no connection cap) and keep the single event loop busy with 429/404 replies — the same loop serves KDS, commands and the engine tick; (2) not-found, `HOST_NOT_ALLOWED` and `HUB_NOT_PROVISIONED` replies are never rate limited; (3) each reply is one journald line, so a flood trips journald's per-service rate limit and **drops the hub's other log lines** (errors, audits of the incident). The 2 statements/request cap is fine; CPU, sockets and logs are not bounded.
**Fix:** M97 / §7.12: the public Fastify instance is created with `connectionTimeout` 10 s, `requestTimeout` 10 s, `keepAliveTimeout` 5 s, `maxRequestsPerSocket` 100, `bodyLimit` 1 024, server `maxConnections` 256, and a per-IP open-connection cap (e.g. 16; extra sockets destroyed on `connection`, no reply); bind `0.0.0.0` (IPv4, as the main listener; `lib/net.ts` matches IPv4 only). §7.2: 429, `unmatched` and invalid-link replies are **not** logged per request; the listener counts them and logs one `info { msg: 'public_summary', ok, invalid, limited, unmatched }` per minute when any is non-zero. §7.13: recommend the router's per-client rate limit where offered. Tests: 40 idle sockets from one IP → the 17th is closed at once, the main listener still answers `/health`; 1 000 unmatched requests → no per-request line, one summary line.

### R2-M-2 — `pay: 'due'` never clears when the group holds a cancelled order
**Where:** §6.41 `StatusView.pay` ("'due' while any order of the group has `billed_at` null"); 02b v1.0.25 §4.2 (`group_of` returns every order of the group "whatever its state", `orders[].cancelled_at` included); 05 bills exclude cancelled orders (`billed_at IS NULL AND cancelled_at IS NULL`), so a cancelled order's `billed_at` stays null forever.
**Problem:** a cancelled addition (or a cancelled root whose addition was paid) makes the page say "Please pay at the counter" after the customer paid. Same defect on the board (05a R2-M-1).
**Fix:** "'due' while any **non-cancelled** order of the group has `billed_at` null". Test 183 adds: root paid + cancelled addition → `pay: 'paid'`.
