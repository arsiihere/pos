## BLOCKER

### R2-B-1: The pricing source crosses a module boundary with no contract, and the cart-to-bill-lines mapping is undefined
**Where:** §6.3a Script l. 1243 ("02b §3.2 steps 4–7 **read-only** through `buildSubmit` … the built `itemAdded` lines as a **projected bill**"); Payload l. 1242 ("the same schema … as `eta-preview`'s `draft`"); §4.1 02b row l. 809; §4.5 (no row); task 11a l. 1881.
**Problem:**
1. 02b v1.0.25 §4.2 l. 396 lists `buildSubmit` as one of "two **module-internal** contracts (02b's own `contracts.ts`, **not used by other modules**)". The draft schema, `submitBuildCtx` and `expandParts` are not exported either. 05 §4.1 lists no such import, and §4.5 has no 02b row. README checklist: "no forward reference except through an *Exposes* contract", and one unticked line blocks approval.
2. `buildSubmit` yields `ItemAdded` payloads (`line_total_minor`, `allocated_price_minor`, `tax_class_id`). `computeBill` takes `ComputeLine { units, unit_price_minor, base_minor, tax_profile_id }`. The bill's base is 02b's §3.4 `billed_minor`, computed in SQL by the orders projection (`exports.ts:13-27`, `:286`; the deal total is the sum of its parts, a `deal_part` counts 0). The spec gives no mapping, so the implementer will invent one, and deals, option children and `part_of` splits can come out differently from the bill after Send.
3. Weighed lines with no weight yet (`quantity: null` → `line_total_minor: null`; the cart shows "pending", `cart.ts:140-164`) are not covered. `openComputeLines` turns `null` into 0 (`bill.ts:351`), so the paper total silently leaves the karahi out.
4. Without `expandParts`, which `eta-preview.ts:144` runs before `buildSubmit`, there is no `part_of`, so §3.16's grouped rows ("Karahi 5,750 / 5 x 1,150") cannot print.
**Fix:** Add a 02b row in §4.5 (02b → v1.0.25, 02b-TK, same package): 02b exposes one pure-plus-read export, e.g. `draftBillLines(db, state, config, draft, now) → { lines: Array<{ order_item_id, line_kind, units, unit_price_minor, base_minor, tax_profile_id, name, options, part_of }>, refused: Array<{ key, code, details }> }`. It runs §3.2 steps 4, 4a and 5–7 read-only (`submitBuildCtx` + `expandParts` + `buildSubmit`, with ids minted as `eta-preview` does), and maps each line to §3.4's `billed_minor` at submit (no comp, removal or void) through the same rule as `exports.ts` (a deal = Σ its parts, a `deal_part` 0). It costs 1 statement (`item_availability`). It also exports the draft schema. A weighed line with no weight prints its name, "weighed at the counter" and no amount, and the total carries "+ weighed items" (or refuse it with `400 … 'weight_pending'`; the owner picks if unsure). 05 §4.1 cites the export, and 05 §6.3a consumes it.

## MAJOR

### R2-M-1: "Refusals exactly as `eta-preview` returns them" means two different things, and step 8 is dropped
**Where:** §6.3a Script l. 1243 ("steps 4–7 … the same … refusals as `eta-preview`"), Errors l. 1246; test #60g l. 1735 ("an unavailable item → the same refusal `eta-preview` gives").
**Problem:** `eta-preview` refuses only the whole request (400 / `BUSINESS_DAY_NOT_OPEN` / `PICKUP_TIME_INVALID`). Line refusals (`ITEM_UNAVAILABLE`, `ITEM_OUT_OF_HOURS`, `OPTION_CHOICE_INVALID`, `MENU_ITEM_NOT_FOUND`, `DEAL_NOT_FOUND`, `STATION_PAUSED`, `ITEM_SOLD_OUT`) come back **inside a 200** as `lines[].refused`, and the other lines are still previewed (`eta-preview.ts:38, 99, 180`, and the step 8 loop after it). A command that prints has to choose: print without the refused line (paper ≠ cart), or refuse the whole command (with which status?). The spec says "steps 4–7", but `STATION_PAUSED` and `ITEM_SOLD_OUT` are step 8, so the test sentence cannot be met.
**Fix:** State: "any line refusal of steps 4–7 → the whole command is refused with that line's code and HTTP status (02b §9), `details.key` = the draft key; nothing written". Recommended: step 8 (paused station, sold out) is **not** checked, because a price quote does not need stock. List the codes in Errors. In #60g, replace "the same refusal `eta-preview` gives" with the explicit code and status.

### R2-M-2: The statement count is ≤ 4 on paper and 5 on the default path, and its description is wrong
**Where:** §6.3a Statements l. 1245 ("the branch stock read of `buildSubmit` when the draft has stock-tracked items, 02b AD-25 memory otherwise; printer route 1; `printDocument` 2"); #60f l. 1734 ("statements ≤ 4"); §12.2 l. 1935.
**Problem:** (a) `buildSubmit`'s statement is `item_availability` (manual On / Off), run on **every** draft that reaches an item (`submit-order.ts:288`). It is not a stock read: stock draws come from engine memory. (b) The result needs `printer_name`, and the builder needs `paper_width_mm` (`width_cols`). `billPrinterFor` returns only an id (`bill-routes.ts:33`), so `PrintCheckBill` reads the printer row afterwards (`print-check-bill.ts:236-237`, `activePrinter`). This is the same defect as run 1 M-1. The routed path is therefore 1 + 1 + 1 + 2 = **5**. With a payload `printer_id` it is 1 + 1 + 2 = 4.
**Fix:** "Statements: ≤ 5 routed (`item_availability` 1, `billPrinterFor` 1, printer row 1, `printDocument` 2); 4 with `printer_id`; 1 when no route". Or join the printer row into the route read (03c's `slipPrinterRow` pattern) for 4. Fix #60f and §12.2.

### R2-M-3: The parity claim is false: the cart has no `computeBill`, and nothing tests parity with the bill after Send
**Where:** §6.3a Result l. 1244 ("`totals_default` = the same figures the cart shows from its pure `computeBill`"); #60f ("the total equal to the pure `computeBill` of the same lines"); 03c run 1 M-5 resolution (same claim).
**Problem:** The cart total is `cartTotal` = Σ of line money (`cart.ts:168`): no tax (tax-exclusive branches), no service charge, no rounding, no cash vs digital rate. Paper and screen will differ whenever tax is exclusive or a takeaway service charge applies, and the customer sees two totals. #60f compares `computeBill` with itself, which proves nothing.
**Fix:** (a) Drop the claim. Say instead that the client shows the result's `totals_default.total_minor` as the paper total, and the cart screen keeps its line sum labelled "items". If the owner wants one figure, the cart shows the hub's total (OWNER, recommended: show the hub figure after the print). (b) Replace #60f's total check with **parity with SubmitOrder**: the same draft → `PrintCartCheckBill` total == `PrintCheckBill { bill_ref: { order_id } }` total after `SubmitOrder` of that draft (same config, same minute), on a fixture with exclusive tax, a service charge, a deal, a linked option and a split line.

### R2-M-4 (OWNER): "No event" leaves no audit trail for paper that looks like a bill and is never rung up
**Where:** §6.3a Script l. 1243 ("**No event** (no bill, order or audit row …; the job row is kept 7 days …); one `info` log line"); §12.2 l. 1935 ("none (a print job only)").
**Problem:** Fraud path: a cashier prints a cart check bill ("PROVISIONAL", items, total), takes cash for ready or counter items (drinks, stock-served items, which need no kitchen ticket), then clears the cart without Send. Nothing in 04's audit, the shift or X / Z shows it. The only trace is a `print_jobs` row for 7 days that no screen lists once printed (`print-queue` shows pending jobs, 03c §6.7), plus a hub log line. The existing `PrintCheckBill` writes `CheckBillPrinted` and audit `check_bill_printed` (§6.3). OR-5 forbids a **bill**; it does not forbid an audit fact.
**Fix (recommended default):** Append a hub-stream event `CartCheckBillPrinted { job_id | null, printer_id | null, line_count, total_default_minor, order_type }` (stream `hub` / branch, no bill, no order), mapped by 05 to audit `cart_check_bill_printed` (04 `registerAuditAction`), and add the count of cart check bills printed but never sent to the X / Z "exceptions" block (or just audit). The cost is an `@pos/events` schema, an audit row and a test, with no table. Alternative: accept no event, and record the accepted risk in §12.3 with the owner's name. **The owner decides.**

### R2-M-5: Test #60g asserts a 400 for a queued replay, but a non-queueable command ignores `X-Queued-At`
**Where:** #60g l. 1735 ("the command is not queueable (`queued_at` set → `400`, 00 §3.12)"); §6.3a Permission l. 1241.
**Problem:** 00 H-1 (b) (HPA l. 222) and `route.ts:253-257`: on a non-queueable command the header is **ignored** (`queuedAt = null`). The command runs and prints. The test cannot pass without an unlisted 00 change. "Not queueable" is a client rule (the client never puts it in the `QueueStore`), as 03c §6.14 treats `PrintTakeawaySlip`.
**Fix:** Change #60g to "`X-Queued-At` is ignored (as 00 H-1 (b)); the client test (#60h) asserts it is never queued, and the button is disabled offline". Add the offline-disable to §8.

### R2-M-6 (OWNER): An addition cart (sent token plus unsent lines) has no rule
**Where:** §6.3a l. 1239; §8 l. 1531; 02b v1.0.25 §8 l. 842 ("On a sent token with money due **the cart** and the token view send `PrintCheckBill`").
**Problem:** OR-5 has "unsent cart" and "sent token with money due". An addition cart is both. `PrintCheckBill` prints the open bill without the new lines, so the customer is handed a total lower than what they will pay. `PrintCartCheckBill` prints only the new lines. Neither is right, and the spec does not say which button does what.
**Fix (recommended default):** On an addition cart with unsent lines, "Print check bill" sends `PrintCartCheckBill { draft, adds_to_order_id }`. 05 then prints the token's open bill lines (`ensure`-free read: projected or live bill, as §6.3's lines read, +2 statements) plus the draft lines, headed `NOT SENT YET - CHECK BILL`, with one total. Alternative: grey the action until the addition is sent. **The owner decides.** Write the result in 05 §6.3a, §8 and 02b §8.
