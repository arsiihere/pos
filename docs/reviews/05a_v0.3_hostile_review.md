## BLOCKER

### B-1 The listed-only guard sits where most listed-only permissions are never checked — TXT

**Where:** 05a:91 (the pipeline rule "permission in the list ∧ session on an `everyone` device → 403", "00 §3.7, after the permission resolve"), 05a:87 ("Plus answering a 01d request of a money kind"), 05a:110, 05a:275.

**Problem:** the rule hooks the **registry** permission of a command (`authorize`, `hub:commands/route.ts:145`). Of the ten listed permissions, these are not checked there:

1. **`close-shift-for-others`** is a second right checked inside the handler with `ctx.directory.resolve`. This is the case for `CountShift`, `CloseShift`, `HandoverCount`, `RemovePayment` of another person's payment and the `shift` query (05:1234, 05:1280-1297, 05 H6-7). The registry permission is `manage-own-shift` or `take-payment`, which are not listed.
2. **Answering a money request:** `AnswerRequest` is `permission: 'checked-in-handler'` with `ctx.permission = null` (00 §3.7, 01d:1527). The pipeline rule never sees a permission. The approve-void range check is the handler's rules 5–6.
3. **`view-audit-log`** and the `manager` screen's reads are **queries** (`GET /queries/…`, 00 §6.2). The rule is written for commands only.
4. **`access-hub-admin`** on `/admin/queries/*` is checked by `requireAdmin` (`hub:auth/guards.ts:246-248`), not by a command. An admin session that already exists on a device later set to `everyone` keeps reading every admin list (see M-6).

**Failure:**
- Ali's leaked manager PIN on the `everyone` counter closes another cashier's shift and removes another cashier's payment. 05a promises these are blocked, but they go through.
- `AnswerRequest` on a void is not refused by any rule as written. Test 4 (05a:319) fails against a literal build, or the builder invents where the check goes.

**Fix:**
- Define one function `listedOnly(ctx, permission)` and name every call site: the pipeline after `authorize`, every handler that calls `ctx.directory.resolve` for a listed permission (05 commands listed), the query registry (the query's permission, plus a query declaring a listed second right), `requireAdmin`, and `AnswerRequest`.
- For `AnswerRequest`, place the check in `preRead` **and** in `prepare`, right after rule 3 (the PIN rule) and **before** argon2. That way a refused answer verifies no PIN and counts nothing, as M38 does. Add it to 01d §3.3 rule 4 (b)'s order list (row D-2).
- Add one test per call site (see M-13).

### B-3 D-1's binding rule has no transitions, legacy rows or hardware rows: bindings stick to the wrong person — TXT

**Where:** 05a:157 (D-1: "a listed device with exactly one person (any hardware) is bound to that person permanently, from `DeviceProfileSet`. Other devices follow today's tablet / kiosk rows by hardware"); 01d:716 (phone row); code `hub:alerts/bindings.ts:54-63,97-105`, `hub:alerts/routes.ts:115-119`, `client:features/alerts/socket.ts:90-94`.

**Problem:**
1. **No transition rule.** Profile edits change one-person ↔ several ↔ `everyone`. The projection writes a permanent row (`session_id NULL`). Two facts make that row stick:
   - `SessionStarted` is ignored for a device whose row has `session_id IS NULL`. The code's guard is `WHERE device_bindings.session_id IS NOT NULL` (`bindings.ts:100-105`).
   - `SessionEnded` deletes only by `session_id`.

   So once a permanent row exists, only `DeviceRevoked` removes it. D-1 does not say that a `DeviceProfileSet` with ≠ 1 person deletes the row.
2. **"Other devices follow … by hardware" leaves `phone` with nobody.** Today's rows are phone (owner), tablet (last signed in), kiosk and KDS (none). A `phone` listing two people, or an `everyone` phone, matches no row. The code skips phone sessions (`bindings.ts:97-99`).
3. **Routes:** only tablet and phone bindings route (`routes.ts:115-119`). A one-person listed `cashier_kiosk` (the owner's laptop) gets a permanent row that never routes. That breaks the BF-3 rule (kiosk = device targets only) or does nothing, and D-1 says neither.
4. **Replay and legacy:** history holds `DevicePaired { device_type: 'phone', owner_staff_id }` long before the upgrade `DeviceProfileSet`. D-1 drops the "from `DevicePaired`" source. It does not say whether the legacy phone rule stays for rows with no profile, or how the bindings projection reads profiles: its `reset` + replay must rebuild exactly (01d:731).
5. **Client:** alert mode is chosen by `device_type` (`socket.ts:93`: kiosk and phone open alert mode, the tablet page never does). A one-person listed tablet bound permanently gets no alert socket on its page. Neither D-1 nor C-1 says the client changes.

**Failure:** Ali's phone is upgraded to `listed [Ali]` (permanent row Ali). The manager edits it to `listed [Ali, Bilal]` (Ali lends it to Bilal for the shift). The row stays Ali, so Ali's urgent alerts, approval receipts and personal notices (01d:776, never "for X") keep ringing on the phone in Bilal's hand. Bilal's sign-in never takes the binding.

**Fix:** write D-1 as a full rule table:
- **Inputs:** `DevicePaired`, `DeviceProfileSet`, `SessionStarted`, `SessionEnded`, `DeviceRevoked`, `BusinessDayClosed`.
- **One-person listed** → upsert the permanent row.
- **Any other profile** → delete a permanent row. From then on the hardware rule applies, and `phone` hardware not bound to one person follows the **tablet** rule.
- **A device with no profile yet** keeps the legacy `DevicePaired` phone rule.
- Say what happens to `cashier_kiosk` hardware (no row, BF-3), and whether `routes.ts` routes a one-person tablet with no idle check (the phone rule).
- Say whether the client opens alert mode for it.
- Test 14 gains the transitions (1 → 2 → everyone → 1) and replay equality.
