## 3. New findings (introduced by the v0.2 changes)

### N-1 The `:alerts` process loses the session and the device context on its own restart, while the page keeps running — MAJOR, TXT

**Where:** M-21 (05b:103: "Held in memory in `:alerts`; after a process restart native assumes **signed out** … a restarted page is signed out too"), M-4 / M-10 (`:alerts`), M-8, M-10, M-15, §10.3 test 21.

**Problem:** with the service in its own process (the M-10 fix), the two processes restart **independently**:
- `:alerts` alone is killed in these cases: S5 `am kill`, an OEM kill, a crash in the service, or the watchdog restart.
- The page in the main process keeps running and stays signed in.
- It never re-sends anything, because `setSession` goes out "on every session change" and `setDeviceContext` "on every profile load or change".

After such a restart, native wrongly believes:
- **signed out**, so M-8 posts alone and a signed-in tablet shows **two banners and two sounds**; and M-15's install window opens while someone is signed in. The install kills the main process and signs the person out mid-shift.
- **`always_on` unknown**, so a Pass tablet falls back to the 10 s urgent repeat (O-15 says one sound per step).
- **language unknown**, so the lock lines fall back to a default language.

The reverse also happens. When the main process restarts (renderer recreate, OOM), `:alerts` still holds "signed in" until the new page speaks, and M-21 does not say a fresh page load calls `setSession`.

After a reboot or an update, no page runs until someone opens the app (test 20, S6), so the service again has no `always_on` and no language.

**Fix:**
- Persist `always_on` and `language` in plain prefs; they are not secrets. Keep only `signed_in` in memory.
- When `:alerts` starts, it broadcasts a `service_started` notice. The plugin then emits `state` with a new flag `needs_context: true`, and the page re-sends `setSession` and `setDeviceContext`.
- The page calls both at **every page load** as well as on every change.
- Until the page has spoken after a service restart, the M-8 hold still applies: wait 1 s for `reportShown`, then post.
- Tests 5 and 15 gain "service restarted while the page stays signed in".

### N-2 The "hub lost after load" fallback cannot tell the main frame, misses HTTP errors, and test 24's second half has no mechanism — MAJOR, TXT

**Where:** M-1 (05b:83: "A main-frame load error on the hub page (`WebViewListener.onReceivedError`) recreates into the bundled 'hub unreachable' page"), §10.3 test 24 (05b:269).

**Problem:**
- **No main-frame check.** `WebViewListener.onReceivedError(WebView)` receives **only the view**, not the request (`cap:WebViewListener.java:25`). `BridgeWebViewClient` calls it for every failed load, subresources included (`cap:BridgeWebViewClient.java:44-52`); only its own `errorPath` branch checks `request.isForMainFrame()` (`:54-57`). So a listener cannot tell a missing image or script from a failed page load. One failed subresource during a Wi-Fi blip would recreate the activity, reload the page and **sign the person out** (the session token is in page memory, 05b:51).
- **HTTP errors are not covered.** A main frame answered with an HTTP error goes to `onReceivedHttpError` (`:85-96`), not `onReceivedError`. Examples: `409 HUB_NOT_PROVISIONED` after a reset, or `403 HOST_NOT_ALLOWED` after `advertised_host` changed (`/staff/` is group `admin-page`, `hub:server.ts:245`, guarded by host, provisioned and guest). M-1 does not name that callback, so the WebView shows the hub's JSON error with no way to reach "Change hub address".
- **Test 24's second half cannot happen.** "Hub stopped while the page is open → hub-unreachable page" has no trigger: an SPA that is already loaded makes no main-frame load when the hub stops. If it did switch, a `1012` hub restart (ship-client, update) would sign everyone out.

**Fix:**
- Subclass `BridgeWebViewClient` (set with `bridge.setWebViewClient`). Override `onReceivedError(view, request, error)` and `onReceivedHttpError(view, request, response)`, and recreate into the bundled page **only when `request.isForMainFrame()`**.
- Test 24's second half becomes: "the hub is stopped while the page is open → the page shows 'Can't reach the hub' (client state), with no reload. A later main-frame load failure → the hub-unreachable page."

### N-3 The native probe runs on the main thread before `super.onCreate` — MAJOR, TXT

**Where:** M-1 (05b:83: "`MainActivity`, before `super.onCreate`, reads the stored hub origin and calls `probeHub`"), M-16 (OkHttp `GET /health`).

**Problem:**
- `BridgeActivity.onCreate` builds the bridge from `config` at once: `super.onCreate` → `load()` → `Bridge.Builder.setConfig(config).create()`, which loads `appUrl` (`cap:BridgeActivity.java:22-50`; `cap:Bridge.java:224-233, 324`). So `config` must be final before `super.onCreate` returns.
- A synchronous OkHttp call on the main thread throws `NetworkOnMainThreadException`.
- A blocking call that waits for the timeout ("no answer", the M-16 case) blocks the UI thread long enough for an ANR at every boot while the hub is down.

**Fix:**
- Override `load()` so that it does nothing at first.
- Show a splash, run `probeHub` on a background thread, then set `config` on the UI thread and call `super.load()`.
- `BridgeActivity`'s lifecycle methods already allow a null `bridge` (`cap:BridgeActivity.java:73-115`).
- §11 step 1's device check gains "the hub is off at app start → no ANR, the bundled page appears within the probe timeout (state it, for example 3 s)".

### N-4 Lock task has no native input and nothing re-enters it after a reboot or an update — MAJOR, TXT

**Where:** M-17 / O-16 (05b:99: lock task always on `everyone` tablets, never on `listed`), M-21 (`setDeviceContext({ always_on, language })`), test 20 ("reboot → service up within 60 s **without opening the app**"), M-15 / M-6 (the self-update restarts the service only).

**Problem:**
- **No input.** The decision "`everyone` → lock, `listed` → no lock" needs the 05a profile audience. `setDeviceContext` carries only `always_on` and `language`, and it is held in `:alerts` memory, while `startLockTask` runs in the activity in the main process.
- **Nothing re-enters lock task.** Nothing in v0.2 starts the activity, or lock task, after a reboot or a self-update. A self-update kills the locked task's process, and `MY_PACKAGE_REPLACED` restarts only the service. Test 20 says outright that the app is not opened after a reboot. So after every reboot and every APK update, an `everyone` tablet sits on the stock launcher, outside lock task, until someone opens the app. That breaks O-16 ("always").
- **Profile changes.** There is no rule for a profile change between `everyone` and `listed` while the app runs.

**Fix:**
- Add `lock_task: boolean` (true when the profile audience is `everyone`) to `setDeviceContext`. Persist it in the main process's prefs.
- The activity calls `startLockTask()` / `stopLockTask()` in `onResume` from that value. `stopLockTask` is native-only and follows the profile, never a page call (O-14 still holds: no page-callable exit).
- On device owner, set the app as the persistent preferred HOME activity (`addPersistentPreferredActivity` with `CATEGORY_HOME`) and declare `android:lockTaskMode="if_whitelisted"`. The activity then comes back by itself after a reboot or an update.
- Test 20 gains: reboot → the app is in front and locked; an APK update → the app is in front and locked; profile `everyone` ↔ `listed` → lock follows.

### N-5 The page side of the close-code rule still wipes on any socket `4403`, including the guest Wi-Fi — MAJOR, TXT

**Where:** §3.5 last line (05b:141), D-2 (05b:200: "a page `DEVICE_TOKEN_INVALID` / `DEVICE_REVOKED` → `confirmRevoked()` then the existing wipe"), test 6.

**Problem:**
- **Socket closes are not covered.** The signed-in page's own session socket handles `4403` by unpairing at once (`client:features/staff/StaffApp.tsx:225-226`, then `wipeDeviceKeys` at `:461`). The pre-auth guest-network and Host closes are also `4403` (`hub:auth/guards.ts:93-95, 107-109`). D-2 routes only the **HTTP codes** through `confirmRevoked`. So a signed-in tablet that roams to the guest SSID gets `4403` on its session socket and wipes IndexedDB → PairAgain → a new pairing request and a manager's approval. That is B-1's failure again, on the page side.
- **`revoked: false` has no rule.** "`confirmRevoked()` then the existing wipe" does not say what the page does when native answers `revoked: false`.
- **Page and native end up split.** The native token is kept, the page has none, and `state.paired` is still `true`.

**Fix:**
- D-2: when `PosNative` is present, **every** page unpair trigger goes through `confirmRevoked()`: HTTP `401` / `403` and socket `4403`. Wipe only on `revoked: true`. Otherwise show the 00 §8.4 text ("Connect to the staff Wi-Fi") and keep retrying.
- Test 6 gains the socket-`4403` case and the `revoked: false` case.

### N-6 A page-owned urgent repeat dies when the screen goes off after the first ring — MAJOR, TXT (owner may confirm)

**Where:** M-10 (05b:92: "the poster owns it … the page if it reported the pair within 1 s"), O-15, test 22 (only "signed in **with the screen off**" at the time of the alert).

**Problem:**
- Ownership is fixed at the first post. A manager is signed in with the screen on, an urgent alert arrives, and the page reports and rings.
- The manager walks away, and the screen times out about a minute later. The activity stops, and the WebView becomes hidden.
- Chromium throttles timers in hidden pages, and audio from a hidden page is not guaranteed. Capacitor itself does not pause timers (`keepRunning`, `cap:Bridge.java:1370-1378`), but that does not stop Chromium's throttling.
- So the 10 s repeat stops, or drifts to once a minute, while the alert stays unseen. The service will not take over, because the page owns it. This is the v0.1 M-6 problem #1, now for the case where the screen goes off **during** a repeat.

**Fix:**
- Ownership moves to the service when the activity stops (`onStop`, or a page `visibilitychange: hidden` through `reportShown`'s channel). The service starts the repeat for every reported pair that is still open and unseen, without a new first ring, and hands it back on `onStart`.
- Add a test: screen off during a page-owned repeat → the service continues within 10 s.
- This refines O-15 rather than reversing it. Owner: confirm.

### N-7 On the guest Wi-Fi the probe says "Not a POS hub", not "Connect to the staff Wi-Fi" — MINOR, TXT

**Where:** M-16 (05b:98), test 18 ("guest Wi-Fi → the M-16 messages").

**Problem:**
- `/health` is in group `health`, which uses `isGuest`, not `guest` (`hub:auth/guards.ts:72`). So it never returns `GUEST_NETWORK_FORBIDDEN`.
- A guest client gets `200 { data: { status } }` (`hub:lib/health.ts:21`), which has no `hub_version`. M-16 maps that to "Not a POS hub".

**Fix:** `200` whose `data` has only `status` → "Connect to the staff Wi-Fi". Drop the `GUEST_NETWORK_FORBIDDEN` row from M-16; it stays in §3.5, where `/app/android/latest` does return it.

### N-8 The guard reads `getUrl()` on the plugin thread; a path check within one origin is not a boundary — MINOR, TXT

**Where:** §3.6 (05b:145: "reads … `bridge.getWebView().getUrl()` on every call").

**Problem:**
- Plugin methods run on the `CapacitorPlugins` handler thread (`cap:Bridge.java:138, 217, 822-860`). Android requires WebView methods on the UI thread and throws for other threads. So the guard must post to the UI thread and wait.
- Between the page's call and that read, the main frame can navigate. The URL read can then be the new page's: a time-of-check / time-of-use race.
- Path rules inside the hub origin (`setDeviceToken` from `/pair` only) are defence in depth. Any script on that origin can open `/pair` itself.

**Fix:**
- State "read on the UI thread".
- State that the origin check is the boundary and the path check is a guard against mistakes, which O-14 already accepts.
- Note that Capacitor already refuses non-main-frame calls (`cap:MessageHandler.java:27-33`).

### N-9 Re-pair paths: the hint is lost, the refused-type flow contradicts itself, and a page / native token mismatch has no rule — MINOR, TXT

**Where:** M-3 (05b:85: native "clears the page store and starts a new request"), H-2 (05b:196: "show its message and start a new request"), §3.4 (05b:129: "→ `/pair`"), M-22.

**Problem:**
- **The hint is lost.** Only the first run opens `/pair?hint=tablet`. PairAgain goes to plain `/pair` (`client:features/staff/tables/PairAgain.tsx:10`), and so do the revoke path and H-2's "new request". On every later pairing the approver gets no `tablet` hint, which invites the very non-tablet approval M-3 refuses.
- **"Native clears the page store" contradicts H-2.** Native cannot clear one IndexedDB database. `WebStorage.deleteOrigin` would also delete `pos-queue`, which holds the unsent orders. H-2 does not wipe.
- **A refused type resumes as that type.** The pair page writes the keys first (`hub:auth/pair-page.ts:216-218`). A refused `phone` approval stays in IndexedDB, and the next `/pair` load **resumes** it (`resumePaired`, `:131-133`) straight to `/staff/` as a phone, with no native token and no alerts.
- **Resume never informs native.** `resumePaired` never calls `setDeviceToken`. So if native lost its copy (M-22, or a kill between the IndexedDB write and the native call), the page has a valid token and native has none. No rule says which side wins. M-22 forces a full re-approval although the page's token works.

**Fix:**
- When `PosNative` is present, the pair page sends `hardware_hint: 'tablet'` whatever the query.
- On a refused type, the page wipes its own three keys (`wipeDeviceKeys`) before it starts a new request.
- `resumePaired` calls `setDeviceToken` when `PosNative` is present.
- `state.paired: false` while the page has keys → the page offers its keys once through `setDeviceToken`. Only a `confirmRevoked` result leads to a wipe.
- Test 8 gains the cases.

### N-10 EncryptedSharedPreferences used from two processes — MINOR, TXT

**Where:** §5 (05b:210), M-2, M-1 (`MainActivity` reads `hub_origin`), M-4 (`:alerts` reads and clears `device_token`).

**Problem:**
- SharedPreferences is not multi-process safe. Each process caches the file, so a clear in `:alerts` (revoke) is not seen by the main process, and a write from the plugin (`setDeviceToken`, main process) is not seen by `:alerts` until it reloads.
- Two processes creating the Tink keyset at the same time can write different keysets. The next read throws `AEADBadTagException`, which M-22 turns into "not paired", and that means a re-approval.

**Fix:**
- Name one owner per file. `:alerts` owns `device_token` and `device_id`: the plugin forwards `setDeviceToken` by broadcast, and `:alerts` replies.
- The main process owns `hub_origin` in its own file.
- Create the keyset only in its owner process.
