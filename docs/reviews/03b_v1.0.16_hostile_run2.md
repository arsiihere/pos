## BLOCKER

### R2-B-1 — The tap check refuses every order that has a no-station line
**Where:** §3.4 l. 207 ("if any live non-deal line of the order is neither `done`, handed over nor served … → toast, nothing sent"); test 113 last clause.
**Problem:** `order-view` gives a line the engine does not hold `stage: null` (`seating-orders.ts:31–35`: deal header, zone line, or "a line the engine does not hold"). No-station lines are never `done`: bottled drinks, and **option children with no station** (every item with a plain-child option). So the toast fires on every such order, and "Handed to customer" never sends. This contradicts l. 204: station-less lines are "outside readiness … handed with the bag". It also contradicts 02b §8, where Hand over sends them in the same `MarkServed`. "A no-station line held for a pickup" is not defined anywhere the Pass can evaluate. "Handed over" (Pass `Handover`) at **another** point is not in `order-view` either (`LineView` has `served_at` only, `contracts.ts:19–60`).
**Fix:** Write the check over **engine lines only** (`stage` not null and not `out_of_engine`). Each must be `done` or served. At this point, handed over also counts (from `point_view`). Lines with `stage: null` never block and are always included in the `MarkServed`. For a pickup order, use 02b's one line-ready rule (02b §4.2 `takeawayProgress` / `LINE_READY_AT_SQL`: a no-station line is held until `pickup_at_ms`). So: `pickup_at_ms` set and hub now < `pickup_at_ms` → toast "Pickup at hh:mm — use 'Customer is here' at the counter". After a boost, `pickup_at_ms` is null and nothing blocks. Tests: an item with a no-station option child → sent, child included; a pickup order with a Cola before and after `pickup_at_ms`.

## MAJOR

### R2-M-1 — A paid parking order can never be handed over from the Pass
**Where:** l. 207 ("a row not yet read counts as Due (greyed)"); test 113.
**Problem:** Parking rows leave `open-orders` at billing (02b §3.3 Open (lists): "for dine-in and parking — not billed (unchanged)"; only takeaway gets the `orders_open_takeaway_paid` branch, 02b §6.16). A paid, not-yet-collected parking order therefore has no row. The Pass reads that as "not yet read", so it stays Due and greyed. "Ask a manager" → `RequestUnpaidHandover` returns `{ needed: false }` (02b §6.4a), so nothing ever unlocks it. OQ-7 says parking is handled like takeaway.
**Fix:** After a **successful** read, an order absent from the result is **not Due**: every unbilled takeaway / parking order is listed, so an absent one is billed, fully served, cancelled or day-closed. Grey only before the first successful read. Test: paid parking, absent row → enabled.

### R2-M-2 — An approval or a payment does not reach the Pass, so the action stays greyed
**Where:** l. 207 ("debounced refetch on the order frames", "unlocks … when the row's `unpaid_handover_approved` is true"); 02b l. 775; `takeaway-promises.ts` `PROMISE_EVENTS`.
**Problem:**
- `UnpaidHandoverApproved` goes only to "the placer and the counter devices of the order" (02b §6.19 l. 775). A Pass staff socket is neither, so the manager's approval never triggers a Pass refetch.
- The as-built refetch set has no `OrdersBilled` / `OrdersUnbilled` / `UnpaidHandoverApproved`. It does poll every 30 s, but only while the filter is on.
- `LineComped` (due → 0) reaches only kiosks and `apply-comp` holders (`orders/audiences.ts:53–66`).
- When the Pass itself asked, only 01d's `request_result` reaches it, and nothing says to refetch on it.

So the Cook asks, the manager approves, and the button stays grey.
**Fix:** (a) Add a To 02b row: `UnpaidHandoverApproved` also reaches every staff socket. Its payload holds ids and `due_minor` only, no contact (R3); the G-10 additive pattern. (b) In §3.4, name the refetch triggers: `OrdersBilled`, `OrdersUnbilled`, `UnpaidHandoverApproved`, `LineComped` / `LineCompRemoved` when received, the requester's `request_result`, catch-up and reconnect. (c) Test 113: approval made on another device → the Pass enables without any other frame.

### R2-M-3 — Offline, the action has no defined behaviour
**Where:** l. 207 ("**Tap:** read `GET /queries/order-view` … through the device queue (02b §3.12, `MarkServed` is queueable)"); test 112.
**Problem:** The tap needs a live `order-view` read and a fresh `bill`. Offline, the read fails and the bill is stale. The text still promises the device queue. What the Pass does offline is not specified: block, send unchecked, or use a stale Due state.
**Fix:** One rule. While the socket is down, or when the tap read fails, the action is disabled ("Offline — hand over at the counter"). The queue covers only the send after a successful check (the 5 s toast, `pagehide`). Test: socket down → disabled, nothing queued.

### R2-M-4 — Parking: 02b's estimate ends "not collected" after a Pass→staff `Handover` (OWNER)
**Where:** §3.5 Handover step 7 (l. 237: "not for a takeaway / parking order … closes by `pass_closures` when its lines settle (the customer is served …)"); OQ-7, OQ-9.
**Problem:** 02b §3.7 now makes the `served_estimate` tick skip **takeaway only** ("Dine-in and parking unchanged"). For parking, a Pass→staff `Handover` is followed `served_estimate_ms` later (180 s default) by `ItemServed { source: 'estimated' }`. That settles the Ready, so `pass_closures` closes it and the counter alert, and the amber stops. Step 7's claim that a parking Ready waits for the customer is false for parking.
**Fix (owner):** Recommended default: accept it for parking, since a hand-over to a runner counts as delivered at the estimate (run 1 m-9 gives the reason). Then state in step 7: "parking: the Ready stays open until the lines settle, which includes 02b's estimate after a `Handover`", and add a test. Alternative: 02b also skips parking (a 02b change).

### R2-M-5 — The manager override OR-7 removed is still in the task list and the strings
**Where:** §11 task 48 (l. 775: "Due greying **+ manager override**"); §8 l. 586 (string `pass.hand_over_anyway`).
**Problem:** OR-7 is binding: "no client override". The builder works from task 48 and the §8 string list, and both still describe the override. The strings that OR-7 does need are missing: "Ask a manager", "Waiting for a manager…", and the rejected text (02b test 90).
**Fix:** Task 48 becomes "Due greying, 'Ask a manager' (`RequestUnpaidHandover`), tap-time check, Undo toast". In §8, remove `pass.hand_over_anyway` and add `pass.ask_manager`, `pass.waiting_manager` and `pass.manager_rejected` (or reuse 02b's keys and say so).

### R2-M-6 — Tests miss the cases that break OR-2
**Where:** §10 tests 112–114.
**Problem:** These cases have no test:

- (2) A pickup order before and after `pickup_at_ms` (B-1).
- (3) A two-point order, where A hands over while B is done but not Ready, and B's card and B's Ready close (m-5 below).

- (5) Approval or payment arriving from another device (M-2).
- (6) Offline (M-3).
- (7) A line removed during the 5 s window (m-6).
- (8) The counter and the Pass handing over at once: the second is all `skipped`, 200, no queue-log entry.
- (9) "Handed to customer" with no `MarkReadyToServe` pressed: no counter alert exists, the lines are served, and nothing else is raised.
- (10) Test 114 "board drops it" when the token has an unserved addition (m-4).

**Fix:** Add (1)–(10).
