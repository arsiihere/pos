### R2-M-3 — `business_day_end_local_ms`: "first occurrence ≥ opened_at + gap" has no formula, no helper and one test case
**Where:** 01a §3.3 l. 517, header item 5, test 218 ("The hub's pickup bound is 02b's test 60"), OD-10; 02b v1.0.25 §3.2 step 2b, test 60.
**Problem:** the only new time math of the package is stated in prose. The straightforward JS form `base + (end − localTimeOfDayMs(base, off)) % 86_400_000` is wrong whenever `end` < the local time of `base` (JS `%` keeps the sign → `latest` in the past → every pickup `no_time_left`), and that is the **normal** case (day opened 08:00, end 04:00). 02b test 60 covers only "opened 08:00, end 04:00, 04:00 accepted, +1 ms refused". Not covered: base local time == end (must give `base`, not `base + 24 h`); end later the same day (end 23:00, opened 10:00 → same day); a day opened after midnight and before end (opened 01:00, gap 4 → 05:00 → next day 04:00, 27 h); `day_min_gap_hours = 0` opened 03:55 → `latest` 04:00 → `no_time_left` after the 10-min lead; a forgotten close past the end (day still open at 05:00 → `no_time_left`, the client's "Close the day first"); a non-zero `utc_offset_ms` (PKT +5 h) so a UTC-day bug shows. 01a owns the setting's meaning (§3.3 states the rule) but cites no test for it.
**Fix:** 02b names a pure helper in `@pos/domain` beside `localTimeOfDayMs` (01a l. 555), e.g. `nextLocalTimeAtOrAfter(baseMs, localMs, utcOffsetMs) = baseMs + ((localMs − localTimeOfDayMs(baseMs, utcOffsetMs)) % D + D) % D`, and test 60 (or a domain unit test) lists the six cases above with offset 18 000 000. 01a §3.3 cites the helper and test 218 cites those cases.
